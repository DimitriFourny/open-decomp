Stage 08 · Reconstruction

Source reconstruction

Reconstruction turns an immutable structured SSA program, recovered types and native evidence into a second, source-shaped model: named values, expressions, a signature, call and return interfaces, promoted stack storage and conditions. It never mutates the analyzed program, never re-structures the CFG, and every rewrite is either an exact bit-level identity or a recorded, proof-carrying presentation change.

Where this sits in the pipeline

The stage consumes an EmissionInput (src/emitters/model.ts): the already structured function (StructuredFunction), the optional TypeRecoveryResult, display names and annotations, and — for native binaries — a SourceEvidence record. That evidence is produced by recoverSourceEvidence in src/service/analysis/source-facts.ts and contains the target ABI profile, observed and proven callee interfaces, address facts (strings, immutable bytes, imports, Objective-C identities), positive caller return demands, observed written result storage, variadic actual signatures and bounded memory-shape transfers. The calls & ABI page explains how those observations are gathered; reconstruction only consumes them. The structured tree and SSA arrive from SSA, values & stack and the structuring pass; types come from Types & metadata.

The caller is the Renderer constructor in src/emitters/renderer.ts: 

this.program = reconstruct(input, context, options.view === 'checked' ? 'checked' : 'source');

reconstruct(input, context, view) is defined in src/reconstruction/index.ts. Its own default is 'checked'; the renderer makes an explicit choice, and the CLI default view is source. The result is a model object (Reconstruction), not text. The renderer consumes it to choose variable names, types, call spellings, requirements comments and mappings. Nothing in this stage writes to the IR, the structured tree or the type result.

Invariant

Reconstruction is a bounded view. The header comment in src/reconstruction/index.ts states the contract: “The original structured SSA remains immutable. Reconstruction is a bounded view: pure expression folding, demand-driven live phi copies, exact physical snapshots and conservative source projections. No CFG is structured twice.” The renderer and the publication checks rely on this: they may print fewer statements than the IR contains, but never a different control graph.

Refusal

Reconstruction throws OperationError with code invalid_input when the structured tree owns a block twice, and with resource_limit when the block, statement or value budget is exceeded (context.budget.blocks / context.budget.ir_nodes). It never silently truncates a function. Publication failures later use unavailable_semantics (see Requirements and validation).

The sub-pipeline inside reconstruct()

reconstruct is one function with a long body, deliberately written as a linear pipeline over shared maps. Every helper receives those maps explicitly; there is no global state, and each pass is free to add synthesized values through the planner's make/alias callbacks. The order below is the execution order in the source.

1. Indexing: ownership, values and edge sources

The first pass walks the structured region tree with an explicit worklist. For every block it records the region, its parameters and every defined value: statement results, call results and register_outputs. Assignment nodes are indexed separately because expression folding needs only pure definitions. Each control transfer is recorded with its owning block; after all blocks are known, every transfer copy is attached to its destination block parameter in parameterSources. That map is the phi-source view used by later passes and by the identity lattice.

Budgeting is part of the pass, not an afterthought: context.checkpoint is called per region, statement, value and transfer copy; the block count, statement count and value count are compared with context.budget.blocks and context.budget.ir_nodes. Duplicate block ownership is a hard invalid_input error because it would make every later map ambiguous.

2. Pure folding and range normalization

foldExpressions (src/reconstruction/expressions.ts) folds only pure SSA expressions. It resolves identity bitcasts, applies integerIdentity (neutral operands such as x+0, x|0, x*1, x<<0 and same-type x&ones), and rewrites subtract/flag patterns into comparisons. It deliberately refuses x-x, x*0 and x^x, because those would erase an operand that may be indeterminate. This pass runs in both views: it is semantic simplification, not presentation.

normalizeSourceRanges (src/reconstruction/source-ranges.ts) runs whenever native evidence exists. It computes forward, edge-constrained unsigned intervals over the values that reach the upper lanes of concat operations — the ARM64 pattern where an upper 32-bit cell is known to be zero or a narrow result. Parallel copies are evaluated before destination facts are joined; a branch contributes both the tested bit range and definedness on the selected edge; growing loop bounds widen conservatively. Only a proof that the upper part is zero lets the concat collapse to a narrower value. Failed proofs leave the expression untouched.

3. Source planning: calls, formals, results, signature

planSource (src/reconstruction/source-planner.ts) is the largest single step. It creates the call/return/tail projections, entry parameters, the function signature, the parameter-name map and the requirement list. It also supplies three closures used by later passes: make (create a deterministic synthesized value and register it), alias (replace a value's expression with a bitcast and force it inline) and materialize (give every live anchored integer forced-inline definition an ordered statement next to its anchor).

Call interfaces are resolved in this order of strength:

  1. Variadic library rule. With view === 'source', a call_argument_signatures entry can supply the actual types for the call.
  2. Observed contracts. A single established call contract is used in either view; in the source view several established contracts are accepted when they are identical (repeatedContract). Both paths are admitted through arity_closure.
  3. Established declaration. signatureFor(subject) accepts exactly one established or asserted signature for the call and the function, whose ABI id matches the evidence ABI and whose types resolve to ABI types. Conflicts and missing pieces yield null.
  4. Inferred callee. Otherwise an InferredCallee from SourceEvidence.callees (and, in the source view, source_callees) provides a register prefix plus optional stack parameters. If a single register location is only partially covered by the observed bindings, bind refuses rather than inventing bits.
  5. Physical fallback. A projection with kind physical keeps the original node.arguments, node.results and register_outputs. This is what the renderer prints as an explicit interface.

The binding primitive is worth knowing because it fails conservatively. Given an ABI location and the register bindings at that boundary, bind walks the overlapping cells in offset order, requires them to tile the location exactly from low to high, extracts a sub-slice when a cell is wider than its contribution, concatenates when several cells contribute, and finally checks that the assembled width equals the expected type width. A gap, an overlap, or a width mismatch returns null. The companion result function then validates coverage before replacing cells, and aliases each original cell to a bitcast/extract of the whole result (or to an insert when only part of a cell is consumed). This is how a returned uint64_t can be reassembled from w0 while the high half of the register remains independently observable.

Entry formals are not guessed from register spelling. The planner asks the target ABI to classify a synthetic call with sixteen pointer-width integer parameters and a second one with sixteen double parameters; the resulting register locations are the candidates. A candidate becomes a formal only if the entry block actually binds one of its cells and the value survives to the demand phase. In the source view, an untyped scalar-width floating-bank argument is presented as the IEEE value of its lane ({ kind: 'float', bits: 32 | 64 }), because every supported C ABI passes such an argument as float/double. In the source view, a hidden-result pointer register outside the argument registers (AAPCS64 x8) becomes the incoming indirect result location under the indirect_result rule.

If an established, completely classifiable, non-variadic function signature without a hidden result exists, every parameter and every return location must bind; only then are the synthetic formals discarded in favour of the declared ones, and the declared parameter names are copied into parameter_names. The functionSignature also suppresses inferred result rules: a declaration is stronger evidence than any observation.

4. Stack planning, cell recombination and closure

planSourceStack (src/reconstruction/source-stack.ts) receives the call and return projections from planSource because outgoing stack arguments and return storage decide what may be private. Its first job is an address fixed point: entry-SP is offset zero; bitcasts, recombined cell halves, add/sub with a constant, and agreeing phi inputs propagate offsets. Only accesses with a known offset can be classified.

recombineSourceCells (src/reconstruction/source-cells.ts) runs next, and only in the source view. It recognizes complete contiguous root cells that are read together as a phi group, and whose cells are all written on an edge by corresponding slices of one value, by a constant, by an unknown of one reason, or by the unchanged cells of another group. When every incoming edge agrees, the group is transported as one whole bitvector and the per-cell edge copies are replaced by one copy of the synthesized value. The original copies stay in the checked view.

After that, reconstruct validates tail-call arity closure and records ABI assumptions. A tail whose boundary claims a complete argument list is downgraded unless presentation('arity_closure', …) admits the proof. Library-contract and Objective-C-selector closures additionally call requireAbi. In the source view, SourceEvidence.source_callees closures are validated inside planSourceStack so that frame classification sees the final answer; a refused closure reopens the conservative area.

5. Demand, normalization and the identity lattice

Before rewriting expressions, reconstruction computes a conservative demand set. It roots every parameter, every boundary argument/result/input/output, every effectful operand (loads, stores, calls, unknown effects, controls and return values), the entry storage base and every indirect target. If it encounters a consumer kind it does not model, it sets complete = false and disables demand filtering entirely. sourceExpressionDemand then walks phi inputs and expressions to close the set. The comment in the code is explicit that this is an over-approximation: it is only used to avoid undemanded pure rewrites, never to remove an effect.

normalizeSourceExpressions (src/reconstruction/source-expressions.ts) is a worklist fixpoint over definitions. It resolves identity chains, rewrites same-type truncations to extracts, folds constant expressions, and — in the source view only — applies the presentation rules listed in Results, conditions & value rewrites. Dependencies include every inspected definition, so a rewrite invalidates its readers and their cached resolutions. Each candidate is either proved by a rule-specific argument, checked by the local bitvector validator, or rejected and left in its original form.

The identity lattice is a three-level analysis: a value is unreached (undefined), an exact identity (a value id), or conflicting (null). It starts from entry parameters and copy sources, and iterates a worklist: a destination joins the identities of its sources; any disagreement becomes null and never recovers. Ignoring unreached backedges is what lets a loop-carried register be recognized as unchanged on the paths that actually execute. Every demanded, non-trivial identity is published as a bitcast alias, and the expression worklist is drained again.

6. Physical snapshots, exit scratch and liveness

Register snapshots are reduced against the entry identity: a binding whose value is still identical to its entry value is omitted. This snapshot path is used when there is no source plan (for example, synthetic IR callers). With native evidence, physical_inputs is deliberately empty: planSource's call and return projections carry the interface explicitly. A projected return stores only its uncertain outputs. The checked view's visible difference here is that those uncertain return outputs stay outputs (an uncertain physical overlay), while the source view may move ABI-scratch slices to exit_scratch.

The source view then converts possible-return slices into exit_scratch. This is the careful part of the return model. For each inferred return, an output slice that overlaps positive result evidence stays an output. Otherwise scratch(root, start) walks backward through lossless transport (identity bitcasts, extracts, concats, phis) and classifies the slice as:

ABI scratch
The slice reaches only entry values of the same register root and/or unprojected call clobbers, and no result cell. It is moved out of line under presentation('exit_scratch', …) plus requireAbi.
computed scratch
The slice is locally computed but outside an established primary, or above its narrow integer width, and either the interface is approved as void-like or the established primary makes it non-result storage. It is recorded with computed: true and the note that no result-use evidence was gathered.
real result
Anything else — a projected call result, an unknown computation, a slice of a register that callers may read — stays an output, and the return is marked unresolved if it cannot be expressed.

Liveness is demand-driven. Every retained statement and control contributes operand uses; use records a count and the set of blocks. Roots include call arguments, projected inputs, branch conditions, switch values, return results and physical exit overlays. Incoming phi sources are demanded only when the destination is live; this is the “demand-driven live phi copies” part of the contract. Source aliases are immutable expressions, so an alias destination does not demand an edge copy.

Two source-only deletions are handled here. A load marked deadReloadCandidates (non-volatile, dominated by a store covering its bytes) is deferred: if its result becomes live through another path it is restored, and the loop repeats until stable. What remains dead is dropped only if presentation('dead_frame_reload', …) admits the argument that the store covers the bytes, so the load cannot fault. Proven jump-table reads in a switch block are handled the same way under dead_jump_table_load, because the dominating unsigned guard bounds the index and the table bytes are immutable.

7. Inlining, origins and final projections

A value is inlined only when it is a constant, an address, or a pure single-use expression in the same block as its owner, with an expansion size of at most 48 operand occurrences and depth at most 10. Values forced inline by alias (ABI transport, stack addresses, source identities) bypass those limits but are still checked for def-use cycles. Constant rotations are excluded from inlining because the renderer prints them as two shifts that read the operand twice. Every retained statement gets a real owner; if a definition is folded into a consumer, that consumer's origin list includes the folded statements. Unmapped statements are attached to the nearest surviving anchor (their block control, or the consuming call for variadic stores).

When a source plan exists the final signature is sourcePlan.signature; otherwise it is the boundary projector's function signature, dropped when a physical parameter was not represented by the projection. In either case it is dropped when the entry stack base is live (the function is then presented with an explicit entry_sp). Memory views come from type-recovery shapes and are removed when the same node is claimed by two fields (ambiguous), when the field is conflicting, or when the field width does not equal the access width. Diagnostics are emitted for live unknown expressions, unknown effects, physical or incomplete call interfaces, incomplete return storage, and unresolved control boundaries — always as unavailable_semantics warnings with the origin's evidence ids.

Finally, projectSourceTypes (src/reconstruction/source-types.ts) attaches complete source type views to values and fields. In the source view only, projectSourceFloating decides which values have native float/double spelling, and projectSourceSignature decides formal pointer/narrow-integer spellings, slot pointer types and narrow return words. Both run after the model exists because they depend on liveness, boundaries and promoted slots.

Ordering matters

Stack planning must follow call planning (closures decide what may be private); cell recombination must follow stack planning and precede expression normalization (which may then see whole values); the identity lattice must follow stack and call aliasing (aliases are inputs to identities); and floating/signature projections must come last (they inspect final formals and promoted slots). Changing this order changes output, so the code keeps the passes in one visible sequence rather than hiding them behind hooks.

Source vs checked view

Both views run the reconstruction pipeline. The difference is a small, explicit set of view === 'source' gates, plus the three source-only passes (constant projection, cell recombination and variadic stack arguments). The checked view is not “raw assembly”: it still folds pure identities, recomputes ranges, projects boundaries from types and records diagnostics. It simply refuses every rewrite whose justification is a presentation argument rather than a semantic identity.

Signature recovery

A source signature has three independent sources, and reconstruction always prefers the strongest one rather than merging them:

  1. A declaration from type recovery. signatureFor(input.function.id) accepts one established or asserted signature whose ABI matches and whose return and parameter types resolve to void, integer, float, pointer or vector ABI types. The parameter locations are classified with abi.classifyCall; the signature is accepted only if every parameter location binds exactly at entry and every return location binds at every return block.
  2. Observed interface. With no declaration, the ABI classification of sixteen integer and sixteen floating candidates produces the entry formals. Return types are then chosen from, in order: an observed written-result interface (SourceEvidence.function_returns) when it binds on every exit; the selectSourcePrimaryResult decision (src/reconstruction/source-results.ts); a typed floating exit slice; or a changed low ABI return cell. Typed slices come from src/reconstruction/source-register-types.ts (registerTypeSlices, registerTypes, unchangedStorage), which tracks storage per register root rather than assuming one interpretation. If every return path yields one integer result, the widest width is used and narrower results are zero-extended to it; if every path returns the same tuple of types, it is published as return_types.
  3. Tail interface. A tail call may determine the result type only when every tail agrees and the type agrees with the ordinary return type. A proven-void callee suppresses a result only if no return path yields one.

Pointer results are not inferred from width. sourceDataValues resolves a returned address against immutable address facts; if every return yields a string, the presentation records return_pointer: 'char', and if every return yields an object (but not all strings) it records 'byte'. Otherwise the result stays an integer uintptr_t-like value.

projectSourceSignature (src/reconstruction/source-signature.ts) then adds spelling-only types. Its rules are deliberately local:

Rule Evidence required Result
formal_pointer whole-value pointer lineage reaches only 8/16/32/64-bit integer or 32/64-bit float accesses C pointer with pointee kind and width; const only with no write, call escape or unknown effect
formal_low_slice every live use through copies, slots and bitcasts reads only the low 8/16/32 bits narrow integer formal; signed only if a signed comparison/extension/division/remainder/arithmetic shift consumes that slice
slot_pointer_type every value stored to a promoted slot is the same pointer formal, a reload of such a slot, or a whole-element constant step the slot and its reloads share the pointer type
return_low_word the high result slice is provably the zero extension of the low word, no result demand above 32 bits, no pointer/void/tail interface narrow return type

Every rule is a presentation record, and the ones that assume ABI behaviour also call requireAbi. A rule that cannot prove its side conditions simply does not run; the machine type remains.

Naming precedence

Names are display data, never identities or constraints. The planner planSourceNames (src/reconstruction/source-names.ts) receives the renderer's supplied name map, which was built from native symbol names and asserted name annotations (debug/prototype parameter names arrive separately, through source.parameter_names). It returns a preferred name per value/local, plus loop-carried and initial-value maps for the source view. The precedence in the code is:

The distinction the task asks about is real: debug/prototype parameter names are not “supplied” entity names. They arrive through source.parameter_names, which planSource fills from a declared signature (or from argN positionally). planSourceNames ignores a positional argN parameter name when the function is inferred, so a role or library name takes precedence; the renderer's formal naming falls back to the positional argN when no such name applies. Generic names are a small fixed set (condition, call_result, element, result), not valueN: the valueN spelling is the renderer's last-resort identifier for a value (a promoted local falls back to local_<hex offset> or localN) when nothing at all named it. Final identifiers are sanitized by sourceIdentifierStem, which prefixes reserved words and runtime helper names with value_.

Two subtleties are encoded in the ordering. First, a library name is skipped when the value has a role other than address, or when it is an element or condition: a loop element or a control predicate is a stronger description than “the strlen result”. Second, a count role that is not a parameter and is proven decreasing (from loop shape analysis) prints as remaining. The library part is implemented in src/reconstruction/library-names.ts (libraryCallNames, libraryParameterStem). That is why the fixture loop declares uint64_t remaining; rather than count.

Names do not imply semantics

The header of source-names.ts is explicit: these are “presentation-only suggestions: no source intent, type, identity or expression is inferred from an identifier.” A recovery rule must never read a chosen name to decide a type or a rewrite.

Stack promotion & stack arguments

Stack handling is the most conservative part of reconstruction. The stack analysis supplies entry-SP-relative byte offsets; reconstruction never invents an offset for an unknown pointer. The classification of one access group is a decision chain:

Escape analysis and the frame-wide gate

The planner first computes a taint set: every value derived from a stack address, through expressions, phis and memory dependencies. It then walks calls, unknown effects, loads, stores and returns. Any tainted value in possible argument or result storage exposes the frame. For frame saves, an address of unknown origin exposes the whole frame (frameExposed), while an escaped address of known offset only excludes the save group it overlaps: it designates its own object, never a compiler-owned save slot elsewhere. Private-slot promotion itself stays frame-wide: in the source view any escape sets saveEscaped and skips every slot, and the checked view likewise requires !escaped.

Promotion itself has a frame-wide prerequisite. In the checked view it requires !escaped && !unknownCallStorage && !aliased. In the source view it requires !saveEscaped, applies the disjoint-store premise (frame_private_to_activation, recorded when external stores or calls exist), and additionally refuses accesses in blocks that reach an open-arity call, or before one in the same block (the call may read that area), slots overlapping established outgoing argument storage, volatile accesses, and any group that is not a negative, exact, non-overlapping interval. Each promoted group is independently checked by validateStackPromotion (src/reconstruction/local-storage-validation.ts), which enumerates small acyclic paths over a byte-addressed trace and requires every read to be definitely initialized. A rejected trace keeps the memory operations.

This is deliberately all-or-nothing per frame when a frame address escapes: the original code notes the escape in saveEscaped, and promotion is skipped. The readability roadmap calls this out as R1 (see Limitations).

Incoming and outgoing stack arguments

Incoming stack parameters are only inferred for a whole scalar word in an actual ABI parameter slot, and only when there is no declared signature: incomingStack(offset, type, contributors) searches the classified call layout for exactly one stack location at that offset with the same size. It then creates one formal per offset, records the offset in formal_stack_offsets, and finalize appends the demanded incoming formals sorted by offset. Entry return addresses, home space and alignment padding are explicitly not source inputs even though their offsets may be non-negative.

Outgoing stack arguments are recovered the other way, from stored SSA values at a call boundary. sourceStackArgumentParts (src/reconstruction/source-stack-arguments.ts) walks byte facts back to their owning stores. A byte merged at a block entry resolves only when, on every incoming edge, the exact owning store wrote the same value or concat component at the same bit offset, or when the copies agree on one shared block parameter. Anything else leaves the part unresolved, and bindStack returns null rather than adding a fake argument. The call then remains argument_list_complete: false or physical.

Darwin arm64 variadic arguments are a separate rule. planVariadicStackArguments (src/reconstruction/source-variadic.ts) recognizes the ABI convention that every variadic argument occupies an 8-byte outgoing stack slot starting at SP+0. A contiguous run of slots is presented as anonymous trailing arguments only if each slot is written by exactly one store that reaches the call on every path, starts at the slot, is not a frame save, private local or hidden traffic, holds no stack address, is read by no load, and is visible at no other call or tail call. The run stops at the first failing slot; later stores stay explicit and the remainder marker stays, so no argument is dropped and the arity remains open.

Results, conditions & value rewrites

Results and return values

selectSourcePrimaryResult (src/reconstruction/source-results.ts) decides whether an undeclared function returns through the ABI integer or FP result register. It is consulted only when the structured returns carry no explicit value (the lifter's register-result shape). A register qualifies only when it is defined on every exit path; unknown entry values, unprojected call clobbers and addresses into the dead frame disqualify it. FP additionally needs typed IEEE evidence. When both qualify, the decision uses positive caller demand, then the register written last on every exit path, then a native written-result interface naming exactly one. An integer-only qualification keeps the explicit form if the untyped FP register is written after it on every exit path.

Two void-like outcomes are possible. incidental_result means the integer result register qualifies but no exit path establishes it deliberately, no caller demands it, the FP carrier is unchanged or undefined on every exit and there is no tail transfer. indirect_result means the function returns through its incoming hidden-result pointer. Both are presentation decisions under presentation plus requireAbi; the exact exit slices remain in metadata and in the checked view. permitsVoidSourceSignature additionally requires the absence of any positive result evidence before the signature layer accepts a void interface.

Condition reconstruction

foldSourceCondition (src/reconstruction/source-conditions.ts) is a source-view rule that turns a one-bit condition assembled from compare flags (NZCV or EFLAGS insertion/extraction, condition-code logic, conditional compares, FP compare flags) into direct relational predicates joined by && and ||. It is exact by enumeration, not by matching surface syntax: each flag is a function of a few outcomes of its operands (equal, unsigned and signed order, wrapped sign; for IEEE, less/equal/greater/unordered). The condition is tabulated over every feasible outcome and every opaque one-bit leaf, and a decomposition is accepted only if it reproduces all rows. If a condition depends on the wrapped sign or overflow alone, or the table cannot be built within its bound (128 nodes, depth 48), the explicit flag form stays.

Bit slices, cells and shifts

ARM64 sub-register accesses naturally produce many narrow SSA cells for one source value. Two independent mechanisms recombine them. recombineSourceCells works at phi-group level (described above): it replaces simultaneous per-cell edge copies with one whole-value copy. recombineBitSlices (src/reconstruction/source-bit-slices.ts) works at expression level. It traces the bits of a concat, insert, or, xor or shl DAG and rebuilds the value from contiguous extracts of one base, optionally zero-extended. It is a wiring analysis: opaque leaves keep their identity and their ordered indeterminate dependencies. Its bounds are 128-bit width, 128 visited nodes and depth 24; failure keeps the original expression. wholeValueConcat is the narrower special case where consecutive slices tile a whole value exactly.

foldShiftIdiom (src/reconstruction/source-shifts.ts) handles the shift/rotate shapes produced by bitfield-move lowering. A constant rotation masked to exactly its non-wrapped bits is the plain shift (ror(x,k) & (ones>>k) = x>>k, and symmetrically for rol); a logical shift OR-ed with the sign bit replicated into exactly the vacated top bits is the arithmetic shift; a field entirely inside the non-wrapped or wrapped part of a rotation is the same field of the rotated operand. A true rotate keeps its rotate. The rule requires 0 < k < w and exact masks, and its scope string says so in the validation record.

constantRotationOperands complements this for printing: a rotation by a constant is printed as two shifts that each read the operand, so the operand must be a printed variable and is excluded from inlining.

Floating point

FP presentation is split in two. projectSourceFloating (src/reconstruction/source-fp.ts, src/reconstruction/source-signature.ts) decides which values may be spelled float/double from typed IEEE evidence: a closed component of whole-bit transports, typed literals, typed arguments, and ordinary 32/64-bit memory accesses whose consumers are IEEE reinterpretations or transports. It refuses when a declaration or conflict exists, and it never retypes an integer consumer silently. sourceFpPresentation handles guards and literals: literals become round-tripping decimals, and an exact lifter environment guard may be omitted on its supported edge when the FPCR/MXCSR state is an unchanged entry value or a call clobber, no explicit environment writer exists, and the unsupported arm is exclusively owned. The guard is then rewritten to a jump on its supported edge and the failure block becomes empty; both stay in the checked view and in requirement metadata.

Ranges and constant data

normalizeSourceRanges is described in the pipeline section. Two other helpers keep values exact without changing effects: sourceDataValues maps an address value to its SourceAddress fact (exact-address lookup only; a nearby literal is never used as a base for another object), and projectSourceConstants (src/reconstruction/source-data.ts) replaces an exact-width, aligned, non-volatile load from immutable file-backed bytes with a constant, provided no store can overlap the bytes and no relocation slot is involved. The load statement is hidden; the checked view keeps it.

Requirements and validation

Reconstruction publishes two different kinds of uncertainty. Requirements are statements about the machine environment or the ABI that a presentation relies on. Validation records are the local proofs (or failures) behind individual rewrites. Both are data; neither changes the emitted text except through explicit rendering rules.

Requirement records

export interface RequirementSite {
  readonly id: string;
  readonly subject_ids: readonly string[];
  readonly evidence_ids: readonly string[];
  readonly instruction_ids: readonly string[];
  readonly state_epoch: string;
  readonly predicate_value_id?: string;
  readonly supported_predicate_value?: boolean;
}
export interface Requirement {
  readonly id: string;
  readonly kind: 'fp_environment' | 'abi_conformance' | 'unresolved';
  // InferenceStatus; this producer uses 'assumption' or 'unresolved'.
  readonly status: 'established' | 'inferred' | 'asserted' | 'hypothesis' | 'conflicting' | 'assumption' | 'unresolved';
  readonly explanation: string;
  readonly subject_ids: readonly string[];
  readonly evidence_ids: readonly string[];
  readonly instruction_ids: readonly string[];
  readonly ranges: readonly AddressRange[];
  readonly sites: readonly RequirementSite[];
  readonly output_spans: readonly { readonly start: number; readonly end: number }[];
}

Producer model in src/core/inference.ts (Requirement, RequirementSite), constructed by src/reconstruction/source-requirements.ts (planSourceRequirements, abiConformanceRequirements).

There are three kinds:

fp_environment
One function-level assumption for all FP arithmetic, conversions and environment guards. A guard site's state_epoch is the value id of the FPCR/MXCSR state it assumes (entry state, a call clobber, or an unchanged transport of one); unguarded arithmetic uses an unmodeled: marker and a call site uses the call's effect input id. A computed or loaded control state does not qualify, so the guard stays explicit. Sites also carry predicate_value_id and supported_predicate_value for the recognized lifter guard.
abi_conformance
One record per presentation rule that assumed ABI behaviour — status assumption. Sites anchor at original statements/controls; state_epoch is the rule name. These are produced from LocalValidationSession.abiConformance by abiConformanceRequirements and do not print as ordinary comments.
unresolved
An indeterminate expression, unknown effect, incomplete call interface, incomplete return storage or unresolved control boundary. Status unresolved; these explain why the text still contains explicit unknowns.

Record ids are fingerprints. requirement_<hash> hashes the function, kind and the identifying site, rule/explanation or a fixed FP tag; site_<hash> hashes the function with the origin/state (FP) or the rule, explanation and anchors (ABI conformance). That makes them stable across runs of the same revision and prevents two different subjects or rules from sharing an id. Budgets are explicit: 1000 sites per record, 10 000 subject ids, 1000 evidence ids, 10 000 instruction ids. The FP site list and the reference sets throw resource_limit when exceeded; the ABI-conformance builder stops admitting further sites at its bound.

In text, the checked view prints one comment per fp_environment requirement, in the form /* Requirement requirement_<id> (assumption): … */, before the signature. For _main the real comment is: 

/* Requirement requirement_985231b20718e258c752fe590aa2ee7e6eaec534d6038514b9f4a8001411a67f (assumption): FP arithmetic requires nearest-even rounding, gradual underflow and disabled exception traps; … */

The source view replaces that block with a trailing signature comment, /* assumes nearest-even rounding and masked FP traps (requirement_<prefix>…) */, naming each requirement by an unambiguous id prefix. The renderer records that decision as the presentation rule requirement_note. Full explanations and sites stay in emission.requirements.

Local validation

LocalValidationSession (src/reconstruction/local-validation.ts) has a deliberately separate work allowance. ValidationAllowance is Math.min(8000, Math.floor((context.remainingWork?.() ?? 8000) / 64)), so local proofs cannot starve the outer operation and cannot claim more than 8000 units. charge() throws a private Unsupported error when exhausted; only that exception is caught by bounded() and converted to an unverified record. Cancellation, deadline and outer budget errors propagate.

The bitvector checker is an independent reduced ordered BDD implementation. Bits are ordered least-significant first and interleaved across symbolic leaves; leaves are capped at 64, operations at 12 000, expression expansion at depth 24, 128 memoized values and 1..64-bit integer fragments. It supports constants, bitcasts/truncate/zero-extend/sign- extend, extract/concat/insert, unary not/neg, and/or/xor, add/sub, constant shifts and multiplies, equality/inequality, and the zero flag of an add. Anything outside that fragment returns unverified, never a false proof.

The session also has global record bounds. At most 256 checking actions can store a record; when a further candidate arrives, one terminal summary record with subject * is written and later candidates are not attempted. Verified records with identical kind/rule/scope/reason are grouped, with subject ids chunked in groups of 64. ABI conformance sites are grouped the same way. These are metadata bounds only: they never change the text except through the presentation gate below. 

presentation(rule, subject, scope, subjectIds?, reason?): boolean {
  if (this.recordVerified({ kind: 'presentation', rule, subject, scope,
                            status: 'verified', ...(reason ? { reason } : {}) }, subjectIds))
    return true;
  this.check('presentation', subject, scope, () => ({
    kind: 'presentation', rule, subject, scope,
    status: 'unverified', reason: 'local validation record bound exceeded',
  }));
  return false;
}

That boolean is the admission control for source-view rewrites. A rule whose record cannot stored returns false, and the caller must keep the checked form. Pure semantic folds do not call it: foldExpressions keeps no record, and the base path of normalizeSourceExpressions uses only its bitvector check. requireAbi(rule, anchors, explanation) is separate: it records the assumption attached to an applied rewrite and never refuses it.

What is checked, and what happens on failure

Check Question Failure behaviour
validateBitvectorCandidate does the candidate expression equal the original for all inputs in the modeled integer fragment? rejected → keep original, record a counterexample; unverified → record reason and continue (the rule has its own side conditions)
validateStackPromotion does a byte-addressed trace agree for small acyclic paths; is every read definitely initialized? rejected → slot stays explicit; unverified → the caller still applies the source presentation gate and keeps the record
foldSourceCondition does the decomposition reproduce every feasible flag row? no decomposition → explicit flag form stays
presentation(rule, …) can the verified, rule-specific proof be stored under the metadata bound? false → caller keeps checked form
validateReconstruction coverage ownership, live definitions, edge-copy destinations, return widths, stack base, initialized promoted locals, inlining cycles throws unavailable_semantics with the origin's address and evidence ids
validateRenderedTransfers / validateEmittedControl does each rendered goto/break/continue/edge mean the executable edge it claims? record rejected; the renderer then calls rejectTranslation (unavailable_semantics)
validateEmittedUses is every used value emitted at a dominated site, including shared locals and coalesced copies? unavailable_semantics via the same publication path

Publication checks live in src/reconstruction/validate.ts (validateReconstruction, validateRenderedTransfers), src/reconstruction/validate-uses.ts (validateEmittedUses) and src/reconstruction/local-control-validation.ts (validateEmittedControl).

There is no “fall back to unchecked text” path. A refused presentation keeps the more explicit form; a failed publication invariant aborts the emission. That asymmetry is intentional: a missing prettiness is acceptable, a wrong program is not. Validation records are published as emission.local_validation and feed the inference records the coordinator resolves, so every applied rewrite remains auditable.

Invariant

A rewrite's validation subject is the published value, not merely the input SSA. The header of validateReconstruction: “Check the published projection, not merely the verified input SSA. Unknown values are legitimate expressions; missing definitions and result bits are not.”

Limitations & extension points

The design intentionally prefers an explicit physical form to a guess. The consequences are visible in real output and are tracked in TODO.md’s readability roadmap; the labels below are roadmap items, not current capabilities.

  • Frame-wide promotion gate (roadmap R1). One escaped frame address sets saveEscaped and skips every private slot in the function. The roadmap proposes per-slot escape analysis so escaped slots stay explicit while the rest are promoted. Until then, a function that hands out one interior pointer may print the whole frame as entry_sp ± N.
  • Expression rules are a hand-picked set (roadmap R3). normalizeSourceExpressions has a bounded worklist and a fixed collection of named rewrites (condition flags, slice reconnection, shift idioms, strength reduction, identity, extension). There is no general rule pool applied to a fixpoint with cost-based selection. Adding a rule means adding a proof, not just a pattern.
  • Proof allowance is finite. The local BDD allowance is shared across one function and is capped at 8000 units (and 12 000 operations per BDD). When it is exhausted, later bitvector candidates are recorded as unverified and skipped (skipExhaustedBitvector), and the more explicit form remains. Verified records are grouped, and at most 256 checking actions can store a record.
  • Pointer and type recovery is per function (roadmap R4). projectSourceSignature requires positive local evidence for a pointer formal and drops a type on any conflict. It does not run image-wide propagation, so integer-typed locals that are clearly dereferenced may still print as integers with casts. type_N names survive when no stronger evidence exists.
  • Open arities remain open (roadmap R5). Only proven interfaces close an argument list. Library contracts, complete callee reads and Objective-C selectors may set argument_list_complete; everything else keeps the remainder marker. The roadmap's opt-in inference: "likely" mode does not exist in this stage.
  • Rewrites only see one function. Requirements, caller demands and callee closures come from available native units; absence of a caller is never treated as proof that a result is unused. The comments on function_return_demands say this explicitly.
  • Source view is a presentation, not a proof of source equivalence. Frame-save elision, exit-scratch hiding and void-like interfaces all rest on abi_conformance assumptions. The checked view exists precisely so a reviewer can inspect the machine-level form without those assumptions.

Adding a new reconstruction rule safely

  1. Decide which layer owns it. If it is an exact semantic identity, put it in foldExpressions or the base path of normalizeSourceExpressions so both views share it. If it is a presentation change, gate it on sourceCells/view === 'source' and give it a rule name.
  2. State the proof in the scope string. The scope argument of check/presentation is the human-readable contract used by the validator table and the docs. Write the side conditions there, as the existing rules do (“0 < k < w and every mask must equal …”).
  3. Use the narrowest proof. Prefer a structural bit-for-bit argument (wholeValueConcat, recombineBitSlices) or an exhaustive outcome table (foldSourceCondition) over the shared BDD. Use validateBitvectorCandidate only for the modeled integer fragment, and handle unverified honestly: either keep the explicit form or document why the rule's own side conditions are sufficient.
  4. Admit presentation through presentation(), then record ABI assumptions with requireAbi(). Do not apply a source rewrite when presentation() returns false; do not silently assume an ABI fact.
  5. Keep the checked view unchanged. Add a test that asserts the rule is present in local_validation for source and absent for checked, as the existing tests in test/reconstruction/ do. Bump the component version when the output identity changes (the roadmap and docs/CORE.md require it).
  6. Measure on the dev loop, not on one fixture. The roadmap's rule is to fix the owning shared layer and tune on scripts/bench/quality-dev-loop.py; a prettier wrong program is a regression.

The extension points are deliberately few: a new ABI profile enters through source.abi.classifyCall; a new address fact enters through SourceAddress and sourceDataValues; a new stack pattern enters through the address fixed point and classifyStackRegion; a new expression idiom belongs in normalizeSourceExpressions with its own proof. None of them requires changing the renderer or the IR.
