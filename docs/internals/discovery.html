Stage 03 · Discovery

Function discovery & CFG

Discovery turns an immutable loaded image into a set of grounded function roots, decodes only code reachable from those roots, resolves a narrow class of indirect transfers, and emits per-function basic-block graphs, control-flow references, boundary claims, overlaps and coverage verdicts.

Where this sits in the pipeline

The loader has already produced a LoadedImage: mappings and an AddressMap, native symbols, exports, imports, relocations, section metadata, entry points and LoaderHint records. Discovery does not parse bytes into sections or guess addresses from file offsets; it consumes that image together with an architecture-matching Decoder and a nonnegative revision. Its outputs are FunctionGraph values (function record, instructions, blocks, gaps, diagnostics, coverage, optional resolved jump tables), a ReferenceRecord list, Evidence, lineage records, jump-table candidates, overlaps, boundary claims and an overall coverage verdict — the DiscoveryResult interface in src/analysis/discovery/index.ts.

There are two service entry points. During project open/import, prepareQueryImport in src/service/queries/prepare.ts decorates names, constructs the architecture decoder, calls discoverFunctions, then builds the string index and the reference index and classifies import stubs. The published function index state is complete only when discovery's own coverage is complete. For navigation and decompilation of an already published function, reconstructFunctionGraph in src/service/queries/graphs.ts reuses a cached DiscoveryIndex and calls discoverFunctions with selected_entry, which decodes only that root and treats every other known root as a boundary. That selected-local graph is cached per project, revision, slice and function, keyed additionally by instruction/block budgets and presentation mode.

The read side avoids decoding during identity lookup: loadFunctionScope in src/service/queries/scope.ts resolves the stored function ID, loadFunctionGraph materializes native name/function arrays once per live LoadedImage and revision in a WeakMap, and loadFunctionIndex reuses those arrays for presentation and xref queries.

Invariant

Discovery never scans for prologues and never sweeps an enclosing address range. It starts from evidence-bearing roots and follows decoded control flow. A side effect is that dead bytes between functions stay undecoded by design; the comments above discoverFunctions state this explicitly, and the discovery tests assert that unseeded prologue bytes produce no function.

Seeds, trust and indexed evidence

prepareDiscoveryIndex collapses everything the loader knows into an IndexedSeed per virtual entry address. A seed carries a set of evidence IDs, optional native names, any boundary claims, and one boolean, established. Multiple loader facts for the same address are merged: the ELF fixture carries two function-symbol evidence records for each function, so 36 such records collapse to 18 seeds. On macho-arm64-symbols, 18 seeds carry 17 function-symbol, 17 export-candidate, 17 loader-function-start, 8 unwind, one entry and one import-callable proof records. Evidence is additive; an established fact can never be downgraded by a candidate fact. 

interface IndexedSeed {
  readonly entry: Address;
  readonly evidence: ReadonlySet<string>;
  readonly names: ReadonlySet<string>;
  readonly claims: readonly AddressRange[];
  readonly established: boolean;
}

Two loader constructs are deliberately not seeds. A data hint becomes a DataRegion in the index; if its encoding is jump_table it also becomes a JumpTableCandidate with a concrete range. An object symbol with a size becomes a data region and its address is added to objectAddresses. The seed gate then refuses to turn an export or an unknown-kind symbol into a function when its address lies in such a region. The test suite calls this out directly: constants in an executable Mach-O __const section are not functions, and a zero-sized object symbol defeats an export-only code guess.

prepareDiscoveryIndex also builds two interval indexes over the immutable image. executableEnd(value) merges mappings that carry the execute permission and a nonzero file size, and returns the end of the containing range or the input value when unmapped. dataAfter(value) binary searches a prefix-maximum array of data-region ends; the prefix maxima are what make a long outer data claim visible even when a nested claim starts later. Both lookups charge the current operation, never the preparation operation, so a reused index cannot hide work from the caller's budget.

Assertions are claims, not facts

An assertion must carry evidence whose origin.kind is assertion; otherwise preparation throws invalid_input. Retracted assertions do not seed. A live assertion seeds with established = false, and its ranges become boundary claims. Its extents do not grant permission to decode unreachable bytes; they only constrain what may be claimed around reachable code.

The traversal workspace

Discovery is a single worklist traversal followed by one graph-extraction pass per seed. The workspace is small and explicit:

seeds
Mutable copies of the indexed seeds for this call, including roots discovered from direct calls.
queue / queued
An array and a membership set; initial entries are sorted by virtual address, later successors append in flow order.
decoded / gaps
One decoded instruction per address, or one DecodeGap with reason data, unmapped, budget or truncated.
incoming
Decoded control predecessors by target address, including proven jump-table edges; this is the input to single-entry proof validation.
tables
Provisional JumpTableProof records keyed by branch address; each graph revalidates them on its final members.
owners
After reconciliation, instruction ID → owning function IDs. More than one owner means shared code.

Evidence is content-addressed rather than minted as a counter. evidenceDeriver fingerprints the selected slice, the literal discovery/1 version, a rule string, the address value and the sorted parent evidence IDs. The same proof reached by the same path therefore produces the same ID across runs, and rule strings are the vocabulary you see in diagnostics: direct call target, loader function start, decoded control flow, indirect branch targets from immutable table entries under a dominating unsigned index bound, and so on.

Revision and slice ownership

The decoder architecture must equal image.target.architecture, the revision must be a nonnegative safe integer, every previous graph must belong to the selected slice, and a supplied DiscoveryIndex must carry the same image ID, slice ID and revision. Any mismatch is an OperationError with unsupported_target or invalid_input; there is no best-effort mode that silently mixes revisions.

The discovery algorithm

The outer loop is a cursor over an append-only queue, not recursion. That matters for ordering and for termination: successors are appended in the order the decoded flow produces them, while the initial roots are sorted by address so the starting order is deterministic. The queue can contain an address at most once because enqueue also consults queued. The loop never revisits a decoded address or a gap.

  1. Validate and prepare. Check decoder architecture, revision, previous graphs and index identity. If no index was supplied, call prepareDiscoveryIndex. In selected_entry mode, require that the entry is a virtual address with an indexed seed, start with only that seed on the queue, and do not copy the other seeds into the mutable seed map.
  2. Sort the initial roots. Queue entries are sorted by address; discovered successors keep structured flow order. Display names never influence scheduling.
  3. Skip completed work. If the address is already decoded or already has a gap, continue. If the next data region contains the address, record a data gap with a conflicting_evidence warning and stop at that address.
  4. Check backing and instruction budget. No executable file backing produces an unmapped gap and an unmapped warning. If the number of decoded instructions has reached context.budget.instructions, record a budget gap, set exhausted = true, and continue draining. This path returns partial graphs rather than throwing.
  5. Decode one bounded window. The window is at most 4 bytes on ARM64 and 15 bytes on x86-64, clipped by executable backing, by the next known data region and by the 64-bit address limit. The decoder gets a derived context whose instruction budget is one, so a single decode cannot consume the caller's whole budget; work, deadline and cancellation still charge the original cumulative operation.
  6. Record failure as a gap. If the decoder returns no instruction starting at the address, use its own gap if present, otherwise a truncated gap with the decoder diagnostics. A decoded instruction is stored immediately; a non-valid instruction is stored too, but no successors are followed.
  7. Seed direct calls. A valid direct call with a target calls seed(target, 'direct call target', [flowEvidence], true), which adds evidence and marks the target established even if it was not a loader root. In normal mode it is also enqueued; in selected mode it is not decoded, because every known root is a boundary.
  8. Follow intraprocedural successors. instructionSuccessors contributes the fallthrough of a call, both edges of a conditional branch, the target of an unconditional branch, the fallthrough of an indirect branch or trap, and nothing for returns. Every successor gets an entry in incoming and is enqueued; in selected mode, a successor that is another indexed root is refused by enqueue and remains a boundary.
  9. Attempt indirect-table proof. A non-conditional indirect branch is offered to proveJumpTable. On success, the proof's targets are enqueued and recorded as incoming edges from the branch, and the proof is stored provisionally in tables. Separately, architecture-shaped heuristics append JumpTableCandidate records (x86 indexed indirect operand with scale at least 4; ARM64 indexed load immediately before a register branch); candidates never create edges. 
queue.sort((a, b) => (a.value < b.value ? -1 : a.value > b.value ? 1 : 0));
for (let cursor = 0; cursor < queue.length; cursor++) {
  const address = queue[cursor]!;
  if (decoded.has(address.value) || gaps.has(address.value)) continue;
  // … data, executable-backing and instruction-budget gaps …
  const result = decoder.decode({ image, regions: [{ start: address, size: length }],
    mode: image.target.architecture === 'arm64' ? 'a64' : 'long64',
    features: image.target.features }, decodeContext);
  const instruction = result.instructions.find((item) => item.address.value === address.value);
  if (!instruction) { /* record a gap and continue */ }
  decoded.set(address.value, instruction);
  const flowEvidence = derive('decoded control flow', address, instruction.evidence_ids);
  if (instruction.validity !== 'valid') continue;
  if (instruction.flow.kind === 'call' && instruction.flow.target) {
    seed(instruction.flow.target, 'direct call target', [flowEvidence], true);
    if (!selected) enqueue(instruction.flow.target);
  }
  for (const successor of instructionSuccessors(instruction, input.noreturn_calls)) {
    addIncoming(successor.value, instruction);
    enqueue(successor);
  }
  // … proveJumpTable / append indirect-transfer candidates …
}

Successors, calls and tail calls

Successor policy lives in instructionSuccessors in src/analysis/cfg/index.ts. It is shared by the discovery worklist and by buildCFG, so the reachable instruction set and the block edges cannot drift apart. Calls intentionally contribute only their continuation: a call is an interprocedural reference, not an intraprocedural edge. The kinds themselves come from instructionFlow in src/decoders/arm64/flow.ts and flow in src/decoders/x86_64/metadata.ts, both returning the DecodedFlow union declared in src/core/decoder.ts.

DecodedFlow.kind Discovery successors CFG edge(s)
fallthrough next fallthrough
call fallthrough, unless a direct target is in noreturn_calls fallthrough, or trap when noreturn
branch target, plus fallthrough when conditional branch (conditional flag from the decoder), plus fallthrough when conditional
indirect_branch fallthrough if present; proven table targets replace this unknown or one branch per proven target, plus fallthrough
trap fallthrough if conditional trap, plus fallthrough if conditional
unknown the next byte/instruction address only when may_fallthrough unknown plus a conditional fallthrough for each successor
return none return

A direct call to a root that is already known merges evidence rather than creating a second root. A direct call to an address that is not known becomes a new established seed; this is how local helper functions appear in stripped and symbol-bearing images. In selected mode the call target is still seeded as evidence, but it is not enqueued, so the selected graph stops at the call continuation and leaves the callee to its own graph.

An unconditional branch whose target is another function entry is a tail call. It appears as a ReferenceRecord of kind tail_call and as a CFG tail_call edge whose to block is null. It is never pushed into the current function's pending set. A conditional branch into another entry, or a call continuation that equals another entry, is treated as a boundary conflict instead: that is evidence that the two claimed extents disagree. A real case is fixture_entry in fixtures/bin/elf-x86_64-symbols: its branch at 0x401e89 targets fixture_native_call at 0x401e70, and the reference index records it as tail_call.

Noreturn calls

noreturn_calls is a map from direct call-target virtual address to the evidence IDs that justify the claim. The production caller obtains it from libraryNoreturnCalls in src/metadata/library-contracts/index.ts: only non-weak imports with an exact library declaration, a callable entry and matching library identity qualify. The map affects two places. instructionSuccessors returns no continuation for such a call, so traversal does not absorb the next bytes. In buildCFG, the same call becomes a trap edge with the noreturn proof added to its evidence. This is what keeps a final bl ___stack_chk_fail from making the following function's entry look like intraprocedural flow. The discovery test for this case runs the same bytes with and without the declaration: without it the caller becomes conflicting with a fallthrough edge; with it the edge is trap and the caller stays established.

Only direct, contract-backed calls

Indirect calls are never noreturn, and an unknown or conflicted library contract is not a noreturn fact. The evidence stays conditional on the named library implementation, and discovery records it as derived analysis evidence rather than a binary fact.

Budgets and partial results

Default budgets come from DEFAULT_BUDGET in src/core/primitives.ts: instructions: 10_000, blocks: 10_000, ir_nodes: 100_000, work: 10_000_000, deadline_ms: 30_000, output_bytes: 1_048_576. Discovery treats them differently. Exceeding the instruction budget produces a gap, sets exhausted, adds the reason instruction budget to the overall coverage, and returns partial graphs. Exceeding budget.blocks while accumulating blocks throws resource_limit, with details.resource = 'blocks'. Work, deadline and cancellation are enforced by context.checkpoint and also throw, so no result is published. An instruction cap reports how much code was observed; a work or deadline cap means the operation did not finish.

Boundaries, conflicts, gaps and overlaps

The traversal produces a global set of reachable instructions, but each function graph is extracted independently with its own pending stack, visited set, gaps and diagnostics. For each seed, the extractor walks successors from the entry and stops at another function entry. It then builds the graph's local predecessor relation, revalidates any provisional jump-table proof against exactly those members, and only after rejection converges does it sort members and derive observed ranges.

Claim checking has two directions. If a seed carries claims, every decoded member must lie entirely inside at least one claim. If it does not, the graph is conflicting. Independently, each claim is checked against the next seed entry: a claim that contains another seed's entry is a conflict, because two roots claim the same bytes. In selected mode, the check is widened to every seed in the index, because even roots that are not decoded in this call remain real boundaries.

Two reachability rules set the conflict flag. A reachable instruction landing in a known data region is a data gap and a conflict. A successor that reaches another function entry is a conflict unless the edge came from a proven jump table or is an unconditional branch (a tail call). The diagnostics preserve both sides' evidence IDs, so a consumer can inspect the disputed proof rather than trusting a boolean.

The enums are independent. boundary is one of the real schema values candidate, established and conflicting from functionSchema in src/core/model.ts. analysis is one of not_analyzed, partial, complete and unsupported; discovery writes partial or complete. The graph coverage uses the same complete/partial split and carries human-readable reasons.

Observed function.ranges are merged from reachable instructions, not from a claimed envelope. Adjacent or overlapping instruction ranges collapse; a function with no members still gets a zero-sized range at its entry. Claimed extents remain separately in DiscoveryResult.boundary_claims, including the seed, range and evidence IDs. This separation lets a caller distinguish "what discovery actually observed" from "what the loader or a user asserts the function owns".

Gaps are collected per graph. Besides traversal failures, the extractor materializes data gaps for every data region intersecting the union of the seed's claims and the observed envelope (first reachable instruction start to last reachable instruction end). Those extras represent embedded literal pools or data inside a claimed extent; they are not decoded instructions and do not create blocks.

After all graphs are reconciled, discovery scans decoded instructions by address for overlaps. An instruction owned by more than one graph produces a shared_tail overlap. Two instructions whose byte ranges intersect produce an overlapping_instructions overlap; the functions listed in that overlap are downgraded to boundary: conflicting, analysis: partial, and get a conflicting_evidence diagnostic. Shared tails are reported but do not by themselves make either function conflicting — a real shared epilogue is legal.

Jump-table recovery

There are three different objects in this area, and only one of them contributes control flow. A JumpTableCandidate is an inventory item with status: 'candidate': a loader hint with encoding jump_table, or an architecture-shaped heuristic. A ResolvedJumpTable is a proof: one indirect branch with an exact target set, guard and byte layout. proveJumpTable in src/analysis/discovery/jump-tables.ts produces the proof; only proofs create edges, while candidates stay inventory. 

export interface ResolvedJumpTable {
  readonly branch: string;
  readonly selector: { readonly instruction: string; readonly register: RegisterDescriptor };
  readonly table: AddressRange;
  readonly entry: { bytes: 1 | 2 | 4 | 8; signed: boolean; stride: number };
  readonly targets: readonly Address[];
  readonly guard: string;
  readonly otherwise: Address;
  readonly guard_exact: boolean;
  readonly chain: readonly string[];
  readonly evidence_ids: readonly string[];
}

The single-entry chain

Proof starts from the branch and walks backwards. The chain stops at a function entry, at a branch with zero or more than one decoded predecessor, at an invalid instruction, or at a predecessor that is not fallthrough or branch. It also stops if the predecessor is already in the chain. The maximum is MAX_CHAIN = 64; fewer than three instructions is an immediate rejection. Each instruction is replayed forward through a symbolic interpreter over 64-bit values. Registers begin as opaque symbols; constants, zero-extension, sign-extension, addition and shifting are hash-consed so equal expressions compare by key. A conditional branch on the chain can establish a fact about the compared left-hand side; the fact records the maximum and the guard instruction that produces the out-of-range edge.

What is modelled in each architecture

Ingredient ARM64 recognition x86-64 recognition

Address arithmetic ADD/SUB immediate, shifted register and extended register; LDR/STR with index and shift lea, mov, add, sub; memory operands with base, index and scale
Guard flag-setting ADDS/SUBS, then a conditional B.cond while those flags survive; unsigned conditions map to >=, <, >, <= cmp/sub/add, then an unsigned ja/jae/jb/jbe form while the comparison flags survive

Both interpreters forward stack and register slots keyed by an affine base, offset and size; a store to an overlapping key kills the forwarded value. On x86-64 the segment base must not be fs or gs and the memory operand's address size must be 64-bit; otherwise the address is opaque. Those restrictions prevent the proof from treating a thread-local or window-relative address as a table base.

Deriving base, bound, entry width and targets

A load is recognized as a table entry only when its effective address is affine with exactly one non-constant term, that term is the same symbolic node as the index register, and the shift matches, and the index node already has a guard fact. The affine constant is the table base. The entry width is the access width in bytes; the stride is 2^shift on ARM64 and the memory operand's scale on x86-64; signedness comes from the signed-load form. The bound is the maximum established by the guard. The count is max + 1, and the proof rejects if that maximum is at least max_entries; discovery passes MAX_JUMP_TABLE_ENTRIES = 256. guard_exact records whether the bound is the fact attached directly to the index node itself, as opposed to a structural bound inherited from a wider expression. 

if (chain.length < 3) return undefined;
const limit = bound(entry.index);
if (!limit.guard || limit.max >= BigInt(input.max_entries)) return undefined;
const count = Number(limit.max) + 1;
const length = (count - 1) * entry.stride + entry.bytes;
const table: Address = { image_id: image.id, space: 'va', value: entry.table };
const bytes = recoverDataBytes(image, table, length, context);
if (!bytes) return undefined;

Table bytes are read little-endian from recoverDataBytes in src/analysis/strings/source-data.ts. That function is intentionally strict: the table range must lie in exactly one containing section, the section must be readable and not writable, the range must fit both the virtual and file extent, no overlapping mapping may be writable or unreadable, no relocation may intersect the range, and the address must map to exactly one file-backed span of exactly the requested length. Zero-fill and synthetic bytes are never accepted.

Rejections and graph revalidation

Rejection Why
Chain shorter than 3, loops, multiple predecessors, invalid instruction The straight-line single-entry premise does not hold.

Revalidation is the key soundness step. The worklist proves a table against decoded predecessors, but a later-discovered edge can add a second predecessor into the chain. The extractor therefore re-runs the proof's shape check on the final graph: every chain member after the first must have exactly one predecessor, that predecessor must be the previous chain member, the selector read and branch must share a block, and every target plus the guard's otherwise edge must be inside the graph. Failed proofs are added to a rejected set and edges are removed; the extraction loop repeats until no proof is rejected.

What counts as a candidate

Discovery appends a candidate for an x86-64 indirect branch whose operand has an index and scale at least 4, and for an ARM64 BR immediately preceded by an indexed load into the same register. These candidates have range: null and never become edges. Target recovery can enumerate only candidates that came from a loader data hint with a concrete range and a multiple-of-eight size; even then its entries are candidate references, not established edges.

Building the CFG

buildCFG receives the reachable instruction list for exactly one function, the set of function entries, the evidence map, the proven table targets by branch address and the noreturn-call map. It sorts the instructions by address and derives leaders with three rules: the function entry is a leader; every successor of a non-fallthrough instruction is a leader; and every address with an incoming count other than exactly one is a leader. The second rule is why a conditional branch's fallthrough terminates a block even though it has only one predecessor, while a plain fallthrough does not. 

const leaders = new Set<bigint>([input.entry.value]);
for (const instruction of sorted) {
  for (const successor of tableTargets(instruction) ??
    instructionSuccessors(instruction, input.noreturn_calls)) {
    incoming.set(successor.value, (incoming.get(successor.value) ?? 0) + 1);
    if (instruction.flow.kind !== 'fallthrough') leaders.add(successor.value);
  }
}
for (const [address, count] of incoming) if (count !== 1) leaders.add(address);

Trimmed from src/analysis/cfg/index.ts (buildCFG).

A single sorted pass then groups instructions. A new group starts at a leader, after an invalid instruction, after a non-fallthrough instruction, or when the previous fallthrough's next is not the current address. Blocks are maximal only with respect to that linear order; the CFG is not reordered to look nice. Block IDs are entityIdentity(slice, 'block', { function, entry }), and a block's range spans from its first instruction to the end of its last.

Edges are emitted from the last instruction of each block, and the target block lookup is local to the function. A target absent from this graph keeps its address with to: null; tail calls and returns also have to: null. A call contributes only a fallthrough edge, or a trap edge when the call is direct and in noreturn_calls (the trap edge carries the call proof's evidence as well as the instruction's). A proven jump table contributes one branch edge per distinct target, all marked conditional, replacing the unknown edge. An unresolved indirect branch gets an unknown edge, with a conditional fallthrough only if the decoder reports one.

The worked example end to end

_fixture_loop enters at 0x100000594. The loader supplied a function symbol, an export and a function-start hint at that address. Discovery decodes cbz w1, 0x1000005b8; its two successors are the target and the fallthrough, so both are enqueued. The fallthrough decodes three moves and falls into the loop body. The body's b.ne 0x1000005a4 targets an address already decoded, so the worklist does not decode it again; the graph extractor's own traversal also stops because the address is visited. The two returns terminate their paths. The resulting observed range is 44 bytes, and the graph coverage is complete because there is no gap, no invalid instruction and no unresolved indirect flow. The two branch references are branch/established to 0x1000005b8 and 0x1000005a4; neither target is a function entry, so neither is a tail call.

Xrefs and indirect target recovery

Discovery itself emits control-flow references while it walks the reconciled graphs. For each instruction it classifies calls, branches, tail calls and unknown transfers, and for a resolved table it emits one branch reference per distinct target with the table proof's evidence. Direct calls carry target_role: 'code' and resolve to the callee function ID when that function is in the discovery result; a call to an import callable entry resolves later to the import record with target_role: 'callable_stub'. These references are intentionally conservative: unresolved indirect transfers are retained as status: 'unresolved', to: null.

recoverTargets in src/analysis/targets/index.ts adds non-control and indirect-target references with a deliberately scoped analysis. It walks each discovery block independently, keeps a value per 64-bit register root, and never lets a value cross a block boundary, a call, an unknown instruction or a store. Values have status candidate or established, origins that name the derivation, optional storage address, optional table base and an optional entity (an import). Memory reads are resolved from relocations or file-backed pointer bytes; those reads are candidate values even when the bytes are known, because the slot may be writable at run time.

The x86-64 path handles RIP-relative and absolute operands, LEA address formation, MOV immediate/register/pointer, ADD/SUB immediate, indirect register calls and IAT calls/jumps. The ARM64 path handles ADR/ADRP, ADD base plus immediate, ordinary 64-bit LDR pointer and stub sequences, BR/BLR and indexed absolute-u64 tables. The table path is narrower than proveJumpTable: it accepts only a discovery candidate with a concrete range, requires that range's size to be a multiple of eight and at most 256 entries, and emits candidate branch references for executable entries. It never asserts index feasibility; that is the table proof's job.

buildReferenceIndex in src/analysis/references/index.ts merges discovery references, target-recovery references and explicit loader relocation relationships. Relocation references are data xrefs with from_function: null, from_instruction: null and kind address. The merge deduplicates by function, instruction, source address, kind, target, target entity, status and target role. An unresolved discovery edge is dropped only when another reference for the same instruction and owner has an established control target; a candidate cannot discharge an unresolved edge. The record cap defaults to 100_000 and adds resource_limit when hit.

Persistence uses the generic records table keyed by kind, ID and revision, plus an indexes table holding one state per image, kind and revision. The record kinds are declared by StoredRecordKinds in src/core/contracts.ts: function, string, reference, symbol, import and export. Queries do not search the analyzer's arrays directly. xrefs_get in src/service/queries/handler.ts loads the persisted reference records, filters by incoming/outgoing direction, target address or entity, kind and include_unresolved (default true), then pages the result. strings_find reads persisted string records and filters by text, encoding, status and address range.

The in-memory searchReferences and searchStrings helpers apply the same shape of query to an index returned by the analyzers. Their shared searchIndex caps the page at 100 by default, examines at most 100_000 records, and binds cursors to the revision, index identity and query fingerprint. A cursor from another revision raises stale_cursor; a malformed or mismatched cursor raises invalid_cursor.

On the Mach-O fixture, discovery produced 144 references from 18 graphs. The reference index state was partial, with diagnostics including “Unresolved indirect targets” and “Discovery coverage is incomplete”. A concrete resolved call is _main at 0x100000aa8, whose reference kind is call, status established, target 0x100000abc, target entity the _puts import, target role callable_stub. A concrete data reference is _fixture_string at 0x10000070c, kind address, status established, target 0x100000ad0, which resolves to the fixture's one string record.

String discovery

buildStringIndex in src/analysis/strings/index.ts is independent of discovery and runs after it in prepareQueryImport. It scans only sections that are ordinary sections with file backing and that are not executable: Mach-O excludes sections whose flags contain 0x80000400 (pure/some instructions), while PE and ELF require a non-executable permission set. Each virtual range is translated to file spans; zero-fill and unmapped spans are skipped rather than synthesized.

The scanner is conservative about encodings. It starts at a non-NUL byte, looks for a NUL-delimited record, and requires at least four characters by default. At an even address, UTF-16LE is recognized only when the section name matches /ustring|utf16/i, a BOM is present, or two consecutive printable-ASCII/zero pairs occur outside a Mach-O C-string section (a C-string section never combines adjacent one-character records into UTF-16). Decoding is fatal: an invalid UTF-8 or UTF-16LE sequence rejects the entire record, not just an inconvenient suffix. The printable test also requires nonempty trimmed text.

Defaults are max_bytes: 32 * 1024 * 1024, max_strings: 50_000, max_string_bytes: 16 * 1024, and min_characters: 4. Hitting the byte or record budget stops the scan and adds a resource_limit diagnostic; overlapping section aliases and unavailable mappings do too. state is partial exactly when such a reason exists.

A record starts as status: 'candidate'. The reference index promotes it to status: 'referenced' only when an established read or address reference with a non-null instruction points inside the record's byte range. Promotion adds the reference's evidence to the string record and re-fingerprints the index identity. Each record's ID is entityIdentity(slice, 'string', [address, encoding]), so the ID follows the address and encoding rather than the text or its reference status.

What "complete" means here

A complete string index means all eligible sections within the documented byte and record budgets were scanned. It does not mean every byte sequence that a human would call a string was found: arbitrary encoded, compressed or encrypted text, strings in executable sections, and strings beyond the budgets are out of scope.

Import stubs

Import stub recognition is a post-pass in src/analysis/discovery/stubs.ts after discovery and reference construction. A stub must have one to four instructions, be sorted from its function entry, end in a forwarding branch, and contain only inert instructions before that branch. On ARM64 the forwarding branch is BR_64_branch_reg and inert means ADRP, ADR, NOP, a positive-offset 64-bit LDR or a 64-bit literal LDR. On x86-64 the branch is jmp and inert means endbr64 or nop. This covers Mach-O __stubs (adrp/ldr/br), ELF PLT entries and PE import thunks (jmp [IAT]).

Shape alone is not enough. The function must have exactly one branch reference, that reference must be established, have to: null and name an entity, and every other reference owned by the function must be a read of role import_slot to that same entity. The entity must resolve to an import with a slot, a name, no weak binding, and either no callable entry or exactly the stub's entry. Anything with other effects, references or a weak import remains an ordinary partial function.

Publication changes the record rather than the graph: the function becomes kind: 'import_stub', boundary established unless it was already conflicting, analysis complete, and if it had no native name it takes the import's name. The stub's evidence is unioned with the function's evidence. On the Mach-O fixture this is how _puts at 0x100000abc is published: before classification its three-instruction graph is partial because the br is unresolved; after classification the persisted record is [established, complete, import stub].

Split and merge lineage

Discovery can be called with the previous revision's graphs. reconcileGraphs in src/analysis/discovery/lineage.ts preserves identity where the ownership shape is unchanged and mints new IDs where it is genuinely split, merged or replaced. A function's shape is its entry plus the sorted list of member instruction IDs; names are not part of the shape, so a rename preserves the ID. An exact shape match reuses the old function ID. A block shape additionally includes the owning function ID, so identical shared tails in two functions remain distinct blocks.

For unmatched entities, the reconciler groups old and new shapes by shared member instructions. It builds a bipartite owner graph, then floods connected components. A one-to-one component whose entry is unchanged is treated as an extension in place and keeps the original ID. Otherwise the component's previous IDs and new shapes are hashed into fresh IDs for all participants, and a lineageSchema record is emitted with reason split (one old, several new), merge (several old, one new) or replacement (many-to-many). When a function ID changes, block IDs are rebased deterministically from the new function ID and the block entry, and every edge's from/to is rewritten to match.

Lineage is computed, not currently published by prepare

discoverFunctions returns the lineage records, and the project store has a lineage table plus putLineage/readLineage, but the service's initial import path calls discovery without previous and does not call putLineage. In the current code the lineage path is exercised by direct API/test calls that pass previous graphs; it is not part of persisted project import.

Limitations & extension points

The most important limitation is intentional: discovery is recursive traversal from evidence. Unseeded functions are invisible, even if they sit in executable sections and look like prologues. Dead bytes are not swept, and a function reachable only through an unresolved indirect edge stays undiscovered. An image with no grounded roots returns no graphs and coverage partial with reason no grounded function seeds. Conversely, unresolved indirect flow is never guessed away: any unknown flow, unresolved indirect branch or indirect call adds unresolved control flow to the function's coverage reasons and makes the overall result partial. The Mach-O fixture demonstrates both sides: 18 graphs are discovered, 16 are complete, and _fixture_indirect and the pre-stub _puts graph are partial because of their indirect control transfer.

Real images therefore stay partial. The project publishes indexes.function = 'partial' whenever discovery.coverage.state is not complete. That is why the CLI's functions command prints a warning such as functions: partial (incomplete_index) on the fixture, and why query envelopes can carry reason incomplete_index. The roadmap in CONTINUE.md names the remedy: “resumable per-root whole-image discovery as a background job so real images stop being permanently partial”. Discovery already supports per-root work through selected_entry and a reusable DiscoveryIndex; the missing piece is scheduling and persistence, not a different traversal rule.

Other concrete gaps visible in the code:

  • Instruction-budget exhaustion returns partial graphs, but work, deadline, block and cancellation limits throw OperationError and publish nothing. There is no resume cursor inside the worklist.
  • Jump tables must have a single-entry straight-line chain, an unsigned constant bound on the exact index value, at most 256 entries, and immutable relocation-free bytes. Signed guards, multi-entry chains, tables in writable sections and indirect dispatch without a table proof remain unresolved.
  • guard_exact is recorded, but the final graph revalidation checks the chain, selector block, targets and otherwise; it does not reject a proof merely because the guard fact is not the fact attached directly to the index node.
  • Discovery's architectural jump-table candidates have no range, so they are inventory only. Target recovery enumerates absolute-u64 tables only from loader data hints with a concrete, eight-byte-multiple range.
  • Shared tails are reported as shared_tail overlaps but are not deduplicated: each function keeps its own graph and blocks. Overlapping byte ranges (mostly possible on variable-length x86) mark the participants conflicting rather than choosing one decoding.
  • Import-stub classification relies on the reference index and on loader-provided import slots and callable entries. A stub-like body without an established import reference stays an ordinary partial function.
  • Selected-local rebuilding adds a synthetic selected-local graph reconstruction evidence record to every selected graph, and an unavailable_semantics diagnostic only when the observed graph differs from the published record. It does not mutate historical ranges.
Extension points

A new architecture starts with a decoder flow classifier that produces the DecodedFlow union and a payload whose operand kinds the symbolic interpreter understands. A new seed source belongs in prepareDiscoveryIndex, not in the traversal; it must state whether it is established and whether it carries claims. A new jump-table pattern belongs in the ARM64 or x86-64 replay functions plus the guard and entry-load recognizers; it must still end as one entry node with a guard fact and immutable bytes. A new xref source belongs in recoverTargets (block-local values) or in buildReferenceIndex (loader facts such as relocations), with a precise ReferenceRecord.kind, status and target role. A new stub shape belongs in inertInstruction/forwardingBranch. Finally, publishing lineage, or resuming discovery per root, requires wiring existing data structures through the service layer rather than changing the discovery result schema.
