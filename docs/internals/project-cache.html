Where this sits in the pipeline

Every other page in this set describes code that transforms a decoded image into pseudocode. This page describes the container around that work: where the immutable input lives, how derived state is made durable, what makes a stored result reusable, and which process executes it. The boundary is deliberate and enforced by process separation. Frontends (the CLI, the MCP server, the JS API) live in a host process that authorizes paths and schedules jobs. All native decoding, analysis, store access and artifact bytes live in a persistent child process, one per canonical project directory. The host never deserializes target bytes and the child never accepts SQL, module names or executable source over the transport.

What comes in: a binary path (or an already-imported project path), a requested revision, a tool request with a work/output budget, and — for mutations — an expected_revision. What goes out: a schema-validated ToolResult bound to a project and revision, optionally carrying a published artifact handle, plus a durable Job record that survives the transport connection. The CLI's openBinary and BinarySession compose this layer (src/api/index.ts); MCP registers the same tool names over the same QueryService (src/mcp/server.ts).

The ordering matters. A request is schema-validated in the host, authorized against configured roots, admitted as a durable job in the child, and only then executed. The child wraps CPU work in one OperationContext whose work counter, deadline and cancellation signal are never reset by an inner pass (src/core/operation.ts, createOperationContext). A published analysis artifact is a side effect of that same job, so a cache hit is still a job: it updates the job's terminal state and artifact list before returning.

Projects: identity, location, lifecycle

A project is a directory, not a database row. Its identity is derived from the input bytes and the selected slice, so two callers that hash the same file and request the same slice necessarily converge on the same directory. hashInput opens the file with O_NOFOLLOW, requires a regular file of at most 512 MiB, hashes in bounded chunks, and re-stats it afterwards; any size, mtime or ctime change is rejected as invalid_input. projectDirectoryName then returns `${sha256}.${sliceId ?? 'default'}` (src/service/queries/input-identity.ts).

The cache root defaults to the sidecar <binary>.open-decomp; the CLI --cache PATH overrides it. BinarySession.open creates it with mode 0o700, resolves symlinks with realpath, and rejects a non-directory or a symlink (src/api/index.ts). The project directory itself is created by SqliteProjectStore.open, which also creates images/ and artifacts/; a project database must be a regular non-symlink file. Everything the store writes is either an immutable content-addressed file (image bytes named by SHA-256, artifacts named by random artifact ID) or the SQLite database.

Import, step by step

project_open with source.kind: "import" is handled by the host facade, which opens a worker for the project path and submits a worker import request. In the child, runProjectWorker admits a durable job with input_revision equal to the current snapshot (0 for a new project), then:

  1. Read and hash. The source path is re-resolved after authorization so a path swap between host and child is rejected (permission_denied). The file is opened O_NOFOLLOW, checked as a regular file of at most 512 MiB, read in 1 MiB chunks with a checkpoint per chunk, and hashed.
  2. Load metadata. The loader is chosen by magic bytes (MZ → PE, \x7fELF → ELF, otherwise Mach-O). It decodes headers, slices, sections, mappings, symbols, imports, exports, relocations, hints, diagnostics and capabilities.
  3. Persist the immutable image. importImage re-hashes the bytes, writes images/<sha256> through a temporary file plus fsync and rename, inserts images and image_imports, and advances the revision by one. Progress image_snapshot is saved and sent.
  4. Prepare derived native facts. prepareQueryImport runs runtime metadata, name decoration, discoverFunctions, the string index, the reference index and import-stub classification — all outside SQLite so a failed preparation publishes nothing.
  5. Publish atomically. One store transaction writes the loaded image, every function/symbol/import/export/string/reference record, index states, evidence and the completed job, then advances the revision again.
  6. Describe. describeProject reports each image as loaded or snapshot_without_metadata; the host then issues a binary_info summary request and returns it with data.resumed.

The index states are not guesses about completeness. After publication, symbol and export are complete unless the native name tables (or derived name decoration) were partial; import follows metadata completeness; function follows discovery coverage; string and reference take the states reported by their builders. In the real macho-arm64-symbols run used on this page, the function and reference indexes are partial, while the other four are complete — and a function decompilation can still be complete, because those are independent facts.

Resume never replays an import

A plain resume of a project with no image, or with an image whose metadata was never loaded, returns partial / incomplete_index with data.image: null and a diagnostic; it does not retry. Repair is explicit: source.kind: "import" with mode: "resume" is accepted only for an empty project or one unfinished snapshot, and the bytes and selected slice must match the saved snapshot. The import-repair checks are in runProjectWorker and QueryService.execute.

The SQLite store

SqliteProjectStore owns exactly one exclusive connection (node:sqlite DatabaseSync) and exposes a domain interface: snapshots, images, records, indexes, evidence/types/signatures/lineage, annotations, jobs, artifacts, native summaries and transactions. It takes the lock with PRAGMA locking_mode=EXCLUSIVE and BEGIN EXCLUSIVE, enables foreign keys, then switches to WAL. The OS releases the lock if the worker crashes; the next resume reconciles jobs rather than leaving a half-owned database. Prepared statements are compiled per SQL text and cached up to 256 entries because statement compilation costs more than most indexed reads.

Schema version and migration chain

Persistence has its own version, independent of the wire schema. The code defines STORE_SCHEMA_VERSION = 6, while SCHEMA_VERSION for results and artifacts remains 1 (src/project/store/index.ts). A resume first probes PRAGMA user_version on a read-only connection and rejects anything below 1 or above 6 with unsupported_version. Under the exclusive lock it re-checks the version and applies every missing step inside one BEGIN IMMEDIATE; failure rolls the whole chain back.

Transactions and the revision guard

The store's general domain-mutation entry point is transaction(expectedRevision, mutate) (image import and artifact publication have their own guarded paths). It first compares the expected revision with the current one; a mismatch returns a typed conflict without opening a transaction. Otherwise it stamps revision = current + 1, exposes a StoreTransaction whose methods validate their domain object, runs the callback synchronously, updates metadata and commits. Asynchronous callbacks and escaped handles are rejected: the callback's promise check and the guard() after return make a partial commit impossible. 

export function nextRevision(current: number): number {
  revisionSchema.parse(current);
  return revisionSchema.parse(current + 1);
}

The store repeats that precondition atomically before opening its transaction:

const current = this.#current();
if (current !== expectedRevision)
  return { state: 'conflict', expected_revision: expectedRevision, current_revision: current };
if (this.#transaction) fail('invalid_input', 'Nested transactions are forbidden');

src/core/validation.ts (nextRevision, assertRevision) and src/project/store/index.ts (transaction).

Invariant

One successful domain mutation advances the global revision by exactly one. The response validator enforces it: a complete mutation result must report nextRevision(expected_revision) (src/core/validation.ts, validateToolResponse). A new-image import is the deliberate exception: it uses two transactions (image bytes, then metadata) and lands at current + 2.

A rejected mutation rolls back and returns state: "rejected" with the diagnostic; an annotation bridge turns that into a failed tool result rather than a throw. Artifact publication cannot nest in a transaction: it writes the payload file first, then inserts the artifact, its inverted-index rows, any reuse row, the completed job and queued native summaries in one BEGIN IMMEDIATE. If the transaction fails, the file is unlinked. Job invariants are checked in saveJob: a job cannot change its input revision or operation, a terminal job cannot restart, a running job cannot return to queued, and every artifact handle must already be published at the job's input revision.

Record encoding

Domain records never go into SQLite as free-form JSON. encodeStored wraps a tagged value in { version: 1, value }; arrays and objects become ['array', …] and ['object', [[key, value], …]], and bigints become ['bigint', decimal]. This keeps identities type-tagged: the number 1n cannot collide with the string "1". The encoder drops undefined object properties and rejects class instances, non-finite numbers and undefined array elements. It caps records at MAX_RECORD_BYTES = 16 MiB, one million nodes and depth 128. The decoder rejects duplicate object keys and defines __proto__ as an own property rather than mutating a prototype (src/project/store/encoding.ts).

Prepared callee units use encodeStoredGraph, which extends the same scheme with Map, object identity (['ref', n]) and string interning (['s', n]). Shared substructure — copy-on-write analysis state, a types.calls object aliased by analysis — is written once and reconstructed aliased. Property names are interned from their third use, long string values from their second. Graph records have their own limits: MAX_GRAPH_BYTES = 128 MiB and twelve million nodes. Summaries are then Brotli compressed at quality 4 and stored as a BLOB.

Revisions, snapshots & annotations

The project revision is a single integer. It is not a per-table version: it names one complete, immutable view of every fact. Reads take a revision explicitly; a query for revision 2 must return the same answers forever, regardless of revisions committed later. The store implements that with "latest row at or before the requested revision" for images, records, types, signatures, evidence, annotations and loaded images. A record inserted at revision 3 is invisible to a revision-2 query; a deletion at revision 3 is represented by a tombstone, so revision 2 still sees the earlier payload.

Two different preconditions appear in requests. Read-only tools carry revision; mutations carry expected_revision. The host's validateToolRequest can assert either against the current revision before work begins, and throws RevisionConflict (code stale_revision) with both numbers. The store repeats the check atomically because time passes between admission and commit. Annotation batches are the richest example:

  1. Preflight. AnnotationService.apply compares expected_revision with the current snapshot and returns a conflict without reading more.
  2. Validate against the old snapshot. Edits must name a durable subject or a trusted catalog subject; evidence and type closures must resolve at the current revision; signature ABI must match the subject image; annotation IDs may not move to another entity, even after removal or lineage changes.
  3. Prepare assertion evidence. An edit with no evidence gets a deterministic assertion proof derived from project, revision, annotation, author, origin and status.
  4. One synchronous transaction. The complete response — including evidence and the completed job — is validated inside the commit hook. A failure there rolls back annotations, evidence and the job together.
  5. Return the new revision. The result reports previous_revision, revision, applied/removed IDs and invalidation.derived_before_revision. If the precondition fails at commit time, no edits are committed; the tool result is failed with stale_revision, current_revision set, and the job saved as stale.
Refusal

A stale annotation batch is not retried, merged or partially applied. The stale_revision diagnostic and current_revision are the contract; callers must inspect and resubmit against the new snapshot.

The analysis cache

The cache stores the semantic result of function_decompile, not the emitted text alone. An artifact payload contains a format version, the full CacheIdentity, the inline decompilation result (state, signature, emission, capabilities, evidence), an internal semantic catalog (subjects, supplied types, proofs) and, optionally, the dependency readset. The media type is application/vnd.open-decomp.function+json; the format version is ANALYSIS_ARTIFACT_VERSION = 2; the artifact bound is MAX_ANALYSIS_ARTIFACT_BYTES = 16 MiB (src/project/cache/model.ts). The exported readAnalysisArtifact is that exact reader for trusted consumers (investigation and catalog assembly), not a second cache path.

Identity: what makes a result reusable

CacheIdentity is a strict object. It includes the image hash and slice, the complete target contract, all pipeline component versions, both revisions, the function ID, the presentation options and the original request budget. The budget is part of the key on purpose: a result computed under a smaller work or output budget is not the result a larger request would produce. 

export const cacheIdentitySchema = z.strictObject({

pipelineVersions composes a version record from the loader, decoder, lifter, ABI, emitter and one explicit analysis string: pipeline/25;discovery/5;targets/2;ssa/5;values-effects/4;stack-calls/9;debug/1;library/8;types/8;annotations/1;structure/3;reconstruction/49. Those numbers are a contract, not a package version: changing any stage's semantics requires bumping its entry, which invalidates old artifacts instead of silently serving them. acceptsAnalysisIdentity checks the stored components against the current composition before an annotation catalog may be trusted.

Lookup, hit and publication

runCachedDecompilation is the only path that decides hit versus compute. It first validates the durable job: the job must exist, belong to this project, be a function_decompile job, be at the current revision, and be queued or running. Then it takes one of five paths:

  1. Exact hit. If caching is enabled and store.findArtifact(identity) returns a row, the payload is loaded, parsed (memoized by its verified SHA-256), checked against the artifact metadata and index key, and passed through validateComputation. The job is completed with the existing artifact handle; no analysis runs.
  2. Reuse hit. Otherwise up to eight earlier artifacts with the same revision-independent scope are tried. A candidate is usable only if it has a complete readset and validateAnalysisReadset observes every selector with the same fingerprint at the current revision. Its result is re-stamped with the current revision; the catalog and readset are kept. It is reported as cache: "hit".
  3. Compute. The pipeline callback runs, and the collector returns the ordered readset. Validation checks the snapshot image, target, function, result metadata, emitter dialect/version, catalog trust, type closure and proof closure.
  4. Size and delivery. The payload is serialized and sized before commit. Delivery is inline when it fits the output limit, otherwise an artifact envelope points at the published handle.
  5. Publish. store.publishArtifact rechecks the job and current revision, then writes the bytes, indexes analysis IDs, records the reuse scope, completes the job and flushes queued native summaries. 
const enabled = input.analysis_cache !== false;
const existing = enabled ? store.findArtifact(identity) : null;
if (existing) {
  const payload = loadPayload(store, existing, context, identity, false, existing);
  const response = delivery(payload.result, existing, 'hit', limit, input.delivery ?? 'auto', true);
  const job = activeJob(store, job_id, identity, context);
  store.saveJob({ ...job, state: 'completed', progress: { phase: 'complete', completed: 1, total: 1 },
    artifacts: [existing], published_revision: identity.annotation_revision });
  return markSchemaValidated(response);
}

src/project/cache/index.ts (runCachedDecompilation). The early return is legitimate because the payload was parsed, size-bounded and validated by loadPayload; no later stage repeats the parse.

Invariant

A stored artifact is not trusted because it exists. loadPayload checks the media type, project and size; verifies the bytes against the stored SHA-256; parses once; checks that the payload identity revisions equal the artifact revision and that the exact cache key matches; then, except for the artifact just located by its exact key, resolves the identity again through findArtifact/findHistoricalArtifact. Every hit re-runs validateComputation; reuse candidates additionally validate their readset before they are accepted.

The dependency readset

Reuse across revisions is only safe if the computation that produced the result depended on nothing that changed. AnalysisDependencyCollector is a ProjectStore proxy. Every store read it sees at the preparing revision is converted into a typed selector and a canonical fingerprint; reads at other revisions are not captured. The selector union is closed: signature, type, proof, annotations, type_annotations, all_annotations, record_scope, function, function_address. 

case 'queryRecords':

src/project/cache/dependencies.ts (AnalysisDependencyCollector, recordRecordScope, createAnalysisReadset). The excerpt is trimmed; the real proxy also wraps signatures, types, evidence and annotation queries.

recordRecordScope captures a negative read: not the functions found, but the version of the whole record/index/image scope, computed by readRecordScopeVersion from the latest record revision, the latest index state and the latest loaded-image revision. That is what makes an empty result reusable — if no function exists at revision 2, and the scope token is unchanged at revision 3, the absence is still valid. recordFunction additionally records the function's evidence and signature closure; recordProof and recordType walk derived_from/conflicts_with and type references to a fixed point, not just one hop. Duplicate selectors are captured once; a re-read costs nothing.

Validation replays the ledger against the new revision: validateAnalysisReadset requires a well-formed selector, recomputes its fingerprint from the store and returns false on the first mismatch. It reports progress (dependency-validation) and bounds the ledger at MAX_READS = 100000. If a candidate has no readset, it is not reusable across revisions at all. replay and verifyTracedReads do the same for persisted callee units, with a per-store/revision memo so shared closures are checked once.

Size limits and shedding

The 16 MiB artifact bound can never cost the pseudocode. When the serialized payload is too large and a readset is present, the readset is dropped first; the artifact then serves only its exact revision. Then whole emission metadata classes are shed in EMISSION_METADATA_SHED_ORDER: inferences, mappings, then requirements. Each shed is recorded in emission.omitted and in a partial provenance coverage/capability; an otherwise complete result becomes partial with reason output_limit. The text, signature and annotation catalog remain. If even the stripped payload exceeds the bound, the operation fails with resource_limit and names the pseudocode size — nothing is published.

Separate caps bound the store and the readers: artifacts are at most 64 MiB at the store boundary (MAX_ARTIFACT_BYTES), parsed payload memoization is 16 MiB (MAX_PARSED_PAYLOAD_BYTES), and annotation-catalog reconstruction reads at most 128 artifacts and 32 MiB. A decompilation response is inline only if it fits the smaller of the request's output_bytes, the transport's max_result_bytes and the frame budget; otherwise the caller receives an artifact handle and must page the bytes.

--no-analysis-cache

This is a trusted host setting, not a tool-request field. It reaches the worker in the open command and is passed to the handler scope as analysis_cache: false. With it, runCachedDecompilation skips findArtifact and findReuseCandidates, never calls publishArtifact, and delivers any artifact-shaped response from publishTransientArtifact — memory only, newest within 64 MiB, readable like a published handle for this session but never indexed or written. Native unit persistence returns undefined, and the in-process prepared-unit cache returns an empty identity, so nothing is read or left behind. The dependency collector still runs, which keeps work charges and therefore results identical. Imports, indexes, annotations and jobs still persist.

The persisted callee-summary tier

Decompiling one function can prepare many callee bodies. Those units are much larger than the final artifact and are the dominant cold cost. There are two reuse tiers: an in-process WeakMap keyed by the loaded image (preparedUnitCache), and the durable native_summaries table. createNativeUnitPersistence supplies the durable tier's load/save pair. The durable tier is keyed by a digest of the format version, project revision, image hash, slice, target, pipeline versions, lifter, ABI and supplied native types — the emitter dimension is fixed to the preparation pipeline's c-like version record because preparation happens before emission. The row key is (scope, function_id).

A row is offered only if its envelope parses, its identity fields equal the request, its dependency targets resolve in the current function list, its call analysis is complete, and verifyTracedReads revalidates every dependency read. The payload uses encodeStoredGraph and Brotli quality 4. It is not stored when it exceeds MAX_PERSISTED_UNIT_SIZE = 8192 prepared-size units (instructions + IR nodes + evidence + traced reads): the comment records that a 32k-unit is roughly 30 MB of JSON, ~330 ms to write and ~260 ms to load against ~450 ms to prepare, while smaller units take a few milliseconds. A single compressed row above MAX_NATIVE_SUMMARY_ROW_BYTES = 16 MiB is rejected; the per-project cap is DEFAULT_NATIVE_SUMMARY_BYTES = 64 MiB. Queued writes flush at the next publication, when they exceed MAX_PENDING_SUMMARY_BYTES = 8 MiB, or at store close. Eviction is deterministic: superseded revisions are dropped first, then the oldest (revision, seq) rows until the cap is met.

Cache writes never fail a request

#writeNativeSummaries runs inside a SAVEPOINT; a failure rolls back only the summaries and leaves the enclosing publication intact. Undecodable or digest-mismatched rows are reported as misses and replaced by the next preparation, never served.

Execution: pools, frames, jobs

ProjectWorkerPool keeps at most max_workers persistent child processes (default 2, allowed 1–32) and a queue of at most max_queued admitted jobs per project (default 16, allowed 0–1024). One canonical project path has exactly one owner in a pool; opening the same path twice is rejected. Admission capacity is reserved before source authorization, so a flood cannot create an unbounded backlog. Exhaustion is immediate resource_limit, not an infinite wait; closing an idle project releases its slot. The comment is explicit that processes provide fault containment, not a filesystem sandbox against a malicious local host.

The transport is a length-prefixed JSON stream, not Node IPC. Each frame is a 4-byte big-endian length followed by UTF-8 JSON; the decoder checks 2 ≤ length ≤ MAX_FRAME_BYTES before allocating or parsing. The host also caps its write queue at 4 MiB and its pending control requests at max_queued + 4; the child serializes commands through a promise chain and rejects more than 1028 pending ones. Stdout is exclusively framed IPC; stderr is not protocol, and more than 64 KiB of it kills the child. Artifact reads are capped at 512 KiB of raw bytes per response because hex doubles the size, with next_offset for continuation.

Job lifecycle, progress and cancellation

submit reserves a queue slot, authorizes the source path, validates the request schema and sends admit. The child writes the queued job and replies; only then does ticket.accepted resolve. The host keeps one running job per project and calls run when it is ready; status reads durable state. JobTicket.result resolves with the terminal job and, when still in memory, its result. A completed recovered job may omit the transient result; callers must inspect artifacts or repeat a read-only query. Annotation and decompilation results are parsed against their tool output schema at the child boundary, and decompilation results may be marked schema-validated so the host does not parse them again.

Progress is written through OperationContext.progress. The runtime throttles saved/written updates to at most one per 100 ms and writes a progress frame only when stdout has no buffered bytes, so a slow reader cannot grow an unbounded queue. Phases seen in a real import are queued, running, image_snapshot, discovery and complete; analysis uses decode, lift, ssa, metadata and later stages with totals. The durable job, not the notification stream, is authoritative.

Deadlines exist twice. The host sets a timer for the request's budget.deadline_ms and calls #interrupt(id, 'deadline'). The child checks the absolute deadline before starting (it may have waited in queue) and clamps the context deadline to min(request.deadline_ms, deadline - now). checkpoint samples the clock every 32 charges and latches expiry, so later checkpoints fail even if the clock is not read again. Work above budget.work fails with a resource_limit diagnostic carrying details.resource: "work" or "deadline_ms".

Cancellation is cooperative where possible and process-level where necessary. For a job that has not started, the host sends cancel instead of run; the child marks it cancelled and never executes it. For a running job the host marks it cancelled and restarts the child: SIGTERM, then SIGKILL after cancel_grace_ms (default 100 ms), then open with interrupted: { id, reason }. On startup the child marks every nonterminal job terminal — cancelled only when the interruption was explicit and the revision is unchanged, otherwise failed with worker_failed/resource_limit and a diagnostic saying the operation was not retried. If a mutation committed before interruption, it is never mislabeled cancelled.

Queries, MCP & settings

Fourteen tool names exist. Four are host-level control operations; ten cross the worker boundary and are dispatched by queryWorkerHandler. The worker schema explicitly excludes project_open, project_close, analysis_cancel and analysis_status, because they manage the pool or durable job state rather than target analysis.

Every worker result passes the same envelope validation. The handler parses against toolSchemas[operation].output, enforces the frame limit, and returns a marked result; the host re-checks the operation/project/revision relationship with validateToolResponse, including the one-revision mutation rule and the output byte budget. A decompilation hit may skip the second parse because runCachedDecompilation already validated the stored payload and sized the response.

MCP mapping and function handles

MCP is a transport adapter, not a second implementation. createMcpServer registers every name in toolNameSchema and calls the same QueryService.execute with max_result_bytes = MCP_CORE_RESULT_BYTES (693,589 bytes, leaving room for text projection and the 2 MiB MCP message). Artifact resources call QueryService.readArtifact, which goes to the owning child; no resource read resolves a filesystem path.

MCP adds three conveniences that are removed before core validation. A function handle may be a name, a va:/rva:/file: address, or an entity ID/prefix of at least 12 hex digits. prepareRequest replaces it with HANDLE_PLACEHOLDER (entity_ plus 64 zeros) so the core schema can validate every other field, and so host authorization never reads an untrusted selector. After authorization, selectFunction resolves the handle through the function index (name/address/prefix) and site.bind substitutes the full entity ID. The same mechanism covers function_get.function_id, function_decompile.function_id and xrefs_get.target.id when the target kind is entity. An ambiguous or unresolved handle is a tool failure with candidate paths/IDs, never a guess. function_decompile also defaults wait to "auto" and accepts detail: "text"|"full"; the advertised JSON schema is patched to match.

Settings precedence

Settings are optional defaults, never a second source of truth. The library does not read the file implicitly; entry points call loadSettings, which validates a strict versioned JSON object and reports the source of every effective value. Precedence is built-in default < settings file < explicit CLI flag / API option / MCP request argument. An explicit settings path that is missing is an error; the default path being missing is not. Invalid JSON, an unknown key, a wrong type or an unsupported version is a SettingsError naming the path and key, never a silent fallback.

Parallel export

exportBinary is the one operation that intentionally opens several projects at once. A SQLite database has one owner, so the exporter does not submit parallel jobs to one project. Instead it finishes the primary import, closes it, and lets worker 0 reopen the original project while workers 1..N-1 open private copies. Each copy is made with cp(..., { recursive: true, mode: COPYFILE_FICLONE }) under <cache>/.export-<pid>-<timestamp>/w<index>/<project>; scratch copies are removed in finally. The worker count is max(1, min(options.jobs ?? max(1, min(4, availableParallelism() >> 1)), rows.length || 1)), so it never exceeds the number of functions. A shared iterator hands rows to whichever session is free; the first real error aborts the controller, every worker stops, and the error is rethrown. Per-function failures are recorded in index.tsv instead of aborting the export. Extra workers inherit --no-analysis-cache when set.

Why copies, not a shared cache

The exclusive connection is a correctness boundary: a project store trusts that no second writer can move the revision under a transaction. Copy-on-write clones preserve the finished import without duplicating disk blocks where the filesystem supports it, and each worker's summary/artifact writes stay private.

Limitations & extension points

The design intentionally trades flexibility for reproducible snapshots. Some consequences are permanent; others are roadmap items from CONTINUE.md. The code is the authority where the two disagree; in particular, the store is at schema 6 even though some prose still says schema 5.

Area Current behavior (verified in code) Remaining work (roadmap)
stdio cancellation Connection end or abort interrupts a job; cancellation of running work restarts the child. A pending-ID leak on cancellation in the stdio transport is still listed.
Per-job cancellation Queued jobs are dropped; running jobs are stopped by terminating the owner and reconciling SQLite. Cooperative per-job cancellation inside a long synchronous pass is not universal.
Poisoned cache rows Native-summary digest, decode and trace failures are misses and are replaced by the next preparation; damaged analysis artifacts are rejected as invalid_input, never served. Broader poisoning cases still rely on recomputation; the roadmap keeps this item open.
Foreign project directory Resume checks schema range, path canonicality and file type; artifacts/images are hash-checked. A full trust check before resuming a directory produced elsewhere is still listed.
HTTP throttling Authenticated principals have configured quotas and deadlines. A global rate limit is applied only after authentication; pre-auth flooding is a deployment concern.
Control-character escaping Text projections escape the characters used by the CLI/export writers. C1 control escaping in emitted strings remains on the reliability list.
Stale prose STORE_SCHEMA_VERSION = 6; migration 5→6 creates native_summaries. Docs that say schema 5 or “summaries are not yet persisted” are stale.
Structural limits

One owner per project caps intra-project parallelism; export works around it with clones. Exact cache hits are current-revision only, so an annotation edit immediately loses exact reuse and must pass a readset check. Prepared units above 8,192 size are never persisted, so large functions stay cold. The host is not a sandbox: worker processes contain faults, not a malicious local host. MCP messages and frames are capped at 2 MiB, so large results must be paged through artifacts.

Adding a new tool

  1. Declare the name and schemas. Add the name to toolNameSchema in src/core/tools.ts and add its input and output schemas to toolSchemas. Strict objects are the convention; every request carries project_id, revision (or expected_revision) and a budget.
  2. Choose the execution path. Analysis/navigation tools automatically become worker operations because workerOperationSchema excludes only the four control names. Add a case to dispatch in src/service/queries/handler.ts. Control tools that manage the pool belong in QueryService.execute instead.
  3. Use the shared envelope and limits. Return queryEnvelope metadata, page with paginate, call context.checkpoint, and enforce the same min(output_bytes, max_result_bytes, MAX_FRAME_BYTES - 16384) bound. If the result is already schema-validated, mark it so the runtime does not parse it twice.
  4. Make it cacheable only with an identity and a readset. Wrap the computation in runCachedDecompilation with a complete CacheIdentity and pass the dependency collector; do not invent an alternate key.
  5. Wire the transports. MCP advertises every schema automatically; add a handle site in prepareRequest only if the tool accepts a short function handle, and update advertisedInputSchema. Add CLI/API plumbing only if the tool is user-facing there.
  6. Test the boundaries. Cover schema rejection, project/revision mismatch, page cursor binding, output-budget failure and worker recovery. The existing suites in test/workers, test/service and test/project show the fixture patterns.

Adding a schema migration

  1. Bump persistence, not the wire. Increment STORE_SCHEMA_VERSION in src/project/store/index.ts. Do not change SCHEMA_VERSION for a persistence-only change; the two are deliberately independent.
  2. Update both creation and upgrade paths. Add the new table/index to the mode === 'create' DDL so a fresh database is born at the new version, and add an if (version < N) block to the resume chain. The chain runs inside one BEGIN IMMEDIATE; a throw rolls everything back.
  3. Backfill only from verified data. The 3→4 migration is the model: decode each stored image, check its identity against the row, and abort on mismatch instead of inventing metadata. Derived tables may start empty; historical facts may not be guessed.
  4. Prove both directions. Open a database created at version N-1, run the migration and verify every historical row; then verify that an older application refuses the new version with unsupported_version. Tests such as test/project/store/history.test.ts and test/project/store/image-metadata.test.ts build the old schema explicitly.
  5. Keep the version in the snapshot. ProjectSnapshot.schema_version reports the store version; do not substitute the wire schema.
