Stage 04 · Lifting

Decoding, lifting & IR

This stage turns machine bytes into a typed, verified semantic graph. A per-architecture decoder produces structured operands and control-flow facts without ever treating assembly text as input; a lifter expands each instruction into explicit dataflow, state effects and a terminator; an IR verifier then proves the graph is well-formed before SSA construction begins.

Where this sits in the pipeline

The stage consumes two things that stage 03 already established: a LoadedImage (bytes plus the address map that translates file offsets, RVAs and VAs) and, per function, a FunctionGraph. A graph is not raw bytes: it holds the discovered CFGBlock boundaries, every DecodedInstruction those blocks reference, decode gaps, coverage, diagnostics, and — when discovery proved them — ResolvedJumpTable facts. Discovery owns block boundaries; calls are reference edges, not intraprocedural successors.

Decoding happens inside discovery: discoverFunctions calls decoder.decode with the image, the regions it wants decoded, the target's feature list and the mode (a64 or long64). The lifter is invoked later by analysis (prepareNativeUnit and the analysis service), which passes the finished graph plus an AbiProfile. The lifter returns RegisterIR — register-form IR with explicit reads and writes — never SSA. SSA construction, value analysis and simplification are separate passes on the next page. The call nodes and physical clobbers produced here are interpreted on the calls & ABI page, and the machine types defined here are refined into source types on the types & metadata page.

The boundary is enforced by the contracts themselves. Decoder.decode returns instructions and gaps; it cannot create IR. Lifter.lift accepts a FunctionGraph and returns { ir, coverage, diagnostics }; it maps each discovered block to one IR block and may add synthetic guard or exit blocks, but it cannot rename, merge or re-split a discovered boundary. Every identity is content-addressed: entityIdentity(slice, kind, birth) hashes the slice, a kind tag and a stable birth key, so re-running the same pass on the same inputs mints the same IDs.

The decoder contract

A decoder is an architectural fact producer. It reports what the bytes mean for a chosen feature set and where control goes; it does not build IR, infer types, or name variables. The whole contract is three declarations: 

export interface DecodeRequest {
  readonly image: LoadedImage;
  readonly regions: readonly AddressRange[];
  readonly features: readonly string[];
  readonly mode: 'a64' | 'long64';
}
export interface DecodeResult {
  readonly instructions: readonly DecodedInstruction[];
  readonly gaps: readonly DecodeGap[];
  readonly coverage: z.infer<typeof coverageSchema>;
  readonly diagnostics: readonly Diagnostic[];
}
export interface Decoder extends ComponentIdentity {
  readonly architecture: Target['architecture'];
  decode(request: DecodeRequest, context: OperationContext): DecodeResult;
  format?(instruction: DecodedInstruction): { readonly mnemonic: string; readonly operands: string };
  dispose(): void;
}

DecodedInstruction

export interface DecodedInstruction {
  readonly id: string;
  readonly address: Address;
  readonly bytes: AddressRange;
  readonly size: number;
  readonly validity: z.infer<typeof instructionSchema>['validity'];
  readonly payload: Arm64Payload | X86Payload | null;
  readonly flow: DecodedFlow;
  readonly diagnostics: readonly Diagnostic[];
  readonly evidence_ids: readonly string[];
}
export interface DecodeGap {
  readonly range: AddressRange;
  readonly reason: 'truncated' | 'unmapped' | 'data' | 'budget';
  readonly diagnostics: readonly Diagnostic[];
}

Three invariants are enforced by the Zod schema itself, not by convention: a valid instruction must carry a structured payload; an instruction with an ARM64 payload is exactly four bytes; and the bytes reference must have the same size as size. The payload is a discriminated union on architecture, so a consumer cannot accidentally read ARM fields from an x86 instruction. The validity enum reserves reserved, which the current two adapters do not emit (upstream folds those words into undefined).

bytes is the byte reference used for display and provenance. It is normally in the file space, but for an instruction whose bytes cross two adjacent virtual mappings with non-contiguous backing, both adapters fall back to a VA reference rather than inventing contiguous file bytes. Provenance later copies this range verbatim, so the original container offsets survive into the IR.

src/core/decoder.ts (instructionSchema, DecodedInstruction, DecodeGap).

DecodedFlow

Flow is a small sum type with two cross-field rules: for branch, indirect_branch and trap flows, conditional === (fallthrough !== null); and an indirect call must have a null target while a direct call must have a decoded target. The kinds are:

Kind Fields Meaning
fallthrough next Ordinary next instruction.
branch target, conditional, fallthrough Direct intraprocedural transfer.
call target | null, fallthrough, indirect Call is a reference edge; execution resumes at fallthrough.
indirect_branch conditional, fallthrough Target unknown to the decoder; discovery may prove a jump table separately.
return — Architectural return.
trap reason, conditional, fallthrough Deliberate trap (e.g. BRK/UDF/HLT on ARM64, ud2/int3/int on x86-64).
unknown reason, may_fallthrough Semantics not established; no invented edges.

A trap is a fact about the instruction, not a catch-all. On ARM64, invalid encodings, feature-gated instructions and exception-generating system calls become unknown with an explanation, and x86-64 invalid encodings do the same; this prevents a decoder bug or a missing CPU feature from masquerading as proven unreachable code.

Register descriptors

Register identity is ISA-qualified and independent of any decoder library's enum. A descriptor is a slice of a physical root: 

{
  id: string;                 // e.g. "x86_64:ah" or "arm64:w0"
  root: string;               // e.g. "x86_64:rax" or "arm64:x0"
  bank: 'integer' | 'float' | 'vector' | 'flags' | 'segment' | 'control';
  offset_bits: number;        // bit offset inside the root
  width_bits: number;
  root_width_bits: number;
  role: 'general' | 'stack_pointer' | 'program_counter' | 'zero' | 'flags';
  write_rule: 'preserve_other_bits' | 'zero_extend_root' | 'replace_root' | 'discard';
}

The schema rejects a slice that exceeds its root and a zero register whose writes are not discarded. The verifier adds two more rules: replace_root must cover the whole root (offset 0, equal width), and zero_extend_root must start at bit zero. These rules make a partial write's effect on the root unambiguous for SSA.

Register access metadata (read, write, read_write, conditional_read, conditional_write, read_conditional_write, none, unknown) is dependency information used by discovery, target analysis and presentation. Lifters deliberately do not use it to decide semantics: an instruction's architectural behaviour is written down explicitly in the lifter.

Payloads

encoding, canonical_encoding, alias encoding (iced Code name), mnemonic
word, fields: Record<string, bigint> operand_bits, address_bits, prefixes
operands (≤32 structured operands) operands (≤16), registers (≤256), memory (≤64)

ARM operands are a discriminated union of register, immediate, relative, memory, condition, system, modifier, floating_immediate, opaque, and the scalable/SME forms. An opaque operand preserves upstream text for presentation only; the lifter refuses to read it. x86 memory operands carry segment, base, index, scale, displacement, address width, access width, RIP-relative target, broadcast and access mode; immediates carry both encoded and effective widths plus a sign_extended flag.

Invariant

valid implies a non-null architecture payload, and an ARM64 payload implies size === 4. The schema encodes both rules.

Presentation is not semantics

format?() exists for diagnostics and UI. The ARM adapter can format a word by re-decoding it; the x86 adapter can format only instructions decoded by the same formatting-enabled instance. No lifter calls it, and no lifter parses operand text.

Wrapping a64js and iced-x86

Both adapters follow the same shape: normalize the requested regions to virtual addresses, partition them at data and mapping boundaries, walk only backed bytes, convert each native instruction into the neutral payload, and report every byte they did not decode as a typed gap. The differences are in the native library and in what “one decode step” means.

Arm64Decoder

The ARM adapter is pinned to the vendored a64js snapshot and reports its version as the upstream commit plus an adapter suffix. It creates a decoder with createDecoder({ features }), then walks each mapped span four bytes at a time:

  1. Normalize regions. Requests in file space are mapped through image.mappings into VA ranges; holes become unmapped gaps and adjacent or overlapping ranges are merged. RVA requests add image_base. Decoding regions must belong to the image.
  2. Prepare data boundaries once. Data hints are normalized once per LoadedImage object and cached in a WeakMap; the cache is keyed by the snapshot object, because another snapshot of the same bytes can have different data boundaries. Failed preparation never publishes a partial entry.
  3. Segment. Each mapped span is split at data-hint ends and at non-mapped span kinds. Data and unmapped segments become gaps of reason data or unmapped.
  4. Decode words. Alignment fragments become truncated gaps. Each four-byte word is decoded from the file bytes; when a word crosses adjacent mappings with non-contiguous backing, the adapter gathers the four bytes across parts and emits a VA byte reference. The instruction budget is checked before every word.
  5. Convert and classify. Native encodings, fields and operands become the neutral payload; the native status and availability become validity; flow is derived from mnemonics and structured relative operands.

Two adapter-specific completions sit outside the generated tables. completeLogical recognises missing logical shifted-register words (AND/ORR/EOR/ANDS and their BIC/ORN/EON/BICS inverses) from their fields, including the 32-bit shift-limit failure. structuredOperands replaces text-only representations of common families (memory addressing, SP/WSP versus XZR/WZR, vector arrangements) with structured operands derived from fields. An operand the adapter cannot structure is preserved as opaque, with an unavailable_semantics diagnostic and the coverage reason opaque_operands.

The native ARM result carries an availability and a status. Availability unavailable becomes feature_disabled; otherwise native status undefined becomes undefined, native unknown becomes invalid, and the rest is valid. Required features are the union of the encoding's features, its feature guards and the feature checks inside its encoding guards. When an instruction is feature-disabled but its encoding is known, the adapter re-decodes the same word with those features enabled only to extract operands; the original availability, diagnostics and behaviour remain authoritative. This is why a disabled instruction can still show useful operands without pretending it is executable.

X86Decoder

The x86 adapter wraps iced-x86 in long mode. It creates one iced Decoder per bounded window, with WINDOW = 64 * 1024 bytes plus up to 14 bytes of lookahead so an instruction beginning at the end of a window can finish. Metadata comes from InstructionInfoFactory (used registers and memory, operand access) and getConstantOffsets (encoded immediate widths); both are freed in finally blocks.

  1. Normalize and partition. File regions are translated through the AddressMap; a file region with no static VA becomes an unmapped hole with a diagnostic. Data hints are preprocessed into ordered, disjoint intervals with a sweep line, and a binary search skips unrelated data while partitioning.
  2. Gather contiguous backing. Decode runs consist of adjacent non-gap parts. windowBytes copies at most WINDOW + 14 bytes, gathering across adjacent mappings even when their file backing is disjoint.
  3. Decode. decoder.ip is set to the VA, and each decodeOut advances the cursor. NoMoreBytes at a backed-region boundary is a truncated gap; an invalid encoding produces an invalid instruction with a null payload, an unknown flow with may_fallthrough: false, and an invalid_input diagnostic.
  4. Convert. payload() synthesizes the neutral payload: registers as architectural slices with root and write rule, memory as segment/base/index/scale/displacement plus resolved RIP target, flags as bit masks in RFLAGS positions, x87 status bits in a separate namespace, and prefixes including REX/VEX/EVEX/XOP/MVEX kind, mask, zeroing and rounding.
  5. Classify flow. iced's FlowControl maps almost one-to-one to DecodedFlow; segmented far transfers become unknown, and XbeginXabortXend becomes a conditional branch when a near target exists.

Feature validity is explicit: required_features is the list of iced CpuidFeature names. If the request supplies a non-empty feature list and any required feature is absent, the instruction is still fully decoded and a payload is kept, but its validity becomes feature_disabled with an unsupported_target diagnostic. privileged is recorded separately; the lifter refuses privileged instructions rather than silently modelling them.

Aliases

ARM keeps the distinction between the matched encoding and its canonical form. encoding is the upstream encoding ID, canonical_encoding is the canonical ID, and when those differ the adapter stores alias: encoding.instructionId. Lifting keys on canonical_encoding.split('_')[0], so an alias is lifted as its canonical operation (for example a MOV that is really an ORR with Rn == Rm), while the payload retains the alias name for presentation. x86 has no separate alias field: iced resolves the encoding and reports Code plus a lowercase Mnemonic, and the lifter switches on that mnemonic.

Invariant

No assembly text participates in semantics. The ARM adapter derives operands and fields from the canonical word; the x86 adapter derives them from iced's structured operand model. opaque text is preserved but never parsed; format strings are only used by format?().

Refusal

Both decoders throw TypeError/RangeError for a mismatched architecture or mode and for a region belonging to another image, and a plain Error after dispose(). Budget exhaustion does not throw: it truncates at the instruction limit and reports a budget gap.

The IR type system and object model

The IR is a typed, immutable semantic graph. It is deliberately not an AST: operands always refer to preceding local definitions by Value, never to nested expression text. The type system is a machine type system, not a recovered source type system.

Types

export interface IntegerType { readonly kind: 'integer'; readonly bits: number; }
export interface FloatType   { readonly kind: 'float'; readonly bits: 32 | 64; }
export interface VectorType  {
  readonly kind: 'vector';
  readonly element: IntegerType | FloatType;
  readonly lanes: number;
}
export type DataType = IntegerType | FloatType | VectorType;
export type IRType = DataType | { readonly kind: 'effect' };

Integers are signless bit vectors; signedness belongs to the operation, not the type. integer(bits) accepts 1..2048, floating(bits) accepts only 32 or 64, and vector(element, lanes) accepts 1..256 lanes with a total width of at most 2048 bits. bitWidth multiplies element width by lane count for vectors; sameType compares kind, width and, for vectors, lanes recursively.

Values, effects and origins

export interface Value { readonly id: EntityId; readonly type: DataType; }
export interface Effect { readonly id: EntityId; readonly type: { readonly kind: 'effect' }; }
export interface Provenance {
  readonly instruction_ids: readonly DecodedInstruction['id'][];
  readonly ranges: readonly AddressRange[];
  readonly evidence_ids: readonly Evidence['id'][];
  /** A nonempty justification is required for nodes without machine instruction origins. */
  readonly synthetic: readonly string[];
}
export interface Origin { readonly id: EntityId; readonly provenance: Provenance; }

Provenance is the audit trail. A node produced from an instruction carries that instruction's ID, its byte range and its evidence IDs. A node invented by a pass (for example a synthetic exit block, or a trusted-fixture program) must carry a non-empty synthetic reason instead; the verifier rejects an origin with neither. Merging provenance is an ordered union of all sources, so a rewrite keeps every contributing instruction rather than only the last one.

Expressions

Every expression is pure and has exactly one result type. The variants group as follows:

Group Kinds Notes
Leaves constant, address, indeterminate Constants are canonical for their width; addresses are 64-bit memory coordinates; indeterminate carries undefined or unknown plus a reason.
Integer integer (add sub mul udiv sdiv urem srem and or xor shl lshr ashr rol ror), integer_unary (not neg clz ctz popcount) Result type equals the left operand; shifts/rotates may take a different right width.
Comparison compare (eq ne ult ule ugt uge slt sle sgt sge) Always i1; operands have identical types.
Bits cast, extract, insert, concat Explicit truncate/extend/bitcast, bit slices, low-bits-first concatenation.
Selection select Condition is i1; both arms have the result type.
Flags flag add or sub, a named flag, left/right and an explicit carry/borrow input; result i1.
Floating float, float_unary, float_compare FP32/64 only; comparisons return i1 and include ordered/unordered.
Vector vector, vector_lane, vector_insert, vector_integer, vector_float Fixed typed lanes, lane 0 in the least-significant bits.

The meaning of a flag is fixed: for add, the carry input is a carry-in; for sub, it is a borrow-in. The carry flag means “no borrow” for subtraction, while borrow means “borrow”. Shift counts are not implicitly masked; a lifter must encode its ISA's masking explicitly. Division by zero and signed overflow produce undefined values rather than traps, because an ISA lifter decides whether the architecture traps.

Instructions, effects and memory

export type Instruction =
  | (Origin & { readonly kind: 'assign'; readonly result: Value; readonly expression: Expression })
  | (Origin & EffectOrder & { readonly kind: 'read_register'; readonly result: Value; readonly register: RegisterDescriptor })
  | (Origin & EffectOrder & { readonly kind: 'write_register'; readonly register: RegisterDescriptor; readonly value: Value })
  | (Origin & EffectOrder & RegisterInputs & { readonly kind: 'load'; readonly result: Value; readonly address: Value; readonly access: MemoryAccess })
  | (Origin & EffectOrder & RegisterInputs & { readonly kind: 'store'; readonly address: Value; readonly value: Value; readonly access: MemoryAccess })
  | (Origin & EffectOrder & { readonly kind: 'memory_fence'; readonly scope: 'inner_shareable'; readonly ordering: 'acquire_release'; readonly accesses: 'reads_writes' })
  | (Origin & EffectOrder & RegisterBoundary & { readonly kind: 'call'; readonly target: CallTarget; readonly arguments: readonly Value[]; readonly results: readonly Value[]; readonly clobbers: CallClobbers; readonly contract_evidence: readonly Evidence['id'][] })
  | (Origin & EffectOrder & RegisterBoundary & { readonly kind: 'unknown_effect'; readonly reason: string; readonly clobbers: CallClobbers });

Every state access — register read/write, load, store, fence, call, unknown effect — carries EffectOrder { effect_in, effect_out }. assign is the only pure instruction and has no effect token. A block owns one linear effect chain: each state access consumes the current token and produces the next; the terminator and every outgoing edge carry the final token. This makes reordering across state accesses impossible without a rewrite that explicitly rewires the chain, and it keeps calls and unknown effects from being silently moved.

MemoryAccess is { endian: 'little' | 'big'; alignment: number; volatile: boolean }. Endianness is explicit rather than assumed; alignment must be a power of two from 1 to 4096 (1 permits unaligned access); volatility is carried but does not by itself add ordering. CallTarget is either a direct Address or an indirect Value.

RegisterInputs and RegisterBoundary exist for SSA form. A call or unknown_effect snapshots the register cells it reads (register_inputs) and the ones it rebinds (register_outputs) without confusing them with source-level arguments and results. Loads and stores use register_inputs for the same reason: if the access faults, the state at that point still describes the physical writes that preceded it. In register form these lists are empty; the verifier rejects non-empty lists there.

Terminators, edges and blocks

export interface Edge {
  readonly target: EntityId;
  readonly arguments: readonly Value[];
  readonly effect: Effect;
}
export type Terminator = Origin & { readonly effect: Effect } & (
  | { readonly kind: 'jump'; readonly edge: Edge }
  | { readonly kind: 'branch'; readonly condition: Value; readonly when_true: Edge; readonly when_false: Edge }
  | { readonly kind: 'switch'; readonly value: Value; readonly cases: readonly { readonly bits: bigint; readonly edge: Edge }[]; readonly otherwise: Edge; readonly jump_table?: JumpTableOrigin }
  | { readonly kind: 'return'; readonly values: readonly Value[] }
  | { readonly kind: 'indirect'; readonly target: Value; readonly reason: string; readonly tail_call?: true }
  | { readonly kind: 'trap'; readonly reason: string }
  | { readonly kind: 'unknown'; readonly reason: string }
);
export interface BasicBlock extends Origin {
  readonly parameters: readonly Value[];
  readonly effect_parameter: Effect;
  readonly instructions: readonly Instruction[];
  readonly terminator: Terminator;
}

Edges pass all data arguments simultaneously plus the final effect token. This is the mechanism for loop-carried values and for joins: there is no implicit phi and no fall-through state. A block has data parameters and its own effect parameter; register-form lifters normally create zero parameters, but they may when a value must cross a synthetic boundary — the x86 divide guard does exactly that, passing the numerator and divisor into its continue block. (The FP guard's continue block has no parameters.) SSA construction later gives blocks parameters for architectural cells.

JumpTableOrigin is proof metadata attached to a switch lifted from a discovery-proven table: load_instruction names the load whose bytes are immutable table entries under the dominating guard, and the optional exact_guard_instruction records that the guard's out-of-range edge is taken exactly when the selector exceeds the largest case.

RegisterIR versus SSA form

export interface RegisterIR extends FunctionBody { readonly form: 'register'; }
export interface SSAForm extends FunctionBody {
  readonly form: 'ssa';
  readonly register_states: readonly {
    readonly block: EntityId;
    readonly entry: readonly RegisterBinding[];
    readonly exit: readonly RegisterBinding[];
  }[];
}
export type FunctionIR = RegisterIR | SSAForm;

RegisterIR is the lifter's output: architectural register operations are explicit, and the graph is stateful. SSAForm has no read_register/write_register at all; architectural state is represented by sparse register_states rows. At dominator-tree roots an entry row binds every tracked cell to a distinct block parameter; elsewhere it lists only the cells whose definitions meet at that block. Exit rows bind every cell at function exits and only cells rebound in other blocks. Unlisted cells inherit the immediate dominator's exit through registerStateAt, so full per-block state is derived, never materialized. The lifter is forbidden from doing any of this: construction is a separate pass (constructSSA), linked on the next page.

FunctionBody.returns is the list of IR value types expected by return terminators, not architectural return registers. Lifters pass an empty list: call/return ABI interpretation belongs to later stages, and both worked examples below have ir.returns = [] while still reading x0/d0 (ARM64) or the return slot (x86-64) for their own reasons.

src/ir/model.ts (FunctionBody, RegisterIR, SSAForm, SSAConstruction); src/analysis/ssa/index.ts (constructSSA).

Invariant

Operands refer to preceding local definitions only. A cross-block reference is legal only when the definition's block strictly dominates the use; joins and loops merge exclusively through simultaneous edge arguments. Effect tokens are block-local and never cross an edge except as the edge's single final token.

Building IR: identity, effects and blocks

Lifters never construct raw objects. IRBuilder and BlockBuilder enforce identity, type and effect discipline at the point of creation, and every builder emits node IDs in a deterministic sequence. 

#identity(kind: string): EntityId {
  if (this.#terminator) throw new TypeError('Cannot append after a terminator');
  return entityIdentity(this.slice_id, `ir.${kind}`, [this.id, this.#sequence++]);
}
#order(): { effect_in: Effect; effect_out: Effect } {
  const effect_in = this.#effect;
  const effect_out: Effect = { id: this.#identity('effect'), type: effectType };
  this.#effect = effect_out;
  return { effect_in, effect_out };
}
assign(type: DataType, expression: Expression): Value {
  this.budget?.nodes();
  const errors = expressionProblems(type, expression);
  if (errors.length > 0) throw new TypeError(errors.join('; '));
  const result: Value = { id: this.#identity('value'), type };
  this.#instructions.push({
    kind: 'assign',
    id: this.#identity('instruction'),
    provenance: this.#source,
    result,
    expression,
  });
  return result;
}

The sequence is per block and shared by values, instructions, effects and the terminator, so IDs are stable across a rebuild. Blocks are different: their identity comes from a caller-owned birth key. block(birth, parameters) hashes ['ir.block', [function_id, birth]]; a duplicate birth key throws. The lifters use ['discovered', block.id] for discovered blocks, so an IR block is traceable to its CFG block; guard continue blocks use instruction-derived births ([instruction.id, reason, 'continue']).

source(provenance) changes the origin attached to subsequent nodes. Lifters call it once per decoded instruction. finish() on the builder merges the function provenance with every block's, materializes the block list, creates empty SSA state rows only if the builder was created with form 'ssa', and calls assertValidIR. A block that was never terminated throws TypeError('Block has no terminator').

The high-level helpers are thin and typed: constant masks its bits with BigInt.asUintN; int/unary/compare/ cast/extract/insert/concat/ select/flag/fp/vectorInt all call assign after checking the expression; readRegister defaults the result type to integer(register.width_bits); load/store default to little-endian, alignment 1, non-volatile. edge(target, args) captures the current effect token, so an edge automatically carries the final effect of its block.

src/ir/builder.ts (IRBuilder, BlockBuilder, #order, assign, terminate, finish).

Enforced at construction

assign rejects an ill-typed expression before allocating a value; #identity refuses to append after a terminator; finish refuses a block without a terminator; IRBuilder.finish refuses any graph that fails verifyIR. Build-time checks are not a substitute for verification: they only see the current node, while the verifier sees cross-block references and dominance.

The lifting algorithm, per architecture

Both lifters share the same driver shape, because the hard part is the same: expand one instruction, then decide how the graph continues.

  1. Preflight. Reject an ABI for the wrong architecture; charge context.checkpoint(0); reject graphs whose instruction count, block count or minimum node requirement (blocks.length * 3) already exceed the budget.
  2. Build the function provenance. Merge every decoded instruction's provenance, or use a synthetic origin for an instruction-less function. This is the function-level audit trail; block and node provenance adds to it.
  3. Create one block per discovered block. Each block is born from ['discovered', block.id], has no parameters, and gets provenance merged from its instructions. Map both CFG block IDs and first-instruction addresses to IR blocks.
  4. Lift instructions in order. Set the source provenance, reject invalid/unavailable payloads, optionally insert an FP-environment guard, then let the architecture semantics append nodes. A jump-table selector is captured just before its selecting load executes.
  5. Dispatch control flow. Calls, returns, indirect branches, conditional branches and traps have driver-level handling; otherwise the semantics method must return true. Anything it declines becomes a boundary.
  6. Terminate. If the block was not terminated by an instruction, use its single non-call CFG successor (x86-64: its single fallthrough successor) as a jump, or a proven noreturn call as a trap, or an unknown boundary. A missing entry gets a synthetic block and an unresolved continuation an unknown terminator, rather than invented edges.

Register model

The IR has no special notion of sub-registers; it knows only roots, slices and write rules. The lifter chooses the descriptors, and therefore encodes the ISA's aliasing rules.

FP/vector arm64:v0..v31 (128-bit root); sN (32) and dN (64) are zero_extend_root slices x86_64:zmmN (512-bit root); xmmN/ymmN are slices; zmmN is in the unknown clobber set; legacy scalar writes use a preserving low slice
Control/status arm64:fpcr, arm64:fpsr x86_64:mxcsr, FS/GS base roots read as explicit control registers

ARM64 has no general-purpose PC operand: ADR/ADRP materialize PC-relative addresses as address constants, and literal loads use the decoded relative target. x86-64's RIP is a real decoder descriptor, but the lifter prefers the decoder's resolved RIP-relative target, so the address is a constant rather than an expression over a PC root.

ARM64 exposes NZCV as one 32-bit register, and the lifter packs four computed i1 flags into bits 31..28 with insert. x86 flags are six separate 1-bit descriptors over a shared 64-bit root, each write preserving the other bits; the decoder's flags payload (read, written, cleared, set, undefined, preserved) is dependency metadata, while the lifter writes each flag explicitly. x87 status bits (fpu_flags) are a separate namespace, not RFLAGS bits.

Memory accesses

ARM ordinary loads and stores are recognised by mnemonic family (LDR/STR/LDUR/STUR/LDP/STP/LDNP/STNP/LDPSW plus byte/half/signed suffixes, and LDRAA/LDRAB). The lifter finds the single memory or relative operand and the register operands, rejects constrained-unpredictable pair or writeback overlap, computes base + displacement plus an optional extended/shifted index, and chooses the pre/post-index address. Literal loads use the decoded relative target. Each element is a typed load/store; signed loads are extended to the destination width; writeback is a normal register write. The real loop example below contains ldr w10, [x8], #4: one load at x8, then x8 + 4 written back.

x86 addressing starts from the decoder's resolved RIP-relative target when present; otherwise it builds displacement + base + index * scale at the operand's address width and zero-extends to 64 bits. An FS or GS segment adds its base root, except for LEA, which computes an address without accessing memory. read/write attach MemoryAccess; alignment-sensitive moves (movaps, movapd, movdqa) request alignment 16, unaligned variants request 1.

Calls and returns

ARM BL/BLR writes the fallthrough address to x30 and emits a call with no source arguments or results and abi.unknown_call_clobbers. A direct call uses the decoded target; an indirect call reads Rn. Calls continue in the same block at the fallthrough instruction. RET with Rn == 30 reads the ABI's return-register capacity (the result registers for a pointer return and an FP64 return) and terminates with return and no values; RET through another register becomes indirect with reason 'Return through non-link register'.

x86 call reads rsp, pushes the address of the next instruction (decrement stack pointer, store), emits the call, then writes the original rsp back: the callee's stack effects are summarized by the call node, not by leaving a modelled push in the caller. ret reads rsp, loads the return slot, adds 8 plus any immediate, and terminates with return. The loaded target is deliberately unused: representing it as a guessed intra-function edge would invent control flow. A discovered tail call emits call without the push and then return; an ARM branch to an external tail-call exit reads the clobbered registers and stack pointer so a bounded callee observer can see untouched argument cells.

Conditional branches

ARM conditional transfers compute an i1 from explicit state. CBZ/CBNZ compare Rt with zero; TBZ/TBNZ extract a bit from Rt; B.cond decodes NZCV. The condition decoder reads nzcv, extracts N/Z/C/V, and selects a predicate from cond >> 1: Z, C, N, V for 0..3, then C && !Z, N == V, N == V && !Z for 4..6, with inverted forms for the odd codes and constant true for code 7. CSEL uses the same predicate.

x86 conditional jumps map the mnemonic suffix to a predicate over the six flag slices (e/z → ZF, ne/nz → !ZF, b/c/nae → CF, l/nge → SF xor OF, and so on). jrcxz/jecxz/jcxz compare RCX/ECX/CX with zero; loop* decrements the address-width RCX and ANDs the loop condition with ZF/!ZF for loope/loopne. The driver builds both edges explicitly; there is no implicit fall-through in IR.

Unsupported instructions and boundaries

Semantics methods signal “I do not model this” by throwing Unsupported. The drivers turn that into an unknown_effect carrying unknownClobbers — for ARM64 all general, vector and control registers plus NZCV/FPSR and memory; for x86 all GPRs, 32 zmm roots, MXCSR, six flags and memory — plus an unavailable_semantics diagnostic (with the instruction address on ARM64) and a coverage reason. Coverage becomes partial; the graph is still valid. ARM then terminates the block with unknown only when the instruction's decoded flow is not a fallthrough or call; x86 terminates immediately. Nothing is silently dropped and nothing is turned into an invented trap: an unknown_effect is a real node, not a no-op.

Provenance and jump tables

Every node produced for an instruction inherits that instruction's provenance, including its byte range. Block and function provenance are the ordered union of their members. The real dump below shows prov_ranges = 588+4 on the nodes from 0x100000588, 58c+4 on those from 0x10000058c, and 590+4 on the return nodes.

When discovery proves a jump table, the driver records the selector just before the selecting load, and at the indirect branch emits a switch with exactly the proven targets, the guard's out-of-range target as otherwise, and a jump_table origin. It requires the selector and branch to be in the same block and every target to be a discovered block; otherwise the branch remains indirect. The otherwise edge is present even when the guard is exact.

Invariant

A lifter never invents an architectural trap from missing semantics, and never drops an instruction. Unsupported means unknown_effect + coverage reason; malformed graph input means unknown/synthetic boundary; a trap terminator is emitted only for an instruction whose decoded flow is a trap, or for a call that discovery proved noreturn.

Dominance and derived register state

Dominance is needed for two things: the verifier must decide whether a cross-block value reference is legal, and SSA construction needs immediate dominators and a dominator tree. The implementation is in computeDominance. It works on every block, including unreachable components, because the IR must stay valid even when the graph is not reducible or when a component has no path from the entry.

  1. Build edges. Successors come from successors(terminator); predecessors are accumulated per block. Edges to missing targets are ignored here — the verifier reports them separately — which keeps the algorithm total on malformed graphs.
  2. Iterative DFS, shared postorder. Start at the entry, then start a new root at every still-unvisited block in block order. Each root is recorded. The DFS is iterative and assigns postorder numbers shared by all components; the virtual root receives the largest number.
  3. Initialize the virtual root. A virtual node precedes all roots. Every root's immediate dominator is the virtual node, so no block in one component dominates a block in another.
  4. Intersect predecessors to a fixpoint. Process blocks in reverse postorder. For a non-root block, take the first processed predecessor with a known idom as a candidate, then intersect each further predecessor by walking both idom chains upward while their postorder numbers differ. Repeat the sweep until no idom changes.
  5. Compress queries. Build the dominator tree's child lists and number each node on entry and exit. dominates(a, b) is then the interval test enter[a] <= enter[b] && leave[b] <= leave[a]; idom returns null for roots and unknown blocks.

This is essentially the iterative dominance algorithm popularised by Cooper, Harvey and Kennedy: reverse-postorder sweeps with the postorder-number intersection over predecessors. It is not Lengauer–Tarjan, and the code does not claim a linear-time bound.

Derived register state

SSA rows are intentionally sparse. registerStateAt(rows, block, cell, boundary) walks from the requested block up the immediate-dominator chain, looking for a row that binds exactly the requested root/offset_bits/width_bits cell. For an exit query it checks the block's exit row and then its entry row; for an entry query it checks the entry row. If the cell is not listed, it moves to the idom and considers that block's exit state, and so on. Returning null means no row on the chain binds the cell. This is why unlisted cells can “inherit the immediate dominator's exit” without materializing a full state vector per block.

Reference semantics and the interpreter

src/ir/semantics.ts is the single reference evaluator for IR expressions. It is a pure function of a type, an expression and a lookup for operand values; it never touches memory or registers itself. That makes it usable for constant folding, not just for tests.

The interpreter's execution model

  1. Verify first. evaluateIR calls assertValidIR; it will not execute an unverified graph.
  2. Initialize roots. Unsupplied register roots read as unknown (the test helpers zero-initialize them). A supplied root that the IR never uses is a TypeError, which catches typos. Each root holds {bits, known, undefined, width}, so partial knowledge and undefined slices are distinct from uninitialized ones.
  3. Enter the entry block. Parameters whose entry row binds a register read that register; remaining parameters consume options.arguments; arity must match exactly.
  4. Execute instructions. Pure assigns evaluate; register reads/writes update root state according to write_rule; loads/stores go through OracleMemory; calls use the trusted oracle and then invalidate declared clobbers; unknown effects stop.
  5. Apply SSA state rows. register_inputs are written before any instruction that carries them; register_outputs are read after a boundary; exit rows write rebound cells before the terminator.
  6. Choose an edge. A branch observes the condition; a switch observes the selector; a jump is direct. Edge arguments are evaluated simultaneously and become the next block's parameters. Return/trap/unknown/indirect stop with a status.

The result is a EvaluationResult with a status (returned, trap, unknown, undefined, memory_fault or step_limit), the returned values, the stopping node, the step count, a register snapshot, a memory snapshot and an effect trace. The step limit defaults to 100_000 and may be set from 1 to 1_000_000.

Trusted calls are deliberately narrow. Inputs are the target, arguments and callbacks to read memory/registers; outputs are results, memory writes and register writes. Memory writes are rejected unless the call declares unknown_read_write; register writes must fall inside the declared clobber mask and obey the descriptor rules. Writes are applied after clobbers are invalidated, so a callee can overwrite a clobbered slice without the invalidation erasing it.

Not a hardware emulator

OracleMemoryFault is an oracle fault, not a proven ISA trap. The interpreter does not model concurrency, signals, precise fault delivery, the OS, or the real FP exception environment. A memory_fault status says “the fixture memory model rejected this access”, which is why tests treat it as a test outcome rather than an architectural conclusion.

Budgets and refusal points

Every layer charges the same cumulative work counter and checks cancellation and the deadline. On top of that, the IR has its own node and block capacity, because a small instruction can expand into dozens of nodes: the real cmp above expands to 22 IR nodes, six of them flag writes. Defaults come from DEFAULT_BUDGET:

export class IRConstructionBudget {
  #nodes = 0;
  #blocks = 0;
  constructor(readonly limits: IRConstructionLimits = {}) {
    for (const limit of [limits.max_ir_nodes, limits.max_blocks]) {
      if (limit !== undefined && (!Number.isSafeInteger(limit) || limit < 0))
        throw new RangeError('IR construction limits must be nonnegative safe integers');
    }
  }
  block(parameters: number): void {
    this.limits.checkpoint?.(0);
    const blocks = this.#blocks + 1;
    if (blocks > (this.limits.max_blocks ?? Infinity))
      this.#exceeded('blocks', this.limits.max_blocks!, blocks);
    // Reserve the block, effect parameter and eventual terminator before allocation.
    this.nodes(3 + parameters);
    this.#blocks = blocks;
  }
  nodes(count = 1): void {
    this.limits.checkpoint?.(count);
    const nodes = this.#nodes + count;
    if (nodes > (this.limits.max_ir_nodes ?? Infinity))
      this.#exceeded('ir_nodes', this.limits.max_ir_nodes!, nodes);
    this.#nodes = nodes;
  }
}

The builder reserves three nodes per block (the block's own allocation, its effect parameter and its terminator) plus one per parameter, before any instruction is emitted. That is why an empty block still has a nonzero cost. #exceeded throws OperationError with code resource_limit and details: { kind: 'limit', resource, limit, consumed }; the partially built block remains structurally usable (the test suite deliberately terminates it and verifies the result), because the failed operation did not mutate the chain.

After lifting, analysis calls boundIR, which charges 3 + parameters + instructions per block and re-checks ir_nodes/blocks before assertValidIR. This catches expansions that a lifter's preflight only estimated. The verifier and dominance computation also charge work per node, so a large but within-capacity graph still consumes the shared clock and can be cancelled.

Why reserve before allocate

The budget is checked before the node is appended, so an over-budget operation cannot leave a half-linked effect chain or a block with an uncharged instruction. The builder's sequence counter is advanced only by successful identities; the failed call throws before mutating #instructions.

Limitations & extension points

Known gaps visible in the code

Area Gap
ARM64 decode A pinned a64js snapshot plus one field-based logical completion. Instructions the snapshot does not recognise are invalid even if a newer Arm XML knows them. Opaque operands are preserved but cannot be lifted.
ARM64 lift SVE/SME scalable state, atomics, barriers other than DMB ISH, privileged/system state, fused FP, FP16, saturating/rounding conversions and unimplemented SIMD become unknown-effect boundaries. Pointer authentication is abstracted to logical pointers: PAC bits, key/modifier checks, failure poisoning and authentication traps are not modelled. FP arithmetic requires an FPCR environment with nearest-even, gradual underflow and masked traps; otherwise an explicit unknown exit is taken. Arithmetic NaNs are canonicalized and FPSR status is explicitly unknown.
x86-64 decode Bounded 64 KiB decode windows; an instruction crossing a window with non-contiguous backing can still be decoded by lookahead, but regions with no static VA are holes. Invalid encodings are facts, not traps.
x86-64 lift x87/MMX, string/REP operations, LOCK/atomic memory, RCL/RCR, SHLD/SHRD, bit-test/scan/BMI/ADX, saturating/shuffle/conversion SIMD, AVX and later encodings, crypto, privileged/transactional instructions and CET enforcement are unsupported. VEX/EVEX/XOP/MVEX and masked/rounding instructions are rejected even though the decoder can describe them. FP requires MXCSR[6:16] = 0x7e; otherwise an unknown exit. MXCSR exception status is abstracted, and precise fault delivery is not modelled.
IR Integers are signless; shifts are not auto-masked; division by zero is undefined rather than a trap; FP is FP32/64 only with no ambient exception state; vectors are fixed-lane and at most 2048 bits; effect tokens are block-local and model ordering, not a concurrent memory model; memory_fence has exactly one supported meaning.
Interpreter A test oracle only: bounded owned memory, no native calls, no OS, no signals, no precise faults, no real FP environment, explicit trusted-call oracles keyed by node ID.

Adding a new instruction

  1. Make the decoder describe it. For ARM64, ensure the canonical encoding, fields and structured operands exist (add a completion only if the fields are sufficient and the table is genuinely missing). For x86-64, the iced payload already carries operands, memory, flags and prefixes; do not add a text parser.
  2. Add semantics, not metadata cases. ARM64: add a branch in ArmSemantics.execute (or memory/simd) keyed by canonical_encoding and fields. x86-64: add a mnemonic branch in X86Semantics.execute, using read/write/address/flag/condition/resize. Throw Unsupported for forms you do not model; never fall through to a guess.
  3. Model faults explicitly. Use X86Semantics.guard for an architectural fault path (it creates a trap or unknown block and passes live values as parameters). Use fpEnvironment/fpStatus for FP environment and status effects.
  4. Test at both levels. A decoder test asserts fields, widths, operands and flow; a lifter test builds real bytes with fromWords (ARM) or liftBytes (x86), lifts, verifies, evaluates with evaluateIR, and checks a register/memory result. Corpus tests then check that no previously supported function regressed.
  5. Expect partial coverage to be visible. If the instruction is recognized but not lifted, it must produce an unknown_effect, an unavailable_semantics diagnostic and a coverage reason — never a silent skip.

Adding a new architecture lifter

  1. Implement Decoder. Produce structured payloads, neutral RegisterDescriptors, DecodedFlow and typed gaps. Do not import decoder-library objects into core; convert at the boundary. Respect the instruction budget and charge work.
  2. Implement Lifter<RegisterIR>. Consume FunctionGraph boundaries rather than rediscovering them; create one block per discovered block with stable birth keys; emit explicit register and memory operations; use unknown_effect for gaps; return coverage and diagnostics.
  3. Supply an AbiProfile. Define the stack pointer, link register (if any), preserved registers, return-address size, red zone, unknown-call clobbers and classifyCall. Calls carry physical clobbers, not invented source signatures.
  4. Register the components and versions. Add the loader/lifter/ABI triple to components, extend targetPipeline, and add a version record whose analysis string is bumped when any downstream pass changes; the emitter versions are part of the same cache identity.
  5. Add corpus and bounds tests. The lifter must be deterministic, respect tiny budgets and cancellation, retain every instruction's provenance, and verify its own output through IRBuilder.finish.

The invariant to preserve across all of this is the separation of concerns: decoding states facts about bytes, lifting states their semantics, verification proves the graph, and SSA construction changes the representation. A change that violates that split (for example a lifter that builds SSA, or a decoder that guesses a trap) breaks the audit trail that the rest of the decompiler depends on.
