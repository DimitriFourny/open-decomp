Loading binaries and addresses

A loader turns an immutable container plus a selected slice into the static address space and native facts every later stage shares: mappings, sections, entry points, symbols, imports, exports, relocations and hints. It never decodes an instruction and never executes the target.

Where this sits in the pipeline

The import worker reads an authorized source file in 1 MiB chunks, refuses anything larger than 512 MiB, hashes the exact bytes with SHA-256 and wraps them in an ImmutableBytes. The content hash mints the image ID (imageIdentity), so two imports of identical bytes name the same image even in different projects. The worker then chooses a loader from the first bytes: MZ selects peLoader, \x7fELF selects elfLoader, and anything else is handed to a fresh MachOLoader, which diagnoses an unknown magic rather than silently accepting it. src/workers/runtime.ts (the work.request.kind === 'import' branch, loader selection).

The output is deliberately a snapshot of binary facts, not an analysis result. The loader has not decided where functions start (beyond explicit entry points and hints), has not decoded bytes, and has not resolved a single import at runtime. Those decisions belong to function discovery and CFG construction, which seeds itself from the arrays this stage returns. Keeping the split sharp means every later fact can cite a file range and a loader record.

Loader contract and slice selection

Every format implements the same small interface. inspect must be cheap enough to enumerate containers and report why a slice is unsupported; load performs the full parse for one slice and returns a LoadedImage. Both receive the caller's OperationContext, whose checkpoint(work) charges work against the operation budget and throws on cancellation or exhaustion. 

export interface Loader extends ComponentIdentity {
  readonly format: Target['format'];
  inspect(
    bytes: ImmutableBytes,
    imageId: string,
    context: OperationContext,
  ): { readonly slices: readonly ImageSlice[]; readonly diagnostics: readonly Diagnostic[] };
  /** A missing selection is valid only if exactly one supported slice exists. */
  load(
    input: {
      readonly image_id: string;
      readonly sha256: string;
      readonly bytes: ImmutableBytes;
      readonly slice_id: string | null;
    },
    context: OperationContext,
  ): LoadedImage;
}

Defined in src/core/contracts.ts (Loader). The contract comment on the missing-selection case is load-bearing.

Slice identity

A slice ID is not a position in an array. sliceIdentity(imageId, offset, size, architecture) hashes the canonical, type-tagged tuple [imageId, formatHexU64(offset), formatHexU64(size), architecture]; the canonical encoding tags bigints so a numeric 1 cannot collide with the string "0x1". The image ID itself is image_<sha256>. Consequently the same fat container yields one image ID and several slice IDs, while a thin copy of one architecture has a different image ID because the container bytes differ. src/core/identity.ts (imageIdentity, sliceIdentity, canonicalIdentity).

How selection fails

  1. Explicit ID, unknown slice. Mach-O raises not_found; PE and ELF raise invalid_input when the ID does not equal their single slice ID. src/loaders/macho/index.ts (load), src/loaders/pe/loader.ts (PELoader.load), src/loaders/elf/loader.ts (ELFLoader.load).
  2. Explicit ID, unsupported slice. Mach-O throws unsupported_target naming the architecture and subtype. PE and ELF throw unsupported_target with the reason recorded by inspect.
  3. No ID, several supported slices. Mach-O throws ambiguous_slice and attaches details.kind = "slice_selection" with every slice's ID, architecture, subtype and support flag. The CLI's --slice value is validated against sliceIdSchema before it reaches the loader. src/cli/commands.ts (--slice).
  4. No ID, no supported slice. Mach-O throws unsupported_target (No supported little-endian ARM64 executable/dylib slice). PE and ELF throw the diagnostic text produced by inspect.
Invariant

load never silently picks one of several supported slices. The first supported slice is used only when it is the only one, so adding a second architecture to a fat binary cannot change which code is analyzed by accident.

The LoadedImage data model

LoadedImage is a plain immutable record. It contains the whole container bytes, not a copy of the selected slice, because file-space addresses are container-global; the selected slice is identified separately and every mapping records where its bytes live inside the container. 

export interface LoadedImage {
  readonly id: string;
  readonly sha256: string;
  readonly bytes: ImmutableBytes;
  readonly selected_slice_id: string;
  readonly slices: readonly ImageSlice[];
  readonly target: Target;
  readonly image_base: bigint;
  readonly address_map: AddressMap;
  readonly mappings: readonly ImageMapping[];
  readonly headers: readonly HeaderRecord[];
  readonly sections: readonly Section[];
  readonly entry_points: readonly Address[];
  readonly symbols: readonly SymbolRecord[];
  readonly imports: readonly ImportRecord[];
  readonly exports: readonly ExportRecord[];
  readonly relocations: readonly Relocation[];
  readonly hints: readonly LoaderHint[];
  readonly evidence: readonly Evidence[];
  readonly diagnostics: readonly Diagnostic[];
  readonly capabilities: readonly z.infer<typeof capabilitySchema>[];
}

Defined in src/core/model.ts (LoadedImage); the Zod schemas above it are strict objects, so no record can carry an undeclared field.

What the collections mean

mappings / address_map
The authoritative VA-to-file backing. Sections are metadata and never a second overlapping mapping set. AddressMap is constructed from these mappings once and validates them; see addresses.
sections
Segments and sections, each with a virtual range, an optional file range, permissions and evidence. Mach-O stores segments and sections; PE and ELF store sections (ELF also stores PT_LOAD pseudo-sections named PT_LOAD[n]).
entry_points
Addresses proven to be executable file-backed memory: the native entry point, Mach-O LC_UNIXTHREAD PC when present, and PE TLS callbacks.
symbols, imports, exports
Native name facts. original_name is immutable linkage text; display_name may later receive a demangled label. An import has a slot (storage address of the pointer) or a callable_entry (a stub known to forward to the import), never an assertion that the slot contains a resolved value.
relocations
kind is one of relocation, rebase, bind or chained_fixup; width_bits, target, symbol_id, signed addend and authenticated preserve the native encoding without applying it.
hints
Format evidence that is not a claim of an analyzed function: function starts, unwind regions, and data ownership. Discovery turns them into seeds or data ranges rather than trusting them as complete function tables.
evidence, diagnostics, capabilities
Provenance and honesty about coverage. Every assertion record (header, section, symbol, import, export, relocation or hint) names one or more evidence IDs whose origin is a file range plus a claim; mappings and slices are validated structural facts rather than textual claims. Diagnostics record refused or degraded metadata; a capability says whether a layer is supported, partial or unsupported.
Hint kind Payload What downstream does with it
function address, optional size Discovery seeds the address as established with that name and range.
unwind range, encoding, record, optional handler Kept as unwind metadata; discovery seeds only the range start as a candidate, because coalesced unwind ranges can cover several functions.
data range, encoding (bytes, jump_table, literal_pool, unknown) Creates data ownership and, for jump_table, candidate jump-table ranges so code bytes are not swept into functions.

Identity and evidence invariants

Entity IDs are derived from [sliceId, kind, birth], where birth is a table index, file offset or name. Splits and merges mint new IDs and record lineage; they never rename an existing ID. Every loader-created evidence record is deduplicated by fingerprint of [sliceId, offset, size, claim], so repeated reads of one table share a proof instead of inflating the store. src/core/identity.ts (entityIdentity), src/loaders/macho/state.ts (State.proof).

Addresses, mappings and translation

The address model is the part of the loader interface other stages depend on most. An Address is never a bare bigint: it carries the image it belongs to and the space it is interpreted in. That makes accidental cross-image arithmetic a typed error rather than a wrong answer. 

export interface Address {
  readonly image_id: string;
  readonly space: 'va' | 'rva' | 'file';
  readonly value: bigint;
}
export interface AddressRange {
  readonly start: Address;
  readonly size: bigint;
}
export type Translation =
  | { readonly kind: 'mapped'; readonly address: Address; readonly mapping_id: string | null }
  | { readonly kind: 'zero_fill'; readonly address: Address; readonly mapping_id: string }
  | { readonly kind: 'unmapped'; readonly address: Address };

file always addresses the original immutable container, including the selected slice's offset. rva is relative to the explicit image_base. va is the static virtual address from the image's own load commands or program headers. No runtime slide is applied or guessed: a PIE ELF and an ASLR-enabled PE are analyzed at their linked or preferred addresses. src/core/addresses.ts (Address, ImageMapping, MappingContext).

Checked arithmetic and checked bytes

U64_LIMIT is 1n << 64n. checkedU64 rejects negative values and values at or above the limit. checkedEnd(start, size) additionally rejects a range whose exclusive end would exceed 2^64, so a half-open range may end exactly at 2^64 but neither its start nor its size may exceed unsigned 64-bit representation. checkedIndex converts a bigint index to a safe JS number only after proving it lies within a bounded buffer. src/core/addresses.ts (checkedU64, checkedEnd, checkedIndex).

ImmutableBytes makes one owned copy on construction and keeps both the buffer and its DataView private. at, u32 and u64 bounds-check before reading; read(offset, length) returns a copy. No mutable view escapes, so a loader cannot accidentally hand later stages bytes that something else can rewrite.

AddressMap construction

The map is built after the format has produced its mappings and is validated once. Construction rejects ambiguous or impossible backing instead of resolving conflicts by array order:

  • the slice must lie inside the container, and the container length and image base must be valid u64 values;
  • mapping IDs must be unique;
  • each mapping's VA range and file range must not overflow 64 bits;
  • file_size must not exceed memory_size, and the file range must lie inside the selected slice;
  • after filtering zero-length ranges, VA mappings and file mappings must each be non-overlapping.

src/core/addresses.ts (AddressMap constructor). This is the enforcement point behind the ownership rules in docs/CORE.md; the code is authoritative where the prose is vague.

translate

  1. Identity check. The source address must name this map's image; otherwise a RangeError is thrown. The source value is checked as u64.
  2. File source. Outside [slice_offset, slice_offset + slice_size) the result is unmapped. File-to-file is mapped with no mapping ID, because container bytes inside the slice are readable even when no mapping backs them.
  3. File to VA/RVA. Find a mapping whose file range contains the offset. If none exists, the result is unmapped; otherwise the VA is mapping.va + offset - mapping.file_offset, and RVA subtracts image_base.
  4. VA/RVA source. Convert RVA to VA by adding the checked image base, then find a mapping whose memory range contains the VA. No mapping means unmapped.
  5. Zero-fill. If the offset within the mapping is at or beyond file_size, there is no file byte. The result is zero_fill; when a file address was requested the returned address deliberately keeps the VA coordinate rather than inventing an offset.

spans

Reads cannot assume one mapping. spans(source, size) partitions the requested range into consecutive mapped, zero_fill and unmapped spans and reports the file offset for each backed span. It never shortens the request silently. For a VA source it walks memory mappings and cuts at the next mapping boundary; for a file source it cuts at slice boundaries and reports holes as unmapped. Consumers that need bytes use the file offsets; consumers that need memory semantics can see exactly where zero-fill begins. src/core/addresses.ts (spans).

Where image_base comes from

Mach-O requires exactly one segment whose file offset is zero and whose file size covers the header and load commands; that segment's vmaddr is the base. PE uses the optional header's ImageBase. ELF uses the lowest PT_LOAD virtual address, which is usually zero for a PIE and 0x400000 for a conventional executable. In all three cases the value is a static linking fact, not a runtime observation. src/loaders/macho/index.ts (parseImage base selection), src/loaders/pe/loader.ts (parseHeaders), src/loaders/elf/loader.ts (parseSegments).

Half-open ranges, not inclusive ends

A mapping's file_size may be zero (pure zero-fill). Its memory_size may be larger. Consumers must test start <= value < start + size and must not treat a mapping as contiguous file bytes merely because its VA range is contiguous; use spans for reads.

Reading Mach-O, PE and ELF

All three loaders follow the same shape: identify and bound the container, create mappings, construct the AddressMap, then read names, fixups and hints. The differences are in which tables exist and how much can be optional. Figure 4 is the map of the three flows; the subsections explain the order and the checks.

Mach-O

  1. Container inspection. inspect reads the magic big-endian to distinguish thin Mach-O from FAT32/FAT64 in both byte orders, rejects containers over 128 MiB, requires 1 to 1,024 architecture entries, checks each entry's offset, size, alignment (power of two, shift at most 63), reserved FAT64 field and non-overlap, and verifies that the architecture table agrees with the slice's own cputype/cpusubtype. src/loaders/macho/index.ts (inspect, add).
  2. Slice selection and state. load re-runs inspect, selects the requested or unique supported slice, and creates a Reader whose base is the slice offset. Every subsequent r.u32/u64/string/range is relative to that base, while State.file adds the slice offset to produce container coordinates.
  3. Header and load-command loop. parseImage reads ncmds/sizeofcmds, bounds the command table, rejects counts above 65,536, and walks 8-byte-aligned commands. Duplicate occurrences of the structural commands (symtab, dysymtab, dyld info, main, function starts, data-in-code, exports trie, chained fixups) are malformed. Every command is retained as a load_command header record: up to 3,800 bytes of fields are decoded as 32-bit words; larger payloads are retained as a file range. Unknown commands produce an unsupported_target warning, not a guess.
  4. Segments, sections and mappings. LC_SEGMENT_64 must have size 72 + 80 * nsects, a valid VM range, file backing inside the slice, and file_size <= memory_size. Sections must name their segment, lie inside it, and agree on file-to-VM displacement; zero-fill section types (1, 0xc, 0x12) get no file range. Relocation tables and ARM64 instruction alignment are checked. Mappings are then split only where a zero-fill section overrides file backing: 
    // Segment mappings are split only where a declared zero-fill section overrides file backing.
// Sections remain metadata, never a second overlapping set of maps.
const boundaries = [va, ...zeroRanges.flatMap((range) => [range.start, range.end]), va + memorySize];
// …
file_offset: s.slice.offset + BigInt(offset) + (backing ? delta : 0n),
file_size: backing,
    Note the s.slice.offset term: a fat slice's mappings point at real container bytes, not at slice-relative offsets. LC_ENCRYPTION_INFO(_64) ranges are also recorded: encrypted bytes are excluded from optional metadata through State.readable, retained as encoding: unknown data hints, and diagnosed rather than decoded.
  5. Structural ownership and base. The header and load-command bytes become a file-space data hint, even inside an executable segment. Exactly one segment with fileoff == 0 and filesize >= commandEnd must exist; its vmaddr is the image base. Section overlaps are rejected independently of mappings, then AddressMap validates the result. Entry offsets from LC_MAIN are translated to VA and must be executable, file-backed memory. LC_UNIXTHREAD flavor 6 with 68 words supplies the PC at offset 256; other thread flavors produce an unsupported-target warning.
  6. LC_SYMTAB and LC_DYSYMTAB. Each nlist_64 carries a string index, type, section ordinal, description and value. STAB entries (type & 0xe0) are excluded from the symbol list. A definition's kind is only inherited from its section when the value lies inside that section; otherwise it is unknown, because linkers also associate header symbols with instruction sections. Weak binding comes from n_desc & 0xc0; external versus local from type & 1. The indirect symbol table is interpreted through sections of type 6, 7, 8 and 0x14: pointer sections yield an import slot, stub sections yield a callable_entry, lazy symbol pointers set delayed.
  7. Exports, then dyld data. The export trie is walked iteratively with an active-offset set, terminal size bounds, child-name bounds and an 8,192-byte name cap. Forwarders are resolved through the dylib ordinal; resolver exports add a function hint. A symbol-table export and a trie export with the same name/address/forwarder are merged by parseImage. readDyld then interprets the legacy rebase/bind/weak-bind/lazy-bind opcode streams into Relocation records and ImportRecords. Repeated fixups are charged against the work budget; conflicting signatures at one VA emit conflicting_evidence unless the conflict is a lazy bind after a rebase or a weak bind. Chained fixups are decoded from the starts/imports/name pools: import formats 1, 2 and 3, pointer formats 1, 2, 6, 9 and 12, 4 KiB or 16 KiB pages, per-page next-delta chains, bind/rebase/auth bits, and multi-start overflow entries. Cycles, repeated slots, reserved bits and out-of-page chains are malformed. src/loaders/macho/metadata.ts (readExports), src/loaders/macho/dyld.ts (readDyld).
  8. Function starts and data in code. LC_FUNCTION_STARTS is a LEB delta chain from the image base; every delta must land in an instruction section and the chain must end in a zero terminator. LC_DATA_IN_CODE marks jump tables, byte data and unknown regions after proving contiguous file backing. src/loaders/macho/metadata.ts (readHints).
  9. Unwind metadata. __compact_unwind is parsed as fixed 32-byte records; a personality slot's relocation supplies the handler when present. __unwind_info is version-checked, requires a sentinel index, supports page kinds 2 and 3 with common/local encodings, and validates LSDA ranges and ordered function ranges. __eh_frame is framed length-by-length and retained as debug records, but PC ranges are not invented from undecoded augmentation encodings; an unavailable_semantics warning says so.
  10. Relocations and capabilities. readRelocations handles section relocation tables plus LC_DYSYMTAB external/local tables. Scattered relocations are warned as unsupported; external symbols must exist; section ordinals must be in range; ARM64 type 10 carries a signed 24-bit addend; type 11 sets authenticated. Capabilities report the Mach-O format as partial if any diagnostic was produced, and separately report native symbol/export tables through NATIVE_SYMBOL_TABLES_FEATURE.
Optional Mach-O metadata can degrade without failing the image

Symbols/indirect imports, exports, dyld streams, function starts, data-in-code, compact unwind, CFI and relocation tables run through State.optional. A MachOError from those sections becomes a warning and a partial capability; cancellation and resource-limit errors are rethrown. Structural errors in headers, segments, mappings or the entry point abort the load with malformed_image. src/loaders/macho/state.ts (optional).

PE

  1. DOS and PE headers. basic() requires MZ, a e_lfanew at or beyond the 64-byte DOS header, and a PE\0\0 signature. parseHeaders accepts only Machine 0x8664 with optional magic 0x20b, a native user-mode image (characteristic 0x2 set, 0x1000 clear) and subsystem 2 or 3. A CLR directory (index 14) is refused because native bodies are not meaningful there. src/loaders/pe/loader.ts (Reader.basic, Parser.parseHeaders).
  2. Image geometry and sections. The loader checks power-of-two section and file alignment, the 4 KiB/512-byte alignment rules, 64 KiB image-base alignment, a nonzero aligned SizeOfImage, and a SizeOfHeaders that contains the section table. The headers themselves get a read-only mapping. Each section maps memory_size = max(VirtualSize, SizeOfRawData) bytes with file_size = SizeOfRawData; raw alignment padding is therefore backed, while a larger virtual size becomes zero-fill. Section permissions come from the read/write/execute characteristic bits.
  3. Data directories. Each directory is bounds-checked and retained as a data_directory header record. Index 4 (certificate) is a file offset; the others are RVAs and must be file-backed for their whole body. Directories the loader does not interpret are kept as raw data hints plus an unsupported capability. The recognized set is export (0), import (1), exception (3), base relocation (5), debug (6), TLS (9), IAT (12), delay import (13) and CLR (14, refused).
  4. Imports and delay imports. Normal descriptors use 20-byte strides and delay descriptors 32-byte strides; both must end in an all-zero descriptor. The loader resolves the DLL name, the lookup table and the IAT, walks 64-bit thunks until zero, and decodes either an ordinal import (bit 63 set, low 16 bits) or a name import (RVA to a hint/name record). The resulting ImportRecord has slot = base + IAT RVA + index * 8 and callable_entry = null. Delay imports set delayed; unknown descriptor attributes or a bound import without a usable lookup table are refused.
  5. Exports. The export directory yields the export address table, name pointer table and ordinal table. Names are grouped by EAT index so several aliases can share one ordinal. A nonempty EAT entry is either a forwarder (its RVA points inside the export directory; library.symbol or library.#ordinal) or a VA proven to be in mapped memory. Empty slots are skipped; a name pointing at an empty slot is malformed.
  6. Base relocations. Blocks are walked with a 4 KiB-aligned page RVA and a block size that is a multiple of four. Only IMAGE_REL_BASED_DIR64 (type 10) is recorded as a rebase fact whose target is the 64-bit value currently stored at the site; other types are retained as raw references and marked unsupported, with HIGHADJ consuming its extra slot. The loader does not add a delta to targets; it records what the file says.
  7. Exceptions and unwind. The .pdata directory is a table of 12-byte runtime-function entries. Ranges must be nonempty, sorted and non-overlapping; each becomes a function hint with an exact size. Each UNWIND_INFO chain is followed up to 64 records, validates version 1, code slots and prolog ordering, records the optional language handler, and stops at a chained entry. Unsupported versions or opcodes degrade to a capability rather than inventing unwind semantics.
  8. TLS, debug and COFF symbols. The TLS directory contributes its template as a data hint, its index address, and each callback as both an entry point and a function hint (bounded to 1,000 entries). Debug records expose CodeView RSDS GUID bytes, age and PDB path, or NB10 offset/timestamp/age, without opening the PDB. The COFF symbol table is read in 18-byte records with auxiliary records skipped; long names come from the COFF string table, and long section names (/nnn) are resolved from the same table.

ELF

  1. Identification. The loader requires \x7fELF, class 2 (ELF64), little-endian data, identification version 1, EM_X86_64, type ET_EXEC or ET_DYN, and OSABI 0 or 3. Extended table counts or indexes and sectionless images are refused as outside the supported subset; program and section tables must not overlap. src/loaders/elf/reader.ts (identification, basic).
  2. PT_LOAD to mappings. Only PT_LOAD creates mappings. Each requires p_filesz <= p_memsz and, when alignment exceeds one, congruent virtual and file offsets modulo that alignment. Permissions come from p_flags. PT_DYNAMIC is remembered for later cross-checking; note, GNU property and interpreter segments are retained as native metadata, while TLS is diagnosed as unsupported. After all segments are read, mappings are sorted and the base is the lowest VA, then AddressMap validates uniqueness.
  3. Sections. The null section must be all zero. Other sections need power-of-two alignment, an in-range sh_link, and either file bounds or SHT_NOBITS. String tables must start and end with NUL. Allocated sections must lie in a PT_LOAD, agree on file offset versus VA, follow their segment's permissions, and not overlap other allocated sections. File-backed sections must not overlap other file-backed sections. Non-allocated sections keep file-space ranges.
  4. Symbol tables. SHT_SYMTAB and SHT_DYNSYM entries are 24 bytes and linked to a string table. The first entry must be null. A defined symbol with a section index must fit inside that section's VA range; SHN_ABS is absolute; SHN_XINDEX, TLS symbols and IFUNC resolvers are explicitly unsupported. Dynamic exports come only from SHT_DYNSYM, with global/weak/GNU-unique binding and default or protected visibility.
  5. Dynamic table and versions. PT_DYNAMIC must match a single SHT_DYNAMIC in offset, size and VA. Records must end with DT_NULL; non-null records after it, duplicate singleton tags, and pointer/size/stride contradictions with section evidence are malformed. DT_STRTAB/DT_STRSZ must match the linked string section. DT_SYMTAB, DT_RELA, DT_REL and the PLT relocation table are each matched to exactly one section with the declared size and entry stride. GNU version-need and version-symbol sections are validated record by record, and a version index must have a provider.
  6. Relocations to imports. SHT_RELA and SHT_REL entries name a symbol table; the symbol index must exist. Relative relocations must use symbol index zero, while COPY, GLOB_DAT and JUMP_SLOT relocations must name a symbol. Known x86-64 encodings are mapped to a width; unknown types are retained as native bytes with an unsupported diagnostic. The addend is explicit for RELA, otherwise read from the relocation site (zero for zero-fill). A target is recorded only when it resolves to mapped memory. An undefined dynamic symbol that a GLOB_DAT, JUMP_SLOT or zero-addend absolute relocation binds becomes an import with a slot only when the site is outside executable sections; a relocation that may patch an instruction immediate cannot prove a pointer slot and yields an import without a slot. Undefined dynamic symbols with no such relocation are still imported, with slot: null.
  7. Entry point and capabilities. e_entry must be backed executable memory. The format capability is supported; specialized omissions (PLT callable entries, TLS execution, RELR, Android packed relocations, COPY ownership, IRELATIVE, IFUNC, compressed tables) are reported as separate unsupported capabilities and diagnostics.
ELF import slots are relocation-evidenced, not PLT-reconstructed

The loader records the GOT slot named by a JUMP_SLOT or GLOB_DAT relocation, or an undefined symbol with no slot. It does not build PLT callable entries or model lazy-binding execution; executable PLT bytes remain code discovered by the next stage, not an import fact. src/loaders/elf/loader.ts (parseRelocations).

Binding imports to stubs, GOT and IAT

An import is useful to discovery only when its name is connected to a storage location or a callable entry. The loader records that connection explicitly and refuses to infer it from pointer-looking bytes.

slot
The VA of the pointer cell the native loader would fill: a Mach-O GOT/lazy-pointer entry, a PE IAT entry, or an ELF GOT/PLT relocation site. The bytes currently at the slot may be zero, unbound or a chained-fixup encoding; the loader does not dereference or execute them.
callable_entry
A code address proven to forward to the import: a Mach-O stub section entry. PE and ELF do not supply one in this implementation, so their import thunks or PLT entries remain ordinary code unless later analysis classifies them.

What downstream actually consumes

Discovery's seed loop turns image entry points, function/unknown symbols, non-forwarder exports and import callable_entry values into established entries. It turns function hints into established seeds with optional exact ranges, unwind hints into candidate starts, and data hints into protected data ranges (jump-table hints additionally become candidate tables). Symbol objects with an address also contribute data ranges. src/analysis/discovery/index.ts (discoverFunctions).

Reference building marks a memory access through an import slot with the role import_slot. classifyImportStubs then accepts a function as a stub only when its body is at most four instructions, ends in an indirect branch, contains only inert address/materialization instructions before it, and has exactly one established branch reference to the import entity. The import must have a slot, must not be weak, must have a name, and any callable_entry must equal the function entry. That is why the slot fact has to be precise: a guessed pointer would create a false stub and a false name. src/analysis/discovery/stubs.ts (classifyImportStubs).

Mach-O imports are not deduplicated across mechanisms

In the real macho-arm64-symbols fixture the loader returns three _puts records: one stub with callable_entry 0x100000abc and two slot records at 0x100004000, one from the indirect symbol table and one from the chained-fixup stream. Exports are merged by name/address/forwarder in parseImage; imports are appended by each mechanism. Consumers address imports by stable ID, not by name, so this is explicit redundancy rather than a lost or merged fact.

Status and bounds

  • More than 4,096 UTF-16 units in the input yields limited with a resource_limit warning; an embedded NUL yields unrecognized.
  • Engine initialization failure yields unavailable plus an unavailable_semantics warning, not a failed import.
  • A parser limit or decoded output over 8,192 UTF-16 units yields limited; a decode that equals the mangled form is unrecognized.
  • The process-local cache is capped at 1,024 entries and 1,048,576 characters; ordinary non-mangled names do not enter it. Identities and original names are never changed.

C-name and library-lookup spellings

cSourceName removes one leading underscore for Mach-O and changes nothing for PE or ELF. libraryLookupName goes further for matching declarations: Mach-O drops the leading underscore and any $INODE64, $UNIX2003, $DARWIN_EXTSN or $NOCANCEL variant suffix (everything from the first $); ELF drops an @VERSION or @@VERSION suffix; PE strips the __imp_ import-thunk prefix. Windows A and W spellings stay distinct. There is no general C identifier sanitization: the native names remain the identity and these helpers only produce lookup/display spellings. src/metadata/symbols/c-names.ts (cSourceName, libraryLookupName).

Bounds, refusals and malformed inputs

Each loader is a parser of hostile input. It does not rely on the host process to catch a bad offset: every read goes through a bounded reader, every table is checked before iteration, and every count is either capped or charged to the operation budget.

Failure model

Structural failures throw an OperationError subclass: MachOError, PELoadError or ELFLoadError, each with a Diagnostic code. The default is malformed_image; a target outside the supported subset is unsupported_target; a budget breach is resource_limit; an unknown encoding version is unsupported_version. This means a caller never receives an empty image that looks valid: either the load succeeds with explicit diagnostics/capabilities, or it throws.

Mach-O additionally distinguishes optional metadata failure. A malformed symbol table, export trie or dyld stream becomes a warning and a partial capability while the structural image survives. PE and ELF keep all metadata in the load's failure domain; they use unsupported(...) for features they intentionally do not interpret, which records a capability and a warning without inventing semantics.

Typical refusals

Mach-O: ambiguous_slice when several ARM64 slices are supported; unsupported_target for an unknown magic, an unsupported CPU/subtype/filetype, or SG_HIGHVM; malformed_image for truncation, overlapping slices or sections, a section outside its segment, an entry point outside executable file-backed memory, or a mapping set that AddressMap rejects. PE: unsupported_target for a non-AMD64 machine, PE32, managed CLR, system driver or unsupported subsystem; malformed_image for alignment, table, directory or unwind contradictions. ELF: unsupported_target for the wrong class/endianness/machine/type, extended indexes, sectionless images, compressed native tables, RELR or Android packed relocations; malformed_image for segment/section/dynamic/version/relocation contradictions.

What the project stores

Import is deliberately two-phase. First the worker calls store.importImage, which stores the immutable bytes by SHA-256 and records the selected slice in image_imports, verifying the hash and refusing anything over 512 MiB. Then the loader output is prepared (names, runtime metadata discovery) and published in one transaction with putImage. src/project/store/index.ts (importImage, putImage).

putImage validates that the image matches an imported snapshot and that its bytes still hash to the claimed digest, then removes the two runtime-only members before persisting: 

export type ImageMetadata = Omit<LoadedImage, 'bytes' | 'address_map'>;
// …
const { bytes: _bytes, address_map: _map, ...metadata } = image;
writeImageMetadata(this.#db, metadata, revision);

src/project/store/image-metadata.ts (ImageMetadata), src/project/store/index.ts (putImage).

One header row goes into loaded_images, and every element of every collection becomes an ordered row in loaded_image_records. The schema is:

  FOREIGN KEY(image_id,slice_id,revision) REFERENCES loaded_images(image_id,slice_id,revision) ON DELETE CASCADE

Reading goes the other way: readImageMetadata checks the header identity and collection counts, rejects missing/oversized/reordered records, and enforces a 1,000,000-record and 64 MiB aggregate budget. readLoadedImage then re-reads and hashes the container, reconstructs the AddressMap from the stored mappings, verifies that the selected slice exists, and validates the domain records together with the map. A warm in-memory cache still re-runs the full-file integrity check, so replacing a stored image cannot go unnoticed. src/project/store/index.ts (readLoadedImage, #readImageBytes).

The stored image is a revisioned snapshot

loaded_images is keyed by (image_id, slice_id, revision). A published snapshot writes its complete ordered fact rows at that revision; reading at an older revision returns the newest metadata at or before it. Later analysis can therefore pin the exact loader facts it used, while AddressMap remains a derived object rather than a serialized one.

Limitations and extension points

The loaders are intentionally narrow static parsers. The supported subset is visible in their capability declarations and in the comments at the top of each implementation.

Known gaps

  • Targets. Mach-O only ARM64/arm64v8/arm64e little-endian 64-bit executable/dylib; PE only AMD64 PE32+ native user-mode EXE/DLL; ELF only ELF64LE EM_X86_64 ET_EXEC/ET_DYN with OSABI 0 or 3. There is no 32-bit, big-endian (except fat-table byte order), ARM64 PE, RISC-V or Mach-O kernel-cache support.
  • Runtime semantics. No ASLR slide, lazy binding, dyld shared cache, dependency loading, syscall behavior, PLT callable entry, IFUNC resolution, COPY relocation ownership or TLS runtime allocation is reconstructed. The analyzed addresses are linked/preferred addresses.
  • Mach-O. Kernel/cache and 32-bit chained formats, compressed chained names, threaded binds, SG_HIGHVM, scattered relocations, and full DWARF CFI augmentation are diagnosed rather than approximated. __eh_frame bytes are framed and retained, but PC ranges require a later DWARF consumer.
  • PE. CLR, PE32, drivers and non-GUI/CUI subsystems are refused. Bound imports without an original lookup table, unknown delay-import attributes, and language-specific exception handler payloads are not interpreted. CodeView records are metadata; PDB files are never opened.
  • ELF. Sectionless images, extended counts/indexes, ET_REL, compressed native tables, SHN_XINDEX, TLS symbol resolution, IFUNC, RELR, Android packed relocations and nonallocated relocation semantics are outside the subset. Non-executable PLT stubs remain code, not import entries.
  • Provenance. A loader fact proves what the file says at a file range, not what a runtime loader would do. A slot address is storage, not a resolved value; an export address may still be interposed at runtime.

Adding a new container format

  1. Extend the target vocabulary. targetSchema currently enumerates macho, pe, elf, two architectures and three ABIs. Adding a format, architecture or ABI requires changing that schema and the cross-field refinement, not just adding a loader. src/core/primitives.ts (targetSchema).
  2. Implement inspect. Return every slice with its container offset, size, architecture, subtype and support flag, plus diagnostics for unsupported slices. Reject truncated containers and unsafe counts here when they are structural. The method must be repeatable because load calls it.
  3. Build mappings first. Produce container-global file_offset values (for a sub-slice, add the slice offset), memory_size, file_size and permissions, then construct AddressMap exactly once. Do not create a second overlapping mapping set for sections.
  4. Emit facts with evidence. Use bounded readers over ImmutableBytes, call context.checkpoint per record or table entry, and create evidence for each non-obvious range. Preserve native names and IDs; put uncertain starts in hints rather than asserting functions.
  5. Separate structural from optional metadata. Follow Mach-O's State.optional pattern if a malformed name/fixup table should degrade the image to partial; otherwise follow PE/ELF and fail the load. Resource-limit and cancellation errors must never be swallowed as optional warnings.
  6. Declare capabilities. Report a format capability and, if native symbol/export tables have independent completeness, a separate feature capability using NATIVE_SYMBOL_TABLES_FEATURE so unrelated unwind/CFI gaps do not weaken name authority.
  7. Register and test. Export the loader from src/index.ts, extend the worker's magic selection in src/workers/runtime.ts, add fixtures with a loader-expectations.json entry, and add smoke/unit tests for slices, mappings, evidence, zero-fill, imports and malformed inputs. The store already persists any LoadedImage whose records satisfy the shared schemas.

Extending an existing format

For a new Mach-O load command, add its name to COMMAND_NAMES, bound it in the command switch, and preserve its raw fields; if it is optional metadata, wrap its parser in s.optional. For a new PE directory or CodeView kind, parse it behind Parser.file and call unsupported when you intentionally do not interpret it. For a new ELF relocation, add it to the RELOCATIONS table only when width and target semantics are actually known; otherwise leave the bytes and emit an unsupported diagnostic. In every case, keep the address spaces and evidence conventions unchanged; later stages resolve bytes through AddressMap.spans and expect every fact to be traceable to a native range.

The next stage consumes these tables directly: Function discovery and CFG seeds entries from entry_points, symbols, exports, import callable entries and hints, then decodes the mapped code.
