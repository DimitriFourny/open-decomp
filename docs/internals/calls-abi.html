Stage 06 · Interprocedural

ABIs, calls & callee summaries

This stage turns a function's SSA form plus an ABI profile into machine-level call facts, and then into an interprocedural interface for every call it makes. It is the only place where "what a register means at a call" is decided: argument carriers, result storage, stack offsets, clobbers, variadic tails and Objective-C selectors. Its output is not a recovered prototype — it is evidence that later source reconstruction may present.

Where this sits in the pipeline

The stage consumes the simplified SSA form of one selected function (page 05), the target's AbiProfile, the image-wide function and reference index, and a set of supplied declarations (library headers, DWARF, durable signatures and annotations). It produces two distinct objects that later stages must not confuse:

  • CallAnalysisResult from analyzeCalls: per call node, its resolved targets, contract observations with an AbiCallLayout, register candidates, explicit arguments, noreturn status, and per-exit function observations. This is intraprocedural evidence about the call boundary.
  • SourceEvidence from recoverSourceEvidence: an InferredCallee for each call whose interface was observed or summarized, carrying the callee's parameter and result storage, plus variadic and Objective-C facts. This is the interprocedural “summary” the source planner and emitters read; calls described entirely by an established supplied contract are rendered from that contract instead.

The orchestration is in executeDecompilation (src/service/analysis/index.ts). It runs resolveCalls and callDeclarations first, because type recovery needs grounded targets and typed contracts; then recoverTypes, which internally calls analyzeCalls and exposes it as TypeRecoveryResult.calls (src/analysis/types/index.ts); then structuring; then recoverSourceEvidence, which builds callee interfaces and can prepare other function bodies; then memory-shape refinement and emission.

Invariant — no name-based calling conventions

All three profiles are stateless and classifyCall is pure. The target's full contract (format, architecture and abi) is dispatched in pipelineComponents (src/service/analysis/versions.ts); src/reconstruction/boundaries.ts keeps the same mapping for boundary projection. No profile consults a symbol name, a host register set, a prototype string or the requested emitter.

The ABI model: one pure layout function

AbiProfile is deliberately small: physical facts plus one classifier. The profile does not know about IR, evidence or source languages. 

export interface AbiProfile extends ComponentIdentity {
  readonly id: Target['abi'];
  readonly architecture: Target['architecture'];
  readonly layout: DataLayout;
  readonly stack_pointer: RegisterDescriptor;
  readonly preserved: readonly RegisterDescriptor[];
  readonly link_register?: RegisterDescriptor;
  readonly stack_return_address_bytes: bigint;
  readonly red_zone_bytes: bigint;
  readonly unknown_call_clobbers: CallClobbers;
  classifyCall(signature: AbiSignature): AbiCallLayout;
}

Defined in src/core/contracts.ts (AbiProfile); see also AbiType, AbiLocation, AbiCallLayout and AbiSignature in the same file.

Member Consumer and meaning
layout Source-level widths (long_bits, long_double_bits vs long_double_storage_bits), stack alignment and aggregate maximum alignment. The layout feeds source type resolution; it is not a second type system.
stack_pointer, stack_return_address_bytes The register whose value anchors stack facts, and whether the return address is pushed. Both x86 profiles declare 8n; Darwin ARM64 declares 0n and names link_register X[30] instead. Every AbiLocation stack offset is relative to the callee-entry stack pointer, so consumers never re-add the hardware push.
preserved Registers a callee must restore. Used by the interface observer to reject callee-saved registers as incoming arguments and by stack recovery to delimit private state. Darwin's comment is explicit that x18 is platform-reserved and therefore not an allocatable callee-saved register.
red_zone_bytes A capability record only. The comments state it never establishes ownership of negative offsets or survival across calls; Windows declares 0n.
unknown_call_clobbers Conservative effects for a call with no known contract: registers, flags and memory: 'unknown_read_write'. Darwin includes only the upper 64 bits of v8–v15, because their low halves are preserved.
classifyCall Maps a typed AbiSignature to parameter/return locations, hidden result, stack bytes, shadow space, alignment, clobbers, implicit register inputs, diagnostics and a state of complete, partial or unsupported.

AbiLocation has three shapes. A register location names a descriptor plus value_offset_bits and width_bits: the offset indexes the source value, not the physical register, which is what makes an HFA member in s3 and the high half of a split 128-bit argument expressible. A stack location carries an offset, object size, alignment and the value offset. An indirect location carries the pointer location and the pointee size; the object bytes are never claimed to be in registers.

Invariant — partial means “stop allocating, do not guess”

Once a parameter's type cannot be classified, every later parameter gets an empty location list and stack_bytes is only the rounded known-prefix lower bound. Both the SysV and Darwin implementations say this in code comments, and when the supplied parameter list is only a known prefix, argument_count stays null. A partial layout therefore cannot be mistaken for “the remaining arguments are on the stack”.

implicit_register_inputs is the one place where a machine requirement is modelled without pretending it is a source argument. On SysV, a variadic or unprototyped call requires AL to hold an unsigned upper bound on vector-register usage. The classifier reports the minimum as the count of vector registers actually allocated and the maximum as 8n, with purpose vector_argument_register_upper_bound. observeImplicitRegisterInputs then records the observed fact and one of satisfied / violated / unknown; a partial layout can never establish satisfaction. The other two profiles return an empty list.

The three profiles

The profiles agree on the data model and disagree on everything else. The table is the quick reference; the subsections explain the algorithms and the deliberate refusals.

System V AMD64: recursive eightbyte classification

classify walks the resolved AbiType tree and produces a list of eightbyte classes from NO_CLASS, INTEGER, SSE, SSEUP, X87, X87UP and MEMORY. Aggregates allocate one class per eightbyte of the first 64 bytes, recursively classify each field at its absolute enclosing offset, and merge into the slots the field covers. merge is the psABI lattice: MEMORY dominates, then INTEGER, x87 forces MEMORY, otherwise SSE.

Three checks matter for accuracy. A field whose absolute offset violates its own alignment makes the whole aggregate MEMORY (this includes packed primitive leaves), and an aggregate larger than 64 bytes starts in memory. A mixed wider sequence is MEMORY, but an aggregate whose classes are all SSE/SSEUP across more than two eightbytes would need AVX semantics, so classify returns null — an explicit unsupported answer, not a guessed MEMORY. locations then consumes one INTEGER or SSE register per class; SSEUP does not consume a new register but widens the previous location.

Register exhaustion is all-or-nothing for an argument: if an aggregate needs more INTEGER or SSE registers than remain, the entire argument goes to the stack at an alignment of max(8, alignment), and the register cursors are not advanced. Default promotions apply only to anonymous arguments (variadic tail or unprototyped call): float becomes double, and 8/16-bit integers become signed 32-bit. A 16-bit float is refused because width alone cannot distinguish _Float16 from a storage-only half type.

Microsoft x64: slots, home space, indirect aggregates

Win64 has no independent register banks. Every argument consumes one slot; the first four slots map to rcx, rdx, r8, r9 or xmm0–xmm3 depending on its class, and slot 4 onward lives at 40 + (slot - 4) * 8 from callee-entry RSP. The 32-byte home area is always part of stack_bytes, even for a zero-argument function, and the final value is rounded up to 16.

classifyType is intentionally narrower than SysV: a plain aggregate of 1, 2, 4 or 8 bytes is passed as an integer of that width; every other supported aggregate is passed by pointer (the caller's copy), and __m128-sized vectors are also indirect. Other vector widths are unsupported because shape alone cannot distinguish the __m64 integer ABI class from a compiler vector extension. For variadic float arguments, the value is placed in both the SIMD register and the corresponding integer register, mirroring the shadow-store requirement.

Darwin ARM64: HFA/HVA, odd registers and variadic stack slots

The Darwin classifier returns a Shape: empty, integer, simd (with up to four homogeneous members), or indirect. An aggregate is simd only when every non-empty field is itself SIMD, fields are contiguous from offset zero, all members have the same width and vector-ness, and the total member count is at most four; otherwise a successfully classified aggregate larger than 16 bytes is passed indirectly, and one of at most 16 bytes is treated as an integer object. Nested HFA fields are flattened into members with absolute bit offsets, which is why a {float,float} inside a larger homogeneous aggregate still lands in consecutive s registers.

Allocation tracks ngrn and nsrn separately. A SIMD shape uses consecutive SIMD registers if all members fit; an integer shape needs ceil(size/8) integer registers. Crucially, Apple does not round NGRN to an even number for a 16-byte value, and an aggregate is never split between the last register and the stack: if it does not fit, the relevant cursor is exhausted (ngrn for integer/indirect shapes, nsrn for SIMD shapes) and the object moves whole to the stack. All stack offsets are relative to callee-entry SP, where the first anonymous argument is at +0.

For variadic actuals the profile departs from ordinary allocation: every anonymous argument goes to the stack, in eight-byte slots, while retaining natural alignment for 16-byte scalars and vectors. Anonymous HFA/HVA aggregates use eight-byte alignment so their members remain contiguous; integer and float promotions match SysV. This is the reason a Darwin call to fixture_variadic(3, 1.0, 2.5, -0.5) has its fixed count in w0 and all three doubles at +0, +8, +16.

Call analysis: facts, not prototypes

analyzeCalls is a single pass over the SSA blocks, sharing its work budget with stack recovery. Its contract is stated in the function's comment: it performs non-rewriting ABI observations, never prototype inference; contracts are explicit typed inputs, and names never establish signatures. The first thing it does is recoverStack, because every register and stack location must be inspected against a snapshot rather than against the final SSA values.

  1. Index contracts and resolutions. A contract's key is either {kind:'address', address} — image, address space and value — or {kind:'import', image_id, import_id}. Pointer storage is never a matching key. Each target is bounded first: aggregate field trees are traversed to depth 64 and charged to the budget, so a hostile recursive type cannot stall the pass.
  2. Collect call targets. A direct call contributes an established address target; an indirect call contributes one only if its target value evaluates to an address fact. Supplied resolutions are appended, and duplicates are allowed to survive so contradictions remain visible.
  3. Match contracts. Only contracts whose target is in the established set are trusted. Two established addresses of the same kind, or two trusted contracts with different headers, parameter types or complete counts, make the call conflicting. conflicting() fingerprints returns, variadic, fixed_parameter_count, calling convention and prototyped flag, plus the noreturn claim and every parameter type by index.
  4. Classify and observe. Each matching contract is run through abi.classifyCall; each parameter, hidden-result and return location is observed in the caller's snapshot at the call and in the output snapshot for returns. A stack location is read as SP + offset; an indirect location is one pointer read plus a pointee read when the pointer itself points into the stack. Sizes above 65,536 bytes stay unknown, and external memory is never read.
  5. Record status and noreturn. Status is conflicting, established (a trusted contract), candidate (a matching contract or resolution that is not trusted), or unresolved. Noreturn is yes only from an unopposed trusted contract. If the CFG still continues after the call, analyzeCalls reports the contradiction and removes nothing.
  6. Collect candidates. Initialized general registers at the call become register_candidates; parameter candidates are the incoming registers of semantic uses; return candidates are exit registers that are not themselves incoming values. These are candidates, never established parameters or results.

The function also supports prepared interfaces for calls without a contract. observePreparedCallInterfaces asks preparedCallArguments whether each ABI slot cell was authored: its definition must reach a load, a constant, a computation or a different entry register, on every path, with casts, extracts, concat and block parameters followed. Being merely live or initialized is not preparation, and the callable target itself is not evidence that the same value is the first source argument. Once a slot is witnessed, its whole physical carrier is kept, including unknown upper cells; trailing slots are not invented, and argument_list_complete remains false.

Result widths are handled symmetrically but in the opposite direction. createCallResultDemandIndex walks backwards from semantic roots — load and store addresses, call arguments and indirect targets, branch/switch conditions, return values — through call outputs, extracts, truncations, sign extensions, concats and block parameters. Each hit records the register root and the width actually consumed, so reading W0 never asserts the unknown high bits of X0. 

const output = outputs.get(value.id);
if (output) {
  const registers = demanded.get(output.call) ?? new Map<string, RegisterDescriptor>();
  const register = output.binding.register,
    high = register.offset_bits + offset + width;
  const previous = registers.get(register.root);
  registers.set(register.root, {
    ...register,
    offset_bits: 0,
    width_bits: Math.max(previous?.width_bits ?? 0, high),
  });
  demanded.set(output.call, registers);
}

Return storage

Result storage is tracked at three independent strengths. analyzeCalls records return_candidates per return terminator: general registers other than the stack pointer that are not themselves incoming values. Those are candidates, not a result list. possibleAbiReturnStorage(abi) then enumerates what the profile could ever use: it classifies one pointer-sized integer, floats of 32/64/80/128 bits, 4/8/16-lane i32 vectors, {word,word}, {f64,f64} and {f32×4} returns, unions the resulting register roots and widens overlapping widths. The answer is cached per profile in a WeakMap.

That capability set is not evidence. The function's comment is explicit that the synthetic probes' fields and offsets never become author structure fields and that a spare register is not thereby a result. With the built modules the register roots are arm64:x0[0:64], arm64:v0[0:128], arm64:x1[0:64], arm64:v1[0:64], arm64:v2[0:32], arm64:v3[0:32] for Darwin, x86_64:rax[0:64], x86_64:zmm0[0:128], x86_64:rdx[0:64], x86_64:zmm1[0:64] for SysV and only x86_64:rax[0:64], x86_64:zmm0[0:128] for Win64. Presentation combines this capability with observed written storage; when the final return projection is inferred and storage changed, reconstruction emits the return_storage diagnostic with the exact output and exit-scratch slices.

Callee summaries carry the complementary fact: NativeInterface.written_result lists the registers a body actually writes on exit, with types. Its comment draws the line that matters for recursion: consumption alone is not a write or extension guarantee, so a caller's demand never seeds a recursive dependency's contract.

Where contracts come from

A contract is always an explicit typed input. callDeclarations is the single place that turns declarations into SuppliedCallContracts, and it insists on a grounded use: an annotation signature is matched through CallScope.calls_by_subject; a DWARF signature is matched only when a direct call's address equals the debug function's address in the same image and va space; a source declaration is applied only to calls with a grounded target identity. Each application publishes an evidence record whose analyzer is pipeline-call-contracts. Library contracts come from recoverLibraryContracts, and the native worklist further filters them to abi_state === 'supported' with no conflicts (nativeLibraryContracts).

Source Strength Behaviour when contradicted
Library prototype (curated catalog + generated headers) Established for the exact import identity or callable entry Conflicting contracts survive as alternatives; no unique conclusion
DWARF signature Established unless the record is conflicting Marked conflicting, not silently preferred
Annotation / durable signature Asserted, established or conflicting, depending on status Retracted annotations are ignored; competing signatures conflict
Objective-C method encoding Established for that method implementation Unparseable encodings and non-unique records yield no signature
Observation (prepared prefix, result demand, callee summary) Physical, never a complete source prototype Supplements locations; a prepared prefix alone cannot close arity

Callee summaries and the dependency worklist

A callee summary answers a narrower question than a prototype: which physical registers and stack slots does this body read on entry, which does it write on exit, and can anything outside that set be read? The answer is built by preparing the callee body through exactly the same lifter/SSA/type pipeline as the selected function, then observing its calls and entry uses. Nothing is inferred from the caller's argument list. 

export type NativeInterface = Omit<InferredCallee, 'call_id' | 'evidence_ids'> & {
  readonly parameter_shapes?: readonly NativeParameterShape[];
  readonly source_interface?: Omit<NativeInterface, 'source_interface'>;
  readonly written_result?: {
    readonly registers: readonly RegisterDescriptor[];
    readonly types: readonly DataType[];
  };
  readonly argument_reaching_calls?: readonly string[];
};
export interface NativeSummary {
  readonly observed: NativeInterface;
  readonly evidence_ids: readonly string[];
  readonly reasons: readonly string[];
  readonly complete: boolean;
  readonly arity_complete?: boolean;
}

src/service/analysis/native-worklist.ts (NativeInterface, NativeSummary, NativeSummaryUnit, NativeDependency).

NativeSummaryUnit is the prepared body plus accounting: instruction, block and final/peak IR-node counts, its dependencies, evidence, human-readable reasons, budget_truncated and an optional arity_complete. NativeDependency carries the call id, target, demanded result registers, optional context assumptions, and the original subject ids used to publish a context-use proof.

Demand-first loading, then refinement

The worklist is deliberately not a whole-program sweep. Its documented rule is that a requested call's arity depends only on the target's own reads and, transitively, on the callees that an unobserved entry argument may reach. Everything else — callees wanted only for effects, results and memory shapes — is deferred.

  1. Schedule roots. For the selected function, recoverSourceEvidence passes its direct dependencies as root_dependencies (with roots: []), records their result demands, and probes the arity sub-closure breadth-first through demandArity. The probe uses argument_reaching; when the probe itself hits its work share, it narrows nothing and every call stays relied on. Callees that the argument cannot reach are queued in deferred.
  2. Schedule contexts. A body may be prepared under constant/alias assumptions derived from the call site (nativeCallContext). The context key is functionId@fingerprint(assumptions). At most max_contexts_per_function (4 in the pipeline) and max_contexts (64) are prepared; beyond that the generic body is used and a reason records that the interface is a conservative generic one.
  3. Load under a fair share. Each load or demand probe receives at most max(1, floor(remainingWork / 4)); the loader's own capacities (instructions, blocks, IR nodes) are also decremented. No new body starts once remaining work is below half of the initial allowance, so finished interfaces keep a reserve for the fixed point. Only a limit that matches this step's own reservation is recoverable; cancellation, deadlines, the global work limit and selected-body failures escape.
  4. Order components. dependencyComponents computes strongly connected components over loaded units and emits them callees-first (the code names the traversal Tarjan). A component is recursive when it has more than one member or a self edge. Non-recursive bodies are observed once, against final callee interfaces; only recursive groups iterate.
  5. Refine. Refinement gets three quarters of the work left after loading. A changed member enqueues only its direct callers inside the group; callers outside it are later components and observe the final result. Each body is visited at most max_refinements (64) times; exceeding that records native interface refinement limit (64) and leaves the body unfinished. Equality is a fingerprint of the whole interface, so transported types and evidence participate in the fixed point, not just register names.
  6. Close recursive groups coinductively. closeRecursive assumes every member closed with its current parameter list, re-observes each body once against those assumptions, and keeps the results only if every member then closes with exactly the assumed parameters. The rationale is in the comment: any actual read happens at a finite call depth, so a self-consistent assumption is a proof; otherwise the group stays open.
  7. Propagate limits. Reasons are propagated as a bounded fixed point, qualified by the callee name and kept as leaf identities so call chains do not grow. Arity completeness is inherited only through the calls in argument_reaching_calls; a callee that sees only observed parameters or computed values cannot widen the caller's argument list.
Invariant — absence is not a zero-argument declaration

A unit that was never observed is summarized with unresolved() — { parameters: [], returns: [], parameter_state: 'ambiguous', argument_list_complete: false } — and an unfinished body keeps whatever it had established. complete requires zero reasons and a non-ambiguous parameter state; arity_complete additionally requires complete machine call/stack semantics, an unambiguous parameter state, no budget truncation, no context fallback and no refinement limit.

budgetReason classifies a reason as budget-related by matching the words limit, capacity, reserve or budget. That single predicate decides whether the eventual diagnostic is resource_limit (“cut by budget”) or unavailable_semantics (“partial”).

Transferring callee facts into the caller

A summary is not copied wholesale onto the call. mergeNativeInterface combines the callee-proven interface with the caller-authored prepared prefix: callee-proven locations take precedence, prepared slots fill missing locations, integer cells of smaller width do not replace wider ones, and the result is re-ordered by parameterRegisters(abi) — a capability probe that classifies sixteen pointer and sixteen double parameters and returns the distinct register roots with the integer bank first and the SIMD bank second. argument_list_complete is forced to false because a caller prefix is not arity.

From there, nativeTypeSlices seeds per-cell scalar/vector lane types, nativeCallInputs observes the transferred parameter registers and stack parameters in the caller's stack snapshot, nativeStackParameters accepts only entry-backed reads as stack parameters (a private spill or write-before-read never becomes an incoming argument), and nativeReturnInterface computes the callee's written result storage. nativeShapeTransfers turns parameter memory shapes into transfers for refineMemoryShapes. The caller also learns the opposite direction: for every prepared unit that names the selected function as a dependency, that dependency's return_demand is replayed into SourceEvidence.function_return_demands, so a callee's consumption of the caller's result is visible without scanning incoming callers.

source_interface is a second refinement used when context assumptions, library tails or a callee's own source interface change the observation. It never replaces the checked interface; it is kept beside it in SourceEvidence.source_callees, and the source view prefers it for the same call only when the summary is arity-complete.

Two cache tiers and why they are invisible

Preparing a callee repeats the lifter/SSA/type pipeline, and the useful unit is the prepared body, not the final summary: the summary depends on demands and context, while the IR, types, call analysis and dependency list do not. The cache therefore stores PreparedNativeUnits and re-observes them on demand.

Tier 1: in-process WeakMap

preparedUnits is a WeakMap<LoadedImage, PreparedUnitCache> bound to the image object, the exact function and reference arrays, and an identity fingerprint over revision, image SHA-256, selected slice, target, pipeline versions, lifter, ABI and supplied native types. Entries are a least-recently-used Map capped at MAX_PREPARED_UNIT_SIZE = 1 << 18 retained size (instructions + IR nodes + evidence + traced reads), roughly 1 KiB of heap per unit according to the comment. A hit is served only when the current allowance is at least the entry's allowance, its instruction/block/node counts fit, and the dependency trace is present and its replay charges fit every enclosing allowance; the trace is replayed and the original preparation work is charged, so a cache hit consumes the same budget as a cold preparation.

Tier 2: the project's native_summaries table

createNativeUnitPersistence sits behind the in-process cache. It stores a row only when analysis caching is enabled and reusablePreparation holds: no instruction budget truncation, no reasons, and a complete call analysis. The row is keyed by (scope, function_id), where scope is a fingerprint of the format, project revision, image SHA-256, slice, target, component versions, lifter, ABI and supplied native types. The table is declared by NATIVE_SUMMARIES_TABLE in src/project/store/index.ts; store schema 6 adds it, and payloads are Brotli quality 4 over the store's graph encoding.

The row carries allowance and work from the reuse contract — never re-derived by the store — plus a digest over scope, function, revision and payload. A read validates the digest, decodes the payload, checks the envelope schema, identity fields, dependency targets against the current function list, and then re-reads every stored dependency read from the project at the current revision (verifyTracedReads). Verification itself does not charge the request; only preparing's charges are replayed. Any mismatch is a miss, and the unit is prepared normally.

Writes are batched: at most 8 MiB of pending payload before an early flush, written in the request's transaction or one batch at the end. A row larger than 16 MiB is not stored, and a prepared unit above MAX_PERSISTED_UNIT_SIZE = 8192 is skipped because encoding it costs more than a later reuse recovers. The per-project cap is DEFAULT_NATIVE_SUMMARY_BYTES = 64 * 1024 * 1024; rows of superseded revisions are dropped first, then the oldest writes. A cache write can never fail a request.

Identity includes the revision

The scope names the revision, so any annotation or other revision change invalidates every stored row; the next write deletes superseded rows. This is deliberate: a row must never be offered for a state in which preparing would produce a different unit.

There is no supplied prototype for fixture_check; it is a local function, so the caller's interface comes from the callee summary. That summary stays open because _fixture_check calls _fixture_indirect, whose body has an unresolved indirect target. The observed interface of _fixture_indirect therefore has parameter_state: 'ambiguous', and observeParameters's closedCallee test rejects an ambiguous callee; _fixture_check gets no argument_list_closure. _main reaches _fixture_check, so the chain propagates and the caller prints fixture_check(...). The same reason appears as callee summaries partial: _fixture_check: the diagnostic is attached to the dependency that stayed incomplete, not to the call site.

Ten obvious physical arguments, eight in x0–x7 and two in the outgoing stack slots — yet the list still carries an open marker. Invariant — a cache hit cannot change the result

--no-analysis-cache disables the in-process cache, the persisted tier and published-result reuse, but not the dependency collector: work charges, and therefore results, are identical. Running the same _main decompilation with --analysis-cache and with --no-analysis-cache produced byte-identical stdout in this repository.

The comparison to make is therefore not “with and without the cache” but “call site against callee interface”. _fixture_float decompiles to double fixture_float(double arg0, double arg1); the caller passes two constants in d0/d1 and still prints them in integer storage form. The summary supplies physical carriers and widths; presentation of a constant as a floating literal is a source-type decision made later, and it is not something the ABI layer asserts.

Objective-C sends and variadic tails

Objective-C is handled as a source-level interface over the same ABI facts. Two metadata forms are resolved: an import that names a dispatcher (_objc_msgSend, _objc_msgSendSuper, _objc_msgSendSuper2) or a runtime entry (_objc_alloc, _objc_alloc_init, _objc_opt_new, _objc_opt_class, _objc_opt_self, _objc_opt_isKindOfClass, _objc_opt_respondsToSelector), and a stub entry in __objc_stubs that names its selector directly.

  1. Find the selector. For a stub, the selector is metadata. For a dispatcher, the second integer argument register is SEL; it must be an exact 64-bit load of a slot in __objc_selrefs. A constant SEL argument without that load is not a proof.
  2. Get keyword arity. selectorArity counts colons. The interface is (receiver, SEL, keyword…); a stub's caller supplies no SEL, so that slot is filtered out.
  3. Type the keywords. The unique method type encoding for the selector is parsed; its parameter count must be arity + 2 for the encoding to be used. Without an encoding, or when that count disagrees, every keyword is a pointer-sized integer. The resulting AbiSignature is run through abi.classifyCall, and a non-complete layout, a hidden result, or a location that is not exactly one register of the declared width rejects the typed interface.
  4. Check caller preparation. If the caller prepares an FP/SIMD or integer argument register beyond the selector's arity, the message would have more actual arguments than the selector names, so the source interface is not applied and the physical call remains.
  5. Close or leave open. A non-variadic selector yields argument_list_closure: 'objc_selector'. A known variadic selector (for example an NSString format selector) closes only when the format argument is an exact string literal and the promoted actuals occupy Darwin's anonymous stack slots; otherwise it is marked variadic_stack: true. A constant stringWithFormat:@"%@=%ld" therefore produces a closed tail with exactly the two promoted actuals, while an unknown format leaves the tail open.

Method implementations are typed by objcMethodSignature: it requires a unique method record at the function address, parses the compiler's type encoding (which includes the result and both implicit parameters), and types self from the class's ivar layout at static offsets, including in-image superclasses. Categories belong to their class (Class(Category) becomes Class). Real output for -[ODCounter summary]: 

id -[ODCounter summary](ODCounter* self, SEL _cmd) {
  uint64_t value0;
  void* object;
  void* objc_claimAutoreleasedReturnValue_result;
  value0 = [NSString class];
  object = objc_claimAutoreleasedReturnValue([self label]);
  objc_claimAutoreleasedReturnValue_result =
    objc_claimAutoreleasedReturnValue([NSString stringWithFormat:@"%@=%ld", object, [self count]]);
  objc_release(object);
  return objc_autoreleaseReturnValue((uintptr_t)objc_claimAutoreleasedReturnValue_result);
}

Produced from test/metadata/fixtures/objc-foundation; the selector, keyword arity and %@/%ld argument classes come from src/service/analysis/objc-messages.ts and src/service/analysis/objc-signature.ts. The super dispatcher stays explicit (objc_msgSendSuper2(..., @selector(init))) rather than being rewritten into a message.

Variadic handling

Variadic calls split into two independent problems: allocation of unknown actuals, and closing the list from a library rule. Allocation is pure classifyCall: SysV promotes and allocates by class with the AL upper bound; Win64 promotes and duplicates float actuals in the integer slot; Darwin puts every anonymous argument on the stack. A fixed prefix still uses registers — the real layout for fixture_variadic is w0 for the count, then +0, +8, +16 for three doubles.

Closing is a separate, evidence-gated step. variadicRuleCalls accepts only calls whose status is established, whose recognized library contract carries a variadic_rule of kind format, scanf_format or open_flags, and whose rule argument has a finite, identical value set in every established observation. constantCandidates is limited to eight candidates and to constants, addresses, phis, selects and pure integer operators; entry values, loads, call results and cycles are unknown. variadicRuleFacts then parses the literal bytes (printfArgumentTypes, scanfArgumentTypes), or applies the Darwin open rule (O_CREAT is 0x200), and emits a signature with argument_list_complete: true only when every possible rule value agrees. A nearby string, mutable storage, a guessed name or a conflicting contract never closes a list.

On the callee side, nativeIncomingStackEscapes detects the shape of an escaping va_list: an exact pointer into the body's own incoming argument area that leaves it (an integer ABI argument register at a call or tail call, or a stored value). Such a body is marked variadic_stack, its arity never closes, and its caller keeps an open marker. Direct reads of the incoming stack area instead become stack_parameters, which is the case for _fixture_stack_args above.

Reading the diagnostics

Three caveats are frequently mistaken for failures of this stage. All three are produced by caveats in src/core/diagnostic-summary.ts, which groups equal diagnostics and renders one reader-facing line per cause.

Caveat text Diagnostic detail Emitted by Meaning
N calls with unresolved interface details.kind === 'call_interface' src/reconstruction/index.ts when a call is physical or its argument_list_complete is false Arguments after those shown are not established and the call's effects remain explicit. It is a per-call count, not one line per call.
return list unresolved (possible storage: …) details.kind === 'return_storage' with a storage list Same reconstruction pass, on a block whose return projection is inferred The listed changed outputs and exit-scratch slices may also carry results. The caveat unions the register names (at most six, then +N); the full slices stay in the envelope.
callee summaries partial: … / callee summaries cut by budget: … details.kind === 'callee_partial' with details.callee src/service/analysis/source-facts.ts for every dependency whose summary has reasons resource_limit becomes “cut by budget”, anything else “partial”. The native message itself lists the reasons, for example Native callee _fixture_indirect remains partial: unresolved control flow.

The cut-by-budget/partial distinction is made by budgetReason over the summary's reasons. A reason like native dependency load work reserve (…) or native interface refinement limit (64) is a budget cut and may be resolved by more allowance; unresolved control flow or an unsupported layout is a semantic limit. The selected body's own analysis stays available either way: the native worklist runs on an optional half of the remaining work, and unfinished interfaces are left unresolved rather than guessed.

Outside the digest, analyzeCalls reports its own diagnostics directly: unavailable_semantics for contradictory supplied targets/contracts or for a noreturn claim that contradicts a retained continuation, and invalid_input for a malformed fixed_parameter_count (severity error on the x86 profiles, a warning on Darwin). classifyCall diagnostics are copied into the result, so an unsupported x87 return or an unknown aggregate surfaces with the layout that produced it.

Adding a new ABI

  1. Create the profile. Add src/abi/<id>/index.ts with a class implementing AbiProfile. Keep it stateless and frozen; do not read symbol names, the host platform or the requested emitter.
  2. Describe the source layout. Fill DataLayout, including the long/long double distinction between precision and storage. Choose preserved, link_register, stack_return_address_bytes and red_zone_bytes from the ABI, not from observed code.
  3. Implement classifyCall. Return one AbiLocation per parameter cell with value_offset_bits indexing the source value; keep stack offsets relative to callee-entry SP. Set state to partial/unsupported as soon as allocation is unknown, and put a specific message in diagnostics. Fill implicit_register_inputs only for requirements that are not source arguments.
  4. Register it. Extend the Target.abi enum in src/core/primitives.ts, add a components entry and a targetPipeline case in src/service/analysis/versions.ts, add the profile to the profiles table in src/reconstruction/boundaries.ts, and export it from src/index.ts.
  5. Prove it. Add table-driven classification tests under test/abi/<id>/, including aggregates, register exhaustion, stack alignment and every refusal; the existing SysV and Win64 suites also contain compiler-evidence fixtures. Then add a service-level fixture under test/service/analysis/ so the profile is exercised through the worklist, not only through classifyCall.
What a new profile does not get for free

Caller-consensus closure, Objective-C selectors and variadic library rules are all layered above classifyCall. A new ABI must at minimum be compatible with parameterRegisters and possibleAbiReturnStorage, which probe the profile with synthetic signatures, and with nativeRegisterPrefix, which consumes the resulting register bank; a profile that answers unsupported to those probes will observe fewer parameters or results even when its real calls are fine.
